# 后端也要懂体验：接口怎么设计才不折腾前端？

> "体验"常被划给前端：骨架屏、loading 动画、微交互。但用户抱怨的"卡""点了没反应""数据不对"，八成出在后端——接口 3 秒才回、翻页翻出重复行、金额少一分、报错只有一句"系统繁忙"。这篇把体验拆成后端必须负责的三件事：**快不快、稳不稳、可不可预期**。

边界先说清：资源命名、状态码、版本策略属于契约骨架，[RESTful 接口怎么设计才不容易返工？](/system-design/basis/design-restful-api.html) 已讲透，这里不重复。换个视角——不看接口合不合规范，只看它落到用户身上是什么感受，以及前端为了兜住设计缺陷要多写多少胶水代码。

## 体验的三个抓手都在后端

| 维度   | 用户原话             | 后端决定的事                           | 常见甩锅       |
| ------ | -------------------- | -------------------------------------- | -------------- |
| 快不快 | "点一下转半天"       | 接口拆分、N+1、缓存预计算、长任务异步  | "网络慢"       |
| 稳不稳 | "报错了不知道咋办"   | 错误码分层、降级、限流退避、提交幂等   | "前端没做容错" |
| 可预期 | "刚才那条怎么不见了" | 分页排序口径、时区、金额精度、空值语义 | "数据就这样"   |

前端能做的只有三件事：把等待包装好看、把失败包装体面、把脏数据洗一遍——都不产生数据。3 秒的接口加十层动画还是 3 秒，区别只是用户从"这破系统"变成"这破系统但至少有个圈在转"。

## 延迟：用户记住的是 P95，不是平均值

100 次请求里 99 次 100ms、1 次 5 秒，平均 149ms 拿去做周报很漂亮，但 P95 是 1.8s、P99 是 5s——那 1 次恰好是每个用户点进详情页的第一发（缓存未命中）。均值把它抹平了，P95 才把它暴露出来。所以性能目标按 P95 定并写进验收口径（详情 P95 ≤ 800ms、提交 ≤ 1.2s），再谈下面四个手段。

**首屏只等非等不可的。** 订单详情最容易长成"什么都返回"的巨型接口：基本信息、物流、发票、风控、推荐、历史一个请求串行查六个下游。拆开后：

| 接口                        | 阻塞首屏     | 目标 P95 |
| --------------------------- | ------------ | -------- |
| `GET /orders/{id}`          | 是           | ≤ 300ms  |
| `GET /orders/{id}/timeline` | 否，展开才拉 | ≤ 500ms  |
| `GET /orders/{id}/related`  | 否，失败静默 | ≤ 800ms  |

拆接口不是为了微服务好看，是让首屏的等待只包含用户此刻必须看见的东西：晚 500ms 的推荐位没人感知，串在首屏里就是 2.8 秒白屏。

**批量接口替代 N+1。** 一页 50 条订单循环查买家，同机 1ms 的调用看不出问题，跨机房 30ms RTT 就是 1.5 秒：

```java
for (Order o : items) o.setBuyer(userClient.getById(o.getBuyerId())); // 50 次 RTT
Map<Long, User> buyers = userClient.batchGet(ids).stream()            // 1 次，内存对齐
        .collect(Collectors.toMap(User::getId, u -> u));
```

批量接口要把上限写进契约（`ids` 最多 200），超限明确报错，别默默截断。

**统计类改预计算 + 缓存。** 看板"今日产量"每次 `sum()` 扫二十万行稳定 800ms，改成 30 秒刷一张汇总表降到 15ms，代价是最多延迟 30 秒。这交换通常划算，但延迟要写在响应里：`{"output":12840,"asOf":"2026-07-14T10:20:00+08:00"}`——用户看到"数据截至 10:20"，对旧 30 秒的容忍度远高于对一个转三秒的圈。

**长任务走三段式。** 导出、对账、批量导入别挂一个请求等 60 秒：网关 30 秒就断，用户刷新连接就丢。

```text
POST /orders/exports      → 202 + {"taskId":"t_1001"} + Location: /tasks/t_1001
GET  /tasks/t_1001        → {"status":"RUNNING","progress":65,"phase":"WRITING"}
GET  /tasks/t_1001/result → 302 到预签名地址（结果落对象存储）
```

第三段给**结果地址**而不是把十万行塞进 JSON；进度用 1~2 秒短轮询就够，别为它上 WebSocket；提交接口自身也要幂等，否则连点两次跑两个任务。状态机与超时分段的细节见 [模型很慢，长任务怎么设计](/ai/ai-async-task-pipeline.html)。

## 列表与分页：最容易被当成"前端细节"的后端活

```sql
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 100000;
-- 扫描 100020 行 → 丢弃前 100000 行 → 只返回 20 行
```

用户在第 5001 页时慢在数据库里，前端换什么加载动画都没用。游标分页把"跳过 N 行"换成"从锚点之后取 N 行"：

```sql
SELECT id, create_time, amount FROM orders
WHERE (create_time, id) < ('2026-07-14 10:00:00', 1802345678901234567)
ORDER BY create_time DESC, id DESC
LIMIT 20;
```

| 能力                     | offset 分页          | 游标分页             |
| ------------------------ | -------------------- | -------------------- |
| 跳到第 N 页 / 显示总页数 | 可以（要额外 count） | 不行                 |
| 深翻页性能               | 越翻越慢             | 稳定，一次索引范围扫 |
| 数据插入时的表现         | 会重复、会漏项       | 锚点之后稳定         |
| 适合                     | 后台管理、结果集小   | 信息流、日志、导出   |

游标的限制要提前讲清：**不能跳页**，页码器做不了；**排序键必须等于游标键**，换个排序字段锚点就失效。它是信息流的方案，不是后台列表的方案。全量拉取（导出、对账）是另一类问题，痛点是 OOM 不是慢，见 [深分页怎么优化](/high-performance/high-performance-deep-pagination.html)。

**排序不稳定，列表就会抖。** 只写 `ORDER BY create_time DESC` 而这列有大量同值（同秒批量导入），行间先后由执行计划决定，两次查询可能不同——翻页时第一条重复、某条永远看不到。补唯一键兜底 `ORDER BY create_time DESC, id DESC`；游标比较要用元组 `(create_time, id) < (?, ?)`，只比时间会漏掉同秒数据。

**`total` 要不要实时精确。**

| 方案                           | 代价                                | 适用     | 前端显示      |
| ------------------------------ | ----------------------------------- | -------- | ------------- |
| 精确 `COUNT(*)`                | InnoDB 扫索引，千万行几百 ms 到秒级 | 后台管理 | "共 1,203 条" |
| 估算（计数表 / 元数据）        | 几乎免费，误差可能很大              | 大表前台 | "约 1200 条"  |
| 只给 `hasNext`（多取一条判断） | 免费                                | 无限滚动 | 到底就停      |

一个常见误解要纠：**InnoDB 的 `COUNT(*)` 不是读元数据**，它挑一棵最小的二级索引扫一遍，只是不读行数据，仍是 O(n)；只有 MyISAM 是 O(1)。`information_schema.TABLES.TABLE_ROWS` 官方口径就是估算值，统计信息没刷新时偏差可以很大。响应结构统一成 `{"items":[],"nextCursor":"...","hasNext":false}`，`nextCursor` 对前端是不透明字符串，以后换锚点字段不用改前端。

## 可预期性三件套：金额、时间、排序

同一份数据两次打开长得不一样，用户就怀疑系统坏了。

**金额。** 库里存 `DECIMAL(18,2)` 或最小单位整数（分），Java 用 `BigDecimal`（`new BigDecimal("199.90")`，别写 `new BigDecimal(199.90)`），**返回字符串**：`{"payAmount":"199.90","currency":"CNY"}`。`double` 的 `0.1+0.2` 不等于 `0.3`；就算后端用 `BigDecimal`，序列化成 JSON 数字后 JS 的 `Number` 还是双精度，大额会被吃掉。**时间。** 统一 UTC 存储，返回带偏移的 ISO-8601（`2026-07-14T10:20:30+08:00`）或明确 epoch 毫秒，时区转换交给前端。坑在类型：`LocalDateTime` 不带时区，序列化出 `2026-07-14T10:20:30`，前端 `new Date()` 按本地时区解释，服务器 UTC+8、用户 UTC+0 就差 8 小时；要带偏移用 `OffsetDateTime`。

**排序与筛选的默认值写进契约。**

| 参数              | 契约里写死                              | 不写的后果                                   |
| ----------------- | --------------------------------------- | -------------------------------------------- |
| `sort` 缺省       | `-createdAt,id`                         | 前端按更新时间展示、后端按主键排，两边都在猜 |
| `size` 缺省与上限 | 默认 20、上限 100，超限截断并回显实际值 | 前端传 1000 以为拿全了，其实只有 100 条      |
| 时间范围缺省      | 默认近 7 天（业务口径）                 | 前端硬编码，后端改默认值就两边错位           |

默认值不是"随便给一个"，它和验收口径一样属于契约，要写进文档并被测试覆盖——与 [需求怎么细化成可验收的条目](/engineering/engineering-user-story-ac.html) 里"形容词要变成数字"同一个道理。

## 错误体验：前端要能"据此决策"

```json
{
  "code": "ORDER_ALREADY_PAID",
  "message": "订单已支付，不能重复扣款",
  "traceId": "4f2a9c1e8b7d",
  "errors": [{ "field": "items[3].qty", "code": "OUT_OF_RANGE", "message": "数量需在 1~999" }]
}
```

`message` 给人看可直接展示；`code` 给程序判断，文案随便改它不变；`traceId` 给排查，用户截图就能定位那一次请求。

| 错误类别   | HTTP    | code               | 前端该做什么               |
| ---------- | ------- | ------------------ | -------------------------- |
| 未认证     | 401     | `TOKEN_EXPIRED`    | 静默刷新 token，失败跳登录 |
| 无权限     | 403     | `NO_PERMISSION`    | 提示即可，不要重试         |
| 参数不合法 | 400/422 | `FIELD_INVALID`    | 定位到字段标红             |
| 状态冲突   | 409     | `VERSION_CONFLICT` | 拉最新数据让用户重选       |
| 限流       | 429     | `RATE_LIMITED`     | 按 `Retry-After` 退避      |
| 下游异常   | 5xx     | `UPSTREAM_TIMEOUT` | 可重试一次，展示 traceId   |

**全都返 500 的接口，前端只剩一个选择：什么都不做，弹"系统繁忙"。** 全都返 200 也一样——前端得靠 `code` 白名单猜，漏一个分支就白屏。这套错误体怎么进契约、怎么校验真实响应，[前后端联调怎么少返工](/engineering/engineering-api-contract-testing.html) 有完整做法。

批量操作要部分成功 + 明细：`{"succeeded":48,"failed":2,"results":[{"index":3,"id":"1802...567","success":false,"code":"STOCK_NOT_ENOUGH"}]}`。整批回滚看着干净，但 50 条错 1 条就让用户全部重来，还不知道错在哪条；除非业务必须原子（扣款、批次库存），否则部分成功更好用，200 还是借 WebDAV 的 207，团队定一套。

## 提交与幂等：按钮防重挡不住网络重试

| 重复从哪来                                                      | 前端 `disabled` 挡得住吗 |
| --------------------------------------------------------------- | ------------------------ |
| 用户连点两下                                                    | 能                       |
| HTTP 客户端超时自动重试、网关重试、刷新页面再提交、弱网切网重发 | 都不能                   |

所以写接口要带**客户端生成**的幂等键，服务端用唯一索引兜底：

```http
POST /orders
Idempotency-Key: 7b1f4c2a-9d3e-4a55-8b1c-6f0d2e8a4c11
```

```java
try { idempotencyRepo.insert(key, userId); }                                // uk(idem_key)，插不进即重放
catch (DuplicateKeyException e) { return idempotencyRepo.findResult(key); }  // 返回首次结果
```

查重与执行必须在同一原子操作里，别"先 select 再 insert"——两个并发请求会同时查到"没处理过"。键必须客户端生成：服务端生成的话，客户端一重试就换了新 key，等于没做。

**"结果未知"比"失败"更麻烦。** 客户端超时了不知道写没写成，这时不要盲目重试写接口，先查：`GET /orders/by-request-key/{key}`——200 表示已成功，直接跳详情；404 表示确实没进来，可以重试。前端做乐观更新（先改本地再等响应）时，这个接口是失败回滚的唯一依据；没有它，回滚只能重新拉全量，比不做还难受。

## 空态与默认值：`null`、`[]`、字段消失不能三种都有

| 情况         | 该返回                       | 不该返回                                   |
| ------------ | ---------------------------- | ------------------------------------------ |
| 列表无数据   | `"items": []`                | `null`、省略字段、204、404                 |
| 单值对象没有 | `"invoice": null`            | `{}`（读 `invoice.status` 得到 undefined） |
| 数值/布尔    | 明确 `null` 或 `0` / `false` | 时有时无，或缺字段让 `if` 走错分支         |

Jackson 的 `default-property-inclusion=non_null` 会让空值字段**整个消失**，前端 schema 校验挂掉、TypeScript 类型跟着说谎——要么统一不裁剪，要么把规则写进契约。第一页没数据也要结构完整：`{"items":[],"nextCursor":null,"hasNext":false,"total":0}`。空态是正常业务结果，用 404 表达"没查到"会让前端把空页面当异常弹红条。筛选条件的默认时间范围、默认排序、默认每页条数同理，应由后端配置下发（或在响应里回显 `appliedFilters`）；前端硬编码一份，后端调一次就两边不一致，最后变成"我这边是好的"。

## 长连接与实时：什么时候值得上 SSE / WebSocket

| 方案        | 方向     | 成本                                     | 适合                      |
| ----------- | -------- | ---------------------------------------- | ------------------------- |
| 轮询 1~5 秒 | 客户端拉 | 最便宜，无状态，天然容错                 | 分钟级/秒级刷新、任务进度 |
| SSE         | 服务端推 | 占连接，要处理断线与代理缓冲             | 进度、通知、日志流        |
| WebSocket   | 双向     | 最贵：心跳、鉴权、网关升级、扩缩容要广播 | 协同编辑、聊天、高频行情  |

判据不是"实时听起来高级"，而是**延迟要求是否低于 1 秒，且事件频率是否高到轮询明显浪费**。两条都不满足，轮询 + 短缓存（`max-age=2`，网关和 CDN 都能兜）就是更便宜的退路——一千人在线看板也用不着长连接。

## 降级也是体验：旧数据带标记，比报错强

| 处理             | 用户看到                         | 什么时候用                       |
| ---------------- | -------------------------------- | -------------------------------- |
| 直接 500         | 白屏 + "系统繁忙"                | 数据错了会误导决策（余额、库存） |
| 旧数据 + `stale` | 页面正常，顶部提示"数据可能延迟" | 展示类、统计类、榜单             |
| 空数据           | "暂无数据"                       | 最差，分不清是没数据还是坏了     |

```json
{
  "items": [],
  "stale": true,
  "asOf": "2026-07-14T10:18:00+08:00",
  "degradedReason": "RECOMMEND_TIMEOUT"
}
```

限流同理：429 必须带 `Retry-After`（秒数或 HTTP 时间），不带的话前端只能写死 1 秒重试，越撞越狠。还有一类隐性问题——**超时倒挂**：前端 3s、后端 5s，前端放弃并提示失败、后端 5 秒后写成功，用户重试就重复；网关 30s、后端 60s，网关 504 而后端还在跑。正确方向是前端 > 网关 > 后端，或者长任务直接换异步三段式。

## 反馈闭环：把"体验"变成能看的数

埋点标签用 `path + method + status + code`，path 归一化成 `/orders/{id}`，否则指标基数爆炸。核心接口盯四个数：成功率、P95、错误码 TopN、429 比例（比如 `order_detail_p95 620ms` 对 SLO 800ms）——和业务指标放同一个看板，"接口慢"不能只活在 APM 里。错误页展示 traceId 短码（八位够），用户报障发张截图就能定位。统一异常处理、traceId 透传、指标拦截器应该长在工程骨架里，而不是每个 Controller 各写一遍，落地位置见 [从 0 搭一个可交付的 Spring Boot 多模块工程](/engineering/engineering-project-scaffold.html)。

## 反模式：一出现，前端就开始写胶水代码

| 反模式                            | 用户看到                  | 后端在付什么       |
| --------------------------------- | ------------------------- | ------------------ |
| 一个列表接口返回 200 个字段       | 首屏 1.2MB JSON，慢在解析 | 带宽与序列化       |
| 让前端全量拉再自己切页            | 第一页等 3 秒             | 每次请求扫全表     |
| 错误只返回 `{code: 500}`          | "系统繁忙"，无从下手      | 排查靠猜           |
| 时间字段时区不明、金额用 `double` | 差 8 小时 / 少一分        | 客服工单与财务返工 |
| 排序不稳定                        | 刷新后顺序变了、翻页重复  | 用户以为数据错乱   |

## 面试怎么答

挑一个你改过的接口，按"改了什么 → 量化收益 → 怎么验证"讲，别只背术语：

```text
背景：订单详情页一个接口串行查 6 个下游，P95 2.8s，前端只能一直转圈。
改动：拆核心接口 + 3 个折叠区接口，首屏只等核心；买家信息从 50 次单查改成 1 次批量；
      统计改预计算 + 30 秒缓存并返回 asOf；提交加 Idempotency-Key 与按 key 查单接口。
结果：首屏 P95 2.8s → 480ms；重复提交 0.3% → 0；前端删掉约 200 行判空与兜底代码。
```

面试官想听的不是"我知道要看 P95"，而是"我改过哪个接口、收益多少、怎么证明不是巧合"——压测前后对比、埋点曲线、灰度期间错误码分布都行。量化不出来的收益，通常也不是真做过的事。

## 容易踩的坑

- **每页都算精确 `COUNT(*)`**：千万级表翻一页扫一次索引，比数据本身还贵。
- **只按时间列排序就上翻页**：同值行顺序不保证，重复和漏项都这么来的。
- **做了游标分页却保留"跳到第 N 页"**：锚点对不上，跳过去数据是错的。
- **`size` 不设上限**：`size=100000` 直接打穿内存或触发超时。
- **幂等键让服务端生成**、**用空格分隔的日期字符串**（Safari 里 `Invalid Date`）、**以为前端加个 loading 就能等**：三条都是"看起来做了其实没做"。

## 小结

- 体验的三个抓手在后端：延迟看 P95 不看均值，稳定看错误能否决策，可预期看分页/排序/时区/金额口径是否统一。
- 首屏只等非等不可的接口；批量替代 N+1；长任务走"提交 + 进度 + 结果"，不挂 60 秒同步请求。
- 深翻页用游标分页（不能跳页，排序键必须等于游标键）；`total` 按场景选精确/估算/`hasNext`；排序必须有唯一键兜底。
- 金额返字符串、时间返带偏移的 ISO-8601、默认排序与 `size` 上限写进契约。
- 错误体要"人话 + 稳定码 + traceId"，批量给部分成功明细；写接口用客户端生成的幂等键，超时后查状态而不是重试写入。

## 参考

综合自仓库内接口设计与契约测试相关材料、MySQL 分页与执行计划实践，并交叉核对了几处容易写错的事实：InnoDB 的 `COUNT(*)` 需扫索引而非读元数据（只有 MyISAM 是 O(1)），`information_schema.TABLES.TABLE_ROWS` 对 InnoDB 是估算值；同值列排序 SQL 标准并不保证稳定；Jackson 的 `NON_NULL` 会让空值字段消失；Safari 无法解析空格分隔的日期字符串。游标分页口径与站内分页专题一致，长任务部分与异步任务流水线一篇互链。
