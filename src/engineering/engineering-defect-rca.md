# 线上缺陷怎么复盘？RCA 写到什么程度才有用？

> 复盘真正的产出不是一份文档，而是几条**能被检查和验收的改动**：下次同样的信号出现时，能更早发现、更容易止血，或者根本不会发生。文档写得再漂亮，改进项挂着没人接，这次事故就等于白出。

线上出问题后的那两小时，多数团队的动作是混乱的：有人猜原因，有人直接改代码，有人安抚客户，还有人已经在写"故障说明"。等风头过去，补一份文档，把"某某操作不规范"写上，事情就算翻篇。这套流程的问题不在于不努力，而在于**顺序错了、证据缺了、产出不可验收**。这篇按真实值班的顺序讲：先分清缺陷和事故，怎么定级，怎么止血，怎么用证据链定位，最后把根因和改进项写到"别人能照着验收"的程度。

## 先把两个词分开：缺陷和事故

这两个词常被混着用，但它们回答的问题不一样，处理方式也不一样。

| 维度         | 缺陷                                      | 事故                                            |
| ------------ | ----------------------------------------- | ----------------------------------------------- |
| 定义         | 系统行为不符合预期                        | 已造成用户影响、有明确影响面和时长的事件        |
| 触发条件     | 代码/配置/设计里客观存在                  | 缺陷 + 触发条件 + 防护没拦住，三者同时成立      |
| 是否影响用户 | 可能完全没有（内部报错、边界用例错）      | 一定有，哪怕只是部分租户、部分时段              |
| 处理与产出   | 走缺陷单按优先级排期，产出修复 + 回归用例 | 立刻响应，产出止血记录 + 证据链 + 复盘 + 改进项 |

一句话：**缺陷是埋着的雷，事故是炸了的那颗**。同一个缺陷可能上线半年都没炸（触发条件没出现，或者被兜底挡住），也可能在大促凌晨爆掉。所以"我们代码里有 bug"不需要复盘，"这个 bug 为什么穿过四道防线影响到用户"才需要。反过来也要防另一种偏差：把每条 P3 的样式错乱都拉全组开复盘会，团队很快学会"复盘就是走过场"，真出大事反而没人认真对待；P3 登记进 [技术债](/engineering/engineering-tech-debt-refactor.html) 里按优先级还，比开会更有用。

## 定级：看影响面，也看可绕过程度

定级不是给领导看的标签，它决定**多久响应、谁到场、要不要对外通报、复盘到什么粒度**。凭"感觉严重"定级，最后一定变成"领导觉得严重就 P0"。两个维度够用：

- **影响面**：受影响用户/租户数、涉及订单与金额、是否资损、数据是否错乱或丢失、是否不可逆。
- **可绕过程度**：用户还有没有别的路走——降级路径、备用通道、人工兜底。有路可走，等级往下压；完全没路，哪怕只影响一个核心租户，也按最高级处理。

| 等级 | 判据（满足其一即成立）                                                          | 响应要求                                                    |
| ---- | ------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| P0   | 核心链路完全不可用；资损或资金错账；数据错乱/丢失；大面积用户受影响且无降级路径 | 立即拉应急群，15 分钟内给出止血方案，每小时同步，24h 出初版 |
| P1   | 主流程部分不可用或严重变慢；有降级路径但用户可感知；影响集中在某类用户或某区域  | 30 分钟内响应，1 小时内止血或明确方案，48h 复盘             |
| P2   | 非核心功能异常；个别用户；有明确绕行方案；错误率小幅抬升但业务结果正确          | 当日响应，按排期修复，一周内轻量复盘                        |
| P3   | 体验瑕疵、内部报错但结果正确、日志噪音                                          | 排期处理，不打断迭代，登记技术债                            |

判据要写成**可观测的阈值**（错误率、受影响用户数、资损金额、时长），而不是形容词，否则每次出事都要重新吵"这算不算严重"。定级也不是一锤定音：止血阶段先粗定，恢复后按真实影响修正，修正过程写进复盘。

## 顺序：止血第一，定位第二，修复第三，复盘第四

```mermaid
flowchart LR
    A["发现异常"] --> B["止血<br/>先让用户能用"]
    B --> C["定位<br/>证据链找触发点"]
    C --> D["修复<br/>改代码/改配置"]
    D --> E["复盘<br/>根因 + 改进项"]
    C -.->|"证据够了就开工"| D
    B -.->|"不阻塞"| C
```

四个阶段的主导者不同：止血由值班和应急负责人拍板，定位交给熟悉这条链路的工程师，修复归模块 owner，复盘由事故负责人牵头。最容易被搞反的是第一条——**止血决定不需要等根因**：值班的人不需要知道"为什么回调解析失败"，只需要知道"关掉新渠道开关，用户就能付款"。坚持"查清再说"，影响面还在扩大，用户还在重复支付。同样容易搞错的是把修复当止血。止血常常是回滚或关开关，修复是改代码，两者可能差好几天；复盘要分别记这两个时间点，否则 MTTR 会被算得很难看。

## 止血手段清单：每一种都有代价

止血的本质是**用可控的代价换时间**。常用的六种，按生效速度和代价排：

| 手段   | 典型动作                             | 生效速度   | 代价 / 风险                                      | 适合场景                 |
| ------ | ------------------------------------ | ---------- | ------------------------------------------------ | ------------------------ |
| 回滚   | 切回上一个制品 digest、回退配置      | 秒级到分钟 | 依赖数据库兼容；DDL 通常不可回滚；会带回旧 bug   | 发布后一小时内出现的异常 |
| 开关   | 关掉新功能/新策略/新渠道             | 秒级       | 开关背后的老代码可能半年没跑过，关掉照样出错     | 新功能引入的问题         |
| 限流   | 网关按接口/租户限速、排队            | 秒级到分钟 | 牺牲部分正常用户，是有损止血，限太狠会误伤大客户 | 流量突增、容量不足       |
| 降级   | 读缓存兜底、返回默认值、关非核心校验 | 分钟级     | 数据可能短暂不一致，事后要有人核对补偿           | 下游依赖故障             |
| 摘流量 | 摘掉单实例/单可用区/单机房           | 秒级到分钟 | 剩余节点容量下降，雪崩风险转移，需健康检查配合   | 单机、单可用区问题       |
| 改配置 | 调线程池、超时、连接池、日志级别     | 分钟级     | 需要重启或热更新，改错会制造第二次故障           | 参数不合理、配置漂移     |

口诀：**先能退（回滚），再能关（开关），再能限（限流/降级），最后才改代码。** 改代码永远排最后，因为它最慢、最容易引入新变量。这些手段能不能用，取决于平时有没有准备：制品能不能一键回滚、开关清单在不在、降级预案写过没有。[滚动、蓝绿、金丝雀怎么选](/engineering/engineering-container-release.html) 讲的是同一件事的上游——发布时就该把退路准备好；出事那一刻才去找开关在哪，止血只能靠猜。

## 定位：靠证据链，不靠直觉

定位最怕"先猜原因，再找证据支持自己"。正确做法是先把现象固定成数据，再决定打开哪类证据。这套口径在 [一次慢请求怎么定位](/high-availability/high-availability-slow-request-tracing.html) 里是分层切段，放到事故里就是**时间、变更、四类证据**三条线并行推进。

**先把时钟对齐到同一分钟。** 日志、指标、链路、发布记录来自四五个系统，时区、时钟漂移、采集延迟各不相同；不对齐时间，后面所有因果关系都是错的。做法就三步：全部换成同一个时区并写进模板；以指标拐点为锚点，把日志、链路、发布记录对齐到分钟（允许 ±1 分钟）；记下各系统的采集延迟（日志常滞后 10 秒到 2 分钟），别把"日志里还没出现"当成"没发生"。

**变更关联：最近 24 小时到底动过什么。** 绝大多数线上异常和变更有关系，而"变更"远不止代码发布；变更记录要能查、带操作人和时间，否则每次定位都得挨个问人——这本身就是一条流程改进项。每次定位都过一遍这份清单：

- 应用发布、镜像/基础镜像升级、依赖 SDK 升级
- 配置中心变更、环境变量、开关状态
- DDL、数据修复脚本、索引变更、批量刷数
- 流量侧：投放、活动、爬虫、压测、上游突然放量
- 证书与域名：TLS 过期、DNS 记录、CDN 回源配置
- 中间件与基础设施：连接数上限、配额、扩缩容、定时任务时间调整、云厂商事件

**四类证据怎么分工。** 分工和 [可观测三支柱](/high-availability/high-availability-observability-pillars.html) 一致：指标负责发现，链路负责定位到哪一跳，日志负责还原这一跳发生了什么，数据库证据把"这一跳"再拆到 SQL 和锁。四类不是四选一，而是从粗到细逐层收窄。

| 证据类型 | 具体看什么                                             | 典型线索                                                                                                                    | 常见坑                                  |
| -------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| 日志     | ERROR/WARN 突增、异常栈首因、业务错误码分布            | `Connection is not available`、`Deadlock found`、`SocketTimeoutException`、`OutOfMemoryError`、`RejectedExecutionException` | 只读最后一条，被上游重试和兜底日志淹没  |
| 指标     | QPS、错误率、P99/P999、线程池队列、连接池等待、GC、CPU | 拐点与变更时间是否重合；是单实例还是全集群                                                                                  | 只看均值不看尾部；只看集群不看单机      |
| 链路     | 同一接口的 span 耗时分布、下游 RT、重试次数            | 某下游 span 占比从 20% 涨到 85%；同一请求里出现多次重试                                                                     | 抽样抽不到异常请求，要按错误标记反查    |
| 数据库   | 慢查询、锁等待、连接数、复制延迟、死锁日志             | `slow log`、`innodb_lock_waits`、`SHOW PROCESSLIST`、`SHOW ENGINE INNODB STATUS`                                            | 慢日志阈值太大，2 秒的 SQL 根本没进日志 |

**现象 → 先查哪类证据。** 不确定从哪下手时，用这张表分流，比在群里问"是不是数据库有问题"快得多：

| 现象                      | 第一优先证据               | 理由                                   |
| ------------------------- | -------------------------- | -------------------------------------- |
| 发布后十分钟内错误率上升  | 变更关联 + 日志异常首因    | 时间相关性最强，先看这次发布改了什么   |
| 无发布，全实例一起变慢    | 链路耗时分布               | 大概率是公共依赖：数据库、缓存、下游   |
| 只有某几台机器异常        | 该实例指标 + 线程栈        | 本地资源、GC、配置漂移、宿主机问题     |
| 错误码集中在超时          | 链路 + 下游 P99 + 重试次数 | 可能是超时阈值和重试放大，形成重试风暴 |
| 数据库 CPU 不高但写入很慢 | 锁等待 + 慢查询            | 等锁几乎不消耗 CPU，指标上很"安静"     |

## 根因分析：三种方法，各有各的适用与陷阱

### 5 Whys：连问五层，但别停在"操作失误"

5 Whys 的价值不是问满五次，而是**逼自己从"谁做错了"走到"系统为什么允许它发生"**。停在前两层，得到的永远是"人不够仔细"这种挂不上任何改进项的结论。看一个例子：某次上线后部分订单卡在"支付中"，用户重复付款。

| 层级 | 问                           | 答（必须是可改动的事实）                                              |
| ---- | ---------------------------- | --------------------------------------------------------------------- |
| 1    | 为什么订单卡在支付中？       | 支付回调消息消费失败，重试三次后进死信队列，没有补偿任务              |
| 2    | 为什么消费失败？             | 新增的渠道枚举 `UNIONPAY` 在消费端没有映射，反序列化直接抛异常        |
| 3    | 为什么漏了映射？             | 生产端和消费端各自维护一份枚举，没有共享契约                          |
| 4    | 为什么各自维护也没人发现？   | MQ 消息体没有版本号和字段约束，也没有兼容性测试，变更不需要下游评审   |
| 5    | 为什么消息体变更进不了评审？ | 发布检查单只覆盖 HTTP 接口契约，MQ 消息体被当成"内部实现"，默认不通知 |

走到第五层，改进项才浮出来：消息体加版本号、消费端把未知枚举降级为"待处理"并告警、消息体变更纳入发布检查单、补兼容性回归用例——分别对应防护、检测、流程、测试，比"加强代码评审"有用得多。判断有没有停早，有个简单测试：**这一层的答案能不能直接改？** "开发不仔细"改不了，"枚举没有共享契约"能改；同理，"手滑点错"要拆到"为什么没有二次确认、为什么权限给到了这一步"，"测试没覆盖"要拆到"为什么这类场景不在回归清单里、谁维护这份清单"。改不了的，就还没到底。

### 时间线还原：把延迟拆成三段

把"第一次异常信号"到"恢复"的每个节点标出来，算三个差值。三段延迟分别指向三类问题，改法完全不同：

| 时间  | 发生了什么                     | 证据来源      | 延迟归因                             |
| ----- | ------------------------------ | ------------- | ------------------------------------ |
| 20:41 | 消费失败率开始上升（首次异常） | 指标拐点      | —                                    |
| 21:13 | 客服转来用户投诉，值班介入     | 工单 + 群记录 | 发现延迟 32 分钟 → **监控/告警缺口** |
| 21:20 | 拉应急群，确认影响面           | 群记录        | 响应延迟 7 分钟 → **流程/值班缺口**  |
| 21:47 | 关闭新渠道开关，止血           | 开关操作记录  | 处置延迟 27 分钟 → **预案/权限缺口** |
| 22:05 | 失败率回落，用户恢复           | 监控          | 恢复延迟 18 分钟 → **技术能力缺口**  |

好处是把"我们反应太慢"这种笼统评价，拆成"监控没告警""告警没通知到人""有权限的人不在群里"三个能分别修的问题：发现延迟长补告警，响应延迟长改值班和升级机制，处置延迟长补 runbook 和权限。

### 变更关联：用二分法验证，而不是猜

1. 有了候选清单，先别开会讨论"哪个最可疑"：按时间倒序列出 24 小时内的变更，标注可回滚性。
2. 挑时间最接近、机制上最可能的那一个，回滚或关开关。
3. **一次只动一个变量**，观察 5 到 10 分钟内同一指标是否回落。
4. 回落就锁定；没回落就标记"已排除"并记录证据，换下一个；无法回滚的（已执行的 DDL）用开关或降级绕过验证。相关性不等于因果，但发布窗口内的时间相关性已经足够支撑回滚决策——先止血，再证因果；最忌讳回滚 A 没好转又顺手改 B、重启 C，最后什么结论都拿不到。

## 复盘文档：一份能直接套的骨架

复盘文档的读者是三个月后遇到类似问题的同事，以及要做验收的 leader，所以它要能被检索、被引用、被检查。按七块写，第四、五块是分水岭——只写直接原因，改进项会全落在代码上；写了"为什么没早发现"，才长得出告警、流程、测试类的改进项。

1. **一句话结论**：什么事、影响多久、根因是什么，三句话内说完，放文档最上面。
2. **现象与影响**：影响用户/租户数、涉及订单与金额、是否资损、数据能否修复；时长写"首次异常到恢复"，同时单独标"发现到恢复"。
3. **时间线表**：按上文格式，标出三段延迟和证据来源。
4. **直接原因与根本原因**：直接原因是触发点（哪个枚举、哪条 SQL、哪次配置），根本原因是"为什么这个触发点能造成这么大后果"，必须分技术和流程两层。
5. **为什么没早发现**：四个缺口逐个自查，没有就写"无缺口，已有告警在 X 分钟触发"，别空着。
6. **改进项表**：动作、类型、owner、截止、验收方式，缺一列就不算写完。
7. **哪些不是这次的原因**：把排查中排除的假设写清楚，防止过度归因，也方便下次直接跳过。

### 为什么没早发现：四个缺口自查

| 缺口 | 自查问题                                   | 合格的样子                                     |
| ---- | ------------------------------------------ | ---------------------------------------------- |
| 监控 | 这个失败模式有对应指标吗？阈值是多少？     | 消费失败率 > 0.5% 持续 2 分钟触发告警          |
| 告警 | 通知到人了吗？有人认领吗？有 runbook 吗？  | 告警带负责人和处置步骤链接，5 分钟内有人响应   |
| 测试 | 有覆盖这个场景的用例吗？在哪个环境跑？     | 集成测试有用例，且每次合并都跑                 |
| 评审 | 这次变更有人评审吗？评的是兼容性还是风格？ | 涉及消息体/枚举/契约的变更，必须有下游参与评审 |

四个缺口里通常至少两个是真的。别四格全写"已具备"——真都具备，这次就不会出事故了。跨团队的评审和通知推不动时，[跨团队怎么对齐、怎么推动](/engineering/engineering-cross-team-collaboration.html) 里那套"把口头约定变成可验证物"的做法可以直接搬。

## 改进项：可验收才算改进

复盘最容易失效的地方就在这里：写下一堆"加强""提高""完善"，看着全面，实际没人能判断做没做完。

| 不可验收（写完就烂在文档里） | 可验收（别人能检查）                                      |
| ---------------------------- | --------------------------------------------------------- |
| 加强测试                     | 给下单接口补 3 条幂等回归用例，纳入 CI 冒烟，本周五前     |
| 提高安全意识                 | 发布检查单加一条"MQ 消息体兼容性确认"，附下次发布记录     |
| 加强监控                     | 新增告警规则（ID 可查），阈值 0.5%/2 分钟，造故障验证触发 |
| 优化代码结构                 | PR 已合并，线上观察 7 天无同类异常                        |
| 完善流程                     | 把消息体变更写进评审模板，下一次发布按模板执行并留痕      |
| 后续持续关注                 | 指定 owner + 截止日期 + 验收证据，到期在周会过一遍        |

判断标准很简单：**这条改进项能不能被一个不在场的人验证？** 说得出"在哪看、看到什么算通过"，就是可验收的。改进项还要分类，否则团队会本能地只补技术：

| 类型 | 作用                 | 典型例子                                               | 常见遗漏              |
| ---- | -------------------- | ------------------------------------------------------ | --------------------- |
| 检测 | 让下次更早发现       | 告警规则、日志字段补齐、看板与 SLI、死信队列监控       | 只加日志不加告警      |
| 防护 | 让问题不易发生或扩大 | 参数校验、幂等键、限流、超时与重试预算、熔断、降级兜底 | 只在入口加，下游裸奔  |
| 流程 | 让变更被看见、被拦住 | 发布检查单、变更审批、变更窗口、跨团队通知、回滚演练   | 流程只写在文档里      |
| 测试 | 让回归能自动发现问题 | 回归用例、契约测试、故障演练                           | 用例不进 CI，等于没写 |

四类至少各一条，复盘才算覆盖完整。只有防护没有检测，下次还是靠用户投诉发现；只有流程没有测试，靠人肉保证质量，迟早要漏。

## 度量：复盘质量不看文档长度

| 指标             | 定义                                   | 口径陷阱                                                 |
| ---------------- | -------------------------------------- | -------------------------------------------------------- |
| MTTD（发现）     | 首次异常信号到被发现的时长             | 别拿"用户投诉时间"当发现时间，也别只统计值班发现的那部分 |
| MTTR（恢复）     | 首次异常到恢复的时长                   | 止血与修复要分开统计，否则数字好看但没有意义             |
| 重复故障率       | 同类根因在 N 个月内再次发生的比例      | 分类口径必须固定，否则永远是 0                           |
| 改进项按期完成率 | 到期改进项中按期关闭且有验收证据的比例 | "关闭"不等于"验收"，没有证据不算完成                     |
| 告警有效率       | 触发的告警中被确认为真问题的比例       | 误报率过高，团队会把告警静音，MTTD 反而变长              |

一份三页复盘加四条按期关闭的改进项，价值远高于两万字的"深刻反思"。**复盘质量只看两件事：改进项有没有落地并被验证，同类故障有没有再发生。** 排版、字数、措辞都不重要。

## 和面试怎么讲

被问到"讲一次你处理过的线上故障"，多数人讲成流水账："那晚报警，我们查了半天，最后发现配置写错了，改完就好了。"这种答法听不出工程能力。稳的讲法是固定五段，每段都有落点：

1. **现象与影响**：哪个功能、什么表现、影响多少用户、持续多久、有没有资损。
2. **你怎么止血**：先做了什么让用户恢复（回滚/开关/限流），为什么选这个，多久恢复。
3. **证据链怎么定位**：先看哪个指标，怎么用 `traceId` 切段，日志里哪个异常首因，锁等待或慢查询怎么确认，怎么用二分法排除变更。
4. **根因两层**：直接原因（技术触发点）+ 根本原因（为什么流程和防护都没拦住）。
5. **改进项与验证**：四类改进各做了什么，怎么验收，之后同类问题有没有再发生。

真正拉开差距的是第 3 段和第 5 段：前者证明你不是靠猜，后者证明你有闭环。工具放在证据链里顺带说一句就够——"用 Arthas 抓了线程栈"远不如"从 P99 拐点定位到库存服务 span 占比从 20% 涨到 85%，再用慢日志确认缺索引"有说服力。

## 容易踩的坑

- **复盘开成追责会**：一旦有人被点名，下次发现异常的人会先想着怎么掩盖，MTTD 反而变长。讨论对象该是"系统为什么允许这个错误通过"，不是"谁手抖了"。
- **根因停在"人为疏忽"**：这句话挂不上任何改进项。人的失误是设计输入，不是根因——要问的是"为什么流程允许这一步靠人记"。
- **把事故写成流水账**：时间线是证据，不是结论。没有直接原因、根本原因和改进项的记录，只是值班日记。
- **改进项没有 owner 和截止时间**："后续优化"等于不会优化；到期没有验收证据，就当作没做。
- **只改代码不改流程**：同一个坑换个模块再踩一遍；反过来只加流程不改代码，就是让人肉去补机器的漏洞。
- **"加强培训/提高意识"式改进**：培训不是改进项，能被机器校验的才叫改进项。
- **过度归因**：把所有历史问题塞进这次复盘，改进项铺太开，最后一个都做不完——所以骨架里要留一节"哪些不是这次的原因"。
- **定级靠感觉、复盘完不回头**：判据不写成阈值，每次出事都要吵严重程度；改进项状态不跟踪，下个季度又写一份几乎相同的复盘。

## 小结

1. 缺陷是"行为不符合预期"，事故是"有影响面和时长的事件"；只有事故必须复盘，别把每条 P3 都开成复盘会。
2. 定级看影响面（用户/数据/资损）和可绕过程度（有没有降级路径），判据要写成可观测的阈值。
3. 顺序是止血 → 定位 → 修复 → 复盘，止血决定不用等根因；回滚、开关、限流、降级、摘流量、改配置，每一种都有代价。
4. 定位靠证据链：时间线对齐到分钟、24 小时变更清单、四类证据（日志/指标/链路/数据库），再用二分法排除变更。
5. 根因要拆到"能直接改"的那一层，改进项要可验收并分四类（检测/防护/流程/测试）；复盘质量看改进项落地与重复故障率，不看文档长度。
