# 指标体系怎么建？原子指标、派生指标和口径一致性怎么落？

> 指标体系的难点从来不是写 SQL，而是让"支付金额"这四个字在交易、财务、BI 三张报表里算出同一个数。拆开就三件事：指标怎么分层、口径怎么定义成文、定义怎么被"一处写、多处引"。

## 同一个「支付金额」，两个部门差 8 个点

周会上，交易团队的大盘 GMV 是 1.28 亿，财务给的支付金额是 1.18 亿。两个人都不认为自己错了——他们的 SQL 确实都没错，问的是两个不同的问题：

| 差异来源   | 交易团队的算法           | 财务的算法               | 差异方向                 |
| ---------- | ------------------------ | ------------------------ | ------------------------ |
| 是否扣退款 | 支付成功即计入，退款不扣 | 扣掉当期退款             | 财务偏小                 |
| 时间字段   | 按下单时间 `create_time` | 按支付时间 `pay_time`    | 跨天订单错位             |
| 数据源     | 交易库订单主表           | 支付流水 + 对账文件      | 支付失败单只在流水里可见 |
| 内部单剔除 | 未剔除                   | 剔除测试账号、内部员工单 | 财务偏小                 |
| 时区       | 服务器本地时区           | 统一按 UTC+8 截断自然日  | 凌晨 0-8 点数据错位      |

这就是"口径"的全部含义：**同一个业务事实，在时间、范围、来源、边界处理上的一组约定**。约定不写下来，每个人只能用自己的默认值，而有默认值的地方必然分裂。

更贵的坑是口径被偷偷改掉：某天日报 GMV 同比涨 40%，排查半天发现是有人把过滤条件从 `order_status = 'paid'` 改成 `order_status != 'cancel'`，把待付款单也算了进来。**口径变更和业务波动长得一模一样。**

## 指标 = 度量 + 口径 + 维度

与其背定义，不如记住指标在 SQL 里的形状：

```sql
SELECT dim_date, dim_channel,             -- 维度：切分角度
       SUM(pay_amount) AS gmv             -- 度量：被聚合的数值
FROM   dwd_trade_order_detail
WHERE  dt BETWEEN '2026-11-01' AND '2026-11-07'
  AND  order_status IN ('paid', 'shipped', 'finished')  -- 口径：范围与边界
  AND  is_test = 0
GROUP BY dim_date, dim_channel;
```

`SUM` 是度量，`WHERE` 是口径，`GROUP BY` 是维度。**三者任一变化，严格说就是另一个指标**——所谓"指标口径"不是文档里的客套话，它就是这个 `WHERE` 子句。

## 指标分层：原子、派生、复合

维度建模方法论把指标分三层，分层的价值在于：**只有原子指标这一层是有界可枚举的，上面两层必须靠规则收敛。**

| 层级     | 构成                         | 例子                                               | 谁来定                 |
| -------- | ---------------------------- | -------------------------------------------------- | ---------------------- |
| 原子指标 | 业务过程 + 度量 + 聚合逻辑   | 支付金额 = `sum(pay_amount)`，业务过程是"支付成功" | 数仓，一次性定义       |
| 派生指标 | 原子指标 + 修饰词 + 时间周期 | 近 7 天**新客**支付**金额**                        | 业务提需，评审后加     |
| 复合指标 | 多个派生/原子指标做四则运算  | 客单价 = 支付金额 / 支付买家数                     | 数仓，必须锁死分子分母 |

为什么原子指标天然有界？它锚定在**业务过程**上：下单、支付、退款、加购、登录。业务过程有限，每个过程能提的度量也就金额、笔数、件数、买家数那么几个，四乘四最多十几个，穷举得完。

```sql
-- 派生指标：近 7 天新客支付金额 = 原子(支付金额) + 修饰词(新客) + 周期(近 7 天)
SELECT SUM(o.pay_amount) AS new_cust_gmv_7d
FROM   dwd_trade_order_detail o JOIN dim_customer c ON o.buyer_id = c.customer_id
WHERE  o.dt BETWEEN date_sub('2026-11-07', 6) AND '2026-11-07'
  AND  o.order_status IN ('paid', 'shipped', 'finished')
  AND  c.first_pay_date >= date_sub('2026-11-07', 6);   -- 新客：首付落在窗口内

-- 复合指标：客单价 = 支付金额 / 支付买家数，分子分母同源、同窗口、同一批用户
SELECT SUM(pay_amount) / COUNT(DISTINCT buyer_id) AS per_buyer_amt FROM dwd_trade_order_detail
WHERE  dt = '2026-11-07' AND order_status IN ('paid', 'shipped', 'finished');
```

## 派生指标不能随便加：组合爆炸

算一笔账：4 个业务过程 × 3 个度量（金额/笔数/人数）× 8 个修饰词（新客、老客、有效、APP、小程序、大促、退货、复购）× 6 个时间周期（当日、近 7 天、自然月、MTD、QTD、累计）= **576 个派生指标**。每个都建一张 ADS 表，物理表就建不完，更别说维护。所以派生指标必须有**受控词表**：

- 修饰词词表：枚举、每个词有明确判定逻辑（"新客"是首单还是首付？"有效订单"排不排除风控拦截？）、有 owner；
- 时间周期词表：只允许 当日 / 近 7 日 / 近 30 日 / 自然月 / MTD / 累计，其余走即席查询；
- 新增要走评审，问三个问题：这个定语能不能做成明细里的一个字段？能不能用现有修饰词组合出来？下游真的每周都要看吗？

反例：业务提"近 30 天访问过商详页且加购未支付的女装新客支付金额"。这不是指标，是把**筛选条件**写进了指标名。正确做法是把它做成明细宽表的标记字段（`is_visited_pdp`、`is_cart_unpaid`），让自助分析的人自己勾选——否则明天换成"男装""近 14 天"，词表立刻爆掉。

## 一份指标定义卡片

指标定义要能让人**只看文档就复现这个数**。模板固定这几项：

| 项                        | 要写清什么                                           |
| ------------------------- | ---------------------------------------------------- |
| 指标名 / 英文名 / 指标 ID | 全局唯一，英文名即字段名，ID 用于血缘追踪            |
| 业务含义                  | 一句话：谁、在什么场景、用它回答什么问题             |
| 计算逻辑                  | 原子指标 + 修饰词 + 时间周期，写公式而不是"看代码"   |
| 数据源表                  | 库.表 + 表的粒度（一行是一笔订单还是一笔支付流水）   |
| 过滤条件                  | 状态枚举白名单、剔除项（测试单、内部账号、风控拦截） |
| 时间口径                  | 用哪个时间字段截断、什么时区、跨天订单归属哪一天     |
| 维度                      | 允许下钻的维度清单，以及维度表版本（类目树 v3）      |
| 边界处理                  | NULL 怎么算、除零怎么处理、退款回冲落在哪一天        |
| 负责人 / 频率 / SLA       | 出问题找谁；T+1 还是小时级；几点前必须就绪           |

填好的支付 GMV 卡片长这样：

| 项         | 内容                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------- |
| 指标       | 支付 GMV / `gmv_pay` / `M_TRD_0001`                                                            |
| 含义       | 支付成功的订单金额，衡量成交规模，不含运费与优惠券补贴                                         |
| 逻辑与源   | `sum(pay_amount)`，取自 `dwd.dwd_trade_order_detail`（一行 = 一笔订单）                        |
| 过滤与时间 | `order_status in ('paid','shipped','finished')`、`is_test = 0`；`pay_time` 按 UTC+8 截断自然日 |
| 边界       | 退款不回冲本期，另设"净 GMV"；`pay_amount` 为空按 0                                            |
| 负责人     | 交易域数仓，T+1，每日 07:30 就绪                                                               |

## 维度与度量：别把「渠道」塞进度量里

一句话判断：**能求和的叫度量，只能拿来 `GROUP BY` 的叫维度**。金额、笔数可以加，日期、地域、类目、渠道加起来没有意义。有人把"渠道"做成三个布尔列塞进事实表当度量，结果做渠道对比得写三个 `SUM`——这就是维度没抽出来。更关键的是**一致性维度（conformed dimension）**：所有事实表共用同一套维度定义，日期只有一张 `dim_date`，地域只有一套行政区划编码，类目只有一棵树，渠道只有一套编码。否则"华东"在 A 表是 6 省、B 表是 7 省，两个指标放同一个看板就是对不上。

```sql
CREATE TABLE dim_date (
  date_key     INT     COMMENT '日期键 yyyymmdd',
  cal_date     DATE    COMMENT '自然日',
  is_weekend   TINYINT COMMENT '是否周末',
  is_holiday   TINYINT COMMENT '是否法定节假日',
  promo_phase  STRING  COMMENT '大促阶段：预热/开门红/返场/无'
);
```

把"促销阶段"这类业务日历放进日期维度，`大促期 GMV` 就只是按维度过滤的普通需求，而不是每次有人在 SQL 里手写日期区间——手写就是分歧的源头。

## 口径治理怎么落地

定义写得再好，没人引用就等于没有。落地四件事：

1. **一处定义**：指标字典/语义层里每个指标一个全局 ID，公式、过滤、时间口径只在这里维护。
2. **多处引用**：看板、报表、取数脚本、特征工程都从字典取定义，而不是各自复制一段 `SUM(pay_amount)`。通用地说，指标平台的核心能力就是"定义维护 + 统一查询入口 + 血缘查询"。
3. **变更评审**：改口径要提评审单，写清改什么、为什么、影响哪些下游；血缘在这里是刚需——从指标反查被哪些看板、模型、对外报表引用，一次列全。
4. **版本与公告**：指标带版本（`gmv_pay@v2`），变更发公告并指定生效日，历史是否重刷同时说清。这条链最容易断在这一步——字典做得再漂亮，变更只在群里说一声，第二天照样有人拿着旧数去汇报。

## 从指标到 ADS：看板为什么不该直连明细

让 BI 直连 DWD 明细，四个问题一起来：每次刷新扫几亿行；十个人同时看就是十个全表聚合；每个人自己写 SQL，口径分裂立刻复发；秒级响应根本做不到。ADS 层的做法是**预聚合到业务最常用的粒度**，粒度必须写死在表名和注释里：

```sql
INSERT OVERWRITE TABLE ads_trade_gmv_1d PARTITION (dt = '2026-11-07')
SELECT '2026-11-07'                    AS stat_date,
       channel_id, category_l1_id, province_id,
       SUM(pay_amount)                 AS gmv,
       COUNT(DISTINCT order_id)        AS pay_order_cnt,
       COUNT(DISTINCT buyer_id)        AS pay_buyer_cnt
FROM   dwd_trade_order_detail
WHERE  dt = '2026-11-07' AND is_test = 0
  AND  order_status IN ('paid', 'shipped', 'finished')
GROUP BY channel_id, category_l1_id, province_id;
```

这张表的粒度是 **天 × 渠道 × 一级类目 × 省份**。注意 `COUNT(DISTINCT)` 不能跨行相加——两个类目的支付买家数加起来会重复计同一个人，所以**复合指标（客单价、转化率、复购率）必须把同一粒度的分子分母同时落进宽表**，不能让 BI 拿聚合结果再算比值。维度组合爆炸怎么办？三个手段：只预聚合高频下钻路径（渠道 → 类目 → 省份），低频组合走即席查询；类目只保留 Top 100，其余合并为 `OTHER`；合并的前提是**保持可加性**——`OTHER` 行的各度量必须等于被合并行之和，这样总量对得上，只是明细不可见。

## 常见指标陷阱

**一、GMV 混着用。** 一个 GMV 至少拆成三个：下单 GMV、支付 GMV、净 GMV（扣退款）。混用最直接的后果是趋势图在退款高峰莫名其妙掉下去。

**二、UV 跨天不能相加。** 周 UV 不等于七个日 UV 之和，同一个人被算七次：

```sql
-- 错：SUM(uv) 把跨天回访的用户重复计数
SELECT SUM(uv) FROM ads_visit_1d WHERE dt BETWEEN '2026-11-01' AND '2026-11-07';

-- 对：按周期重算去重
SELECT COUNT(DISTINCT visitor_id) FROM dwd_visit_log WHERE dt BETWEEN '2026-11-01' AND '2026-11-07';

-- 量大时用近似去重：合并 HLL 草图，但要对外说明误差量级
SELECT hll_count(hll_union(hll_hash(visitor_id, 12))) AS uv_approx FROM dwd_visit_log
WHERE dt BETWEEN '2026-11-01' AND '2026-11-07';
```

HLL 是近似算法，常规精度配置下相对误差在 1% 上下且随精度参数变化，**用了近似就必须在指标卡片里写明"近似值 ±1%"**，否则和精确去重的数对不上又是一场扯皮。

**三、转化率的分子分母必须同源同口径。** 常见错法：分子取交易库"支付订单数"，分母取埋点"商详曝光 UV"，时间窗口还一个按支付时间、一个按曝光时间——算出来的既不是用户转化也不是订单转化，涨跌都无法解释。正确做法是分子分母都取自同一份用户日粒度明细，同一批人、同一个窗口。

**四、平均值不能对平均值再求平均。** 这是辛普森悖论最常见的工程化身：

| 渠道 | 新客 访问/支付 | 新客转化率 | 老客 访问/支付 | 老客转化率 | 整体转化率 |
| ---- | -------------- | ---------- | -------------- | ---------- | ---------- |
| A    | 900 / 90       | 10.0%      | 100 / 20       | 20.0%      | 11.0%      |
| B    | 100 / 7        | 7.0%       | 900 / 108      | 12.0%      | 11.5%      |

A 在新客、老客两个分组里都赢，整体却输——B 的流量结构偏向了转化率更高的老客。**只看总体会得出错误结论，只拆一层就下结论同样不可靠。** 客单价同理：渠道 A 客单价 200 元（1 单）、渠道 B 客单价 50 元（100 单），平均客单价不是 `(200+50)/2 = 125`，而是 `(200+5000)/101 ≈ 51.5` 元。所以永远汇总分子分母再相除：

```sql
-- 错：对已聚合的日客单价再求平均
SELECT AVG(avg_price) FROM ads_channel_price_1d WHERE dt BETWEEN '2026-11-01' AND '2026-11-07';
-- 对：分子分母各自汇总后相除
SELECT SUM(pay_amount) / SUM(pay_order_cnt) AS avg_price
FROM   ads_channel_price_1d WHERE dt BETWEEN '2026-11-01' AND '2026-11-07';
```

## 上游口径变了怎么办

标准五步，顺序不能换：

1. **冻结口径**：先把现口径标记为 v1 冻结，变更完成前任何人不得改动，避免两个人同时改。
2. **评估影响面**：顺着血缘往上找，哪些指标、看板、对账任务、模型特征依赖它，列清单和责任人。
3. **双跑校验**：新旧逻辑并行跑 3-7 天，比对总量差异和差异分布（全量偏移还是集中在某个渠道/类目），在预期范围内才继续。
4. **公告切换**：定切换日、发公告、看板标注口径版本，敏感报表双写一段时间。
5. **保留旧口径**：旧逻辑至少留一个版本周期可回切；历史数据要不要重刷必须提前定——**只改新数据不重刷历史，同一条时间序列会出现跳变点**，趋势图上看着像业务暴涨或暴跌，之后半年都有人来问"那天发生了什么"。

## 容易踩的坑

- 指标名里塞定语（"近 30 天加购未支付新客支付金额"），短期满足一个需求，长期让词表失控。
- 用 `COUNT(*)` 当订单量却不剔重——订单明细表一行可能是一笔子订单，主订单数要 `COUNT(DISTINCT order_id)`。
- 把退款当负向记录追加进同一张表，`SUM` 时金额正负抵消但笔数不抵消，金额和笔数口径打架。
- 宽表只落分子不落分母，下游自己补分母，等于把口径分裂推迟到最后一公里；指标字典建了没人查、口径活在某个人的 SQL 脚本里，则是治理失败的典型信号。

## 小结

1. 口径 = 时间字段 + 时间窗口 + 数据源 + 过滤边界（退款/测试单/内部账号）+ 去重逻辑 + 时区，任一不同就是两个数。
2. 指标三层：原子指标锚定业务过程所以有界；派生指标 = 原子 + 修饰词 + 时间周期，靠受控词表防组合爆炸；复合指标必须锁死同源同窗口的分子分母。
3. 指标定义卡片要让人只看文档就能复现数字：含义、逻辑、数据源、过滤、时间口径、维度、边界处理、负责人。
4. ADS 按"天 × 高频维度组合"预聚合，BI 不直连明细；低频组合走即席查询，Top N 之外合并 `OTHER` 且必须保持可加性。
5. 口径变更五步：冻结 → 影响面 → 双跑 → 公告切换 → 保留旧口径；历史是否重刷决定趋势图上会不会出现假拐点。
