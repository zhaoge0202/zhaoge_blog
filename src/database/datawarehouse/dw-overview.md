# 数据仓库为什么要分层？ODS、DWD、DWS、ADS 各管什么？

> 分层不是"把表多建几层显得正规"，而是把「数据从哪来、经过哪道加工、出了问题谁负责」这三件事钉死。分层答不好，后面建模、指标、质量全是糊的。

## 先看一个真实会发生的场景

假设一家电商公司有三个报表都在算 GMV：

| 报表     | 数据来源                  | 算法                                   | 结果    |
| -------- | ------------------------- | -------------------------------------- | ------- |
| 运营日报 | 订单明细表 `order_detail` | 下单时间在下单日的订单金额（含未支付） | 1200 万 |
| 财务对账 | 支付流水表 `pay_flow`     | 支付时间在当天的成功支付金额（扣退款） | 1050 万 |
| 老板看板 | 业务库直连 + 视图         | `order` 主表金额，按创建时间，含测试单 | 1240 万 |

三个数都对，但没人说得清哪个是"公司的 GMV"。开会两小时，最后结论是"以后统一口径"——而下周又出现同样的争论。

把这件事拆开，差异来自五处：**数据源不同、时间字段不同、过滤条件不同（是否含未支付/退款/测试单）、去重逻辑不同、清洗规则不同**。只要这五处没有统一收口的地方，口径就一定会漂。分层做的第一件事，就是给"统一收口"安排一个物理位置。

## 不分层会怎样

- **复用为零**：每张报表自己 join 一遍订单、用户、商品，同样的清洗逻辑抄十遍。上游逻辑一改，十个地方都得改，漏一个就产生"同一个指标两个数"。
- **口径漂移**：某个分析同学在报表 SQL 里顺手 `where status != 'cancel'`，另一个人没写。差异从这一刻埋下，半年后没人知道为什么两个看板差 3%。
- **变更冲击**：业务库加字段、改类型，所有直连业务库的报表同时挂。
- **无法回溯**：数字对不上时，中间没有可比的基准层，只能在几百行 SQL 里猜哪一步错了。
- **表只增不减**：没人知道哪张表还有人用，因为没有统一入口、也没有血缘，只能都留着，存储和计算成本一直涨。
- **无法按天重跑**：没有按业务日期分区的中间层，补一天历史数据等于重跑全量。

## 四层（其实还有一层维度）各自回答什么问题

先给一张速查表，再逐层解释。

| 层  | 存什么                             | 粒度                  | 写入方式               | 回答的问题                         |
| --- | ---------------------------------- | --------------------- | ---------------------- | ---------------------------------- |
| ODS | 贴源数据，几乎原样                 | 与源表一致            | 每日新增分区（append） | 上游给了什么？原始长什么样？       |
| DWD | 清洗后的业务过程明细               | 业务过程最细粒度      | 按天分区覆盖写         | 一次订单/支付/点击到底发生了什么？ |
| DWS | 按主题 + 常用维度轻度汇总          | 天 × 维度组合         | 按天分区覆盖写         | 这个主题在某维度下是多少？         |
| ADS | 面向具体应用的结果表               | 跟着报表/接口要的粒度 | 按天分区覆盖写         | 这个看板/接口要的数字是多少？      |
| DIM | 公共维度（日期、地域、类目、用户） | 维度主键              | 全量覆盖或拉链         | 这个维度属性当时是什么？           |

### ODS：尽量别动数据

ODS 的职责是"留证据"。它要做的事很少：统一字段类型、按业务日期分区、加 `etl_time` 之类的加载标记。**不要在这里做业务清洗**——把无效订单过滤掉、把金额单位从分换成元，一旦后面发现过滤错了，原始数据已经没了，回溯无从谈起。

有个常见的反面写法：ODS 层直接写 `insert overwrite ... select ... where is_deleted = 0`。这等于把"删除"这个事实永久抹掉，而下游某个对账场景恰恰需要看被删掉的记录。清洗放到 DWD，ODS 只负责"原样搬进来 + 可定位"。

### DWD：一行一个业务事件，粒度最细

DWD 是整层的价值中枢。它按**业务过程**组织表：下单是一个业务过程，支付是一个，退款是另一个，每次点击日志也是。一张 DWD 表通常对应"一个业务过程的最细粒度事实"，比如 `dwd_trade_order_detail` 一行是订单里的一个商品行，不是一张订单。

关键判断：**粒度定在"最细"是复用能力的上限**。如果 DWD 只存订单头（一单一行），那"商品卖得怎么样"这个问题就永远答不了，只能回头再去 ODS 重算一遍——等于 DWD 白建了。

DWD 要做的事：去重（同一订单被推送两次）、规范化（枚举值翻译、单位统一、时间字段统一）、维度关联（把商品类目、用户注册渠道这些**相对稳定的**维度属性拍平进来）、保留退化维度（订单号这类"是号码但经常用来过滤"的字段直接放事实表）。

### DWS：轻度汇总，别做成报表

DWS 按主题建（交易、流量、用户、供应链），粒度是"天 × 最常用的一组维度"，比如 `dws_trade_user_1d`（用户 × 天）、`dws_trade_category_1d`（类目 × 天）。它的服务对象是**一类分析**，不是一个报表。

这里最容易做错的是"维度组合爆炸"：用户、商品、渠道、地域、终端全排列组合，会得到几十张表，维护不动。实际做法是只沉淀 2~4 个高频组合，其余查询回 DWD 现算，或临时在 ADS 里拼。

一个简单的判断标准：**如果这张表只有一个报表在用，它就应该在 ADS，不该占着 DWS 的位置。**

### ADS：允许冗余，为查询和业务语义让路

ADS 面向具体应用：一块看板、一个导出任务、一个数据接口。它要做的是"一次查询就把数字拿出来"，所以允许宽表、允许字段冗余、允许字段名直接用业务叫法（`gmv`、`pay_cnt`、`refund_rate`），而不是 `sum_pay_amt_1d`。

但这不意味着 ADS 可以随便写复杂逻辑。**口径逻辑要在 DWD/DWS 收口，ADS 只做取数与轻量组合**。一旦有人在 ADS 里重新写了一遍"有效订单"的过滤条件，口径就又散开了，前面三层白做。

### DIM：一致性维度的存放地

维度表单独成层，是为了让"用户""商品""地域"这些维度在多个主题里是同一份。交易看"新客"、流量也看"新客"，如果两张表各自算一套新客定义，跨主题分析立刻失效。维度建模里把这叫一致性维度，后面[维度建模那篇](./dw-dimensional-modeling.html)会展开。

## 层间流转的规矩

分层的价值不在表的数量，而在**依赖方向**。四条规矩：

1. **单向依赖**：只允许 ODS → DWD → DWS → ADS 往上走。ADS 反查 ODS 拼数、报表直连业务库，都是绕过口径收口的捷径，代价是以后没人能解释数字。
2. **禁止跨层跳跃**：报表直接查 ODS 看上去快，实际是把清洗逻辑复制到每个下游。
3. **同指标单一定义**：一个指标只能在一处被定义，其余地方引用。定义散落是"三个 GMV"的技术根因。
4. **每层有 Owner 和产出时间**：出了问题知道找谁，下游知道几点能依赖。

```mermaid
flowchart LR
  A[业务库 / 日志 / 埋点] --> B[ODS 贴源]
  B --> C[DWD 明细<br/>业务过程最细粒度]
  C --> D[DWS 轻度汇总<br/>主题 × 常用维度]
  D --> E[ADS 应用结果表]
  C --> E
  F[DIM 公共维度] -.-> C
  F -.-> D
  E --> G[看板 / 报表 / 数据接口]
```

注意 DWD 到 ADS 的那条直连：面向单一口径的简单指标（比如"昨日支付金额"），直接从 DWD 聚一次写 ADS 是合理的，不必强行多绕一层 DWS。但如果这个指标会被反复引用、维度组合多，就该在 DWS 沉淀。

## 一个电商例子走完全程

假设要回答"昨天各品类支付金额是多少"。

```sql
-- ODS：原样落地，只统一类型和分区
-- ods_order_detail(dt, order_id, sku_id, item_amt, create_time, update_time, ...)
-- ods_pay_flow(dt, order_id, pay_amt, pay_time, pay_status, ...)

-- DWD：一行一个订单商品行，去重 + 关联支付
insert overwrite table dwd_trade_order_detail partition (dt = '${bizdate}')
select
  od.order_id,
  od.sku_id,
  od.item_amt,
  pf.pay_amt,
  pf.pay_time
from (
  select *,
         row_number() over (partition by order_id, sku_id order by update_time desc) as rn
  from ods_order_detail
  where dt = '${bizdate}'
) od
left join (
  select order_id, sum(pay_amt) as pay_amt, max(pay_time) as pay_time
  from ods_pay_flow
  where dt = '${bizdate}' and pay_status = 'SUCCESS'
  group by order_id
) pf on od.order_id = pf.order_id
where od.rn = 1
  and od.order_id is not null;

-- DWS：类目 × 天
insert overwrite table dws_trade_category_1d partition (dt = '${bizdate}')
select
  p.category_id,
  sum(d.pay_amt)             as pay_amt,
  count(distinct d.order_id) as pay_order_cnt
from dwd_trade_order_detail d
join dim_product p on d.sku_id = p.sku_id
where d.dt = '${bizdate}' and d.pay_amt is not null
group by p.category_id;

-- ADS：看板就查这一张
select category_id, pay_amt, pay_order_cnt
from dws_trade_category_1d
where dt = '${bizdate}';
```

注意这条链上两个容易被忽略的细节：DWD 用 `row_number()` 去重，是因为上游可能重复推送；DWS 的 `count(distinct order_id)` 和 `sum(pay_amt)` 必须是同一批过滤条件，否则"客单价 = 金额 / 订单数"会算出荒谬值。

## 湖仓和实时链路之后，分层变了吗

没变。变的只是每层的**存储与实现方式**：

- ODS 从"每天一份全量文件"变成湖表（Iceberg/Hudi/Paimon），支持 upsert 和增量读，能承接 CDC 数据；
- 实时链路也照同一套分层走（Flink 里同样分 ODS 主题、DWD 明细、DWS 指标），好处是离线实时可以共用一套口径定义；
- 但**代价是双链路要对账**。同一份 DWD 逻辑用 Flink SQL 和 Spark SQL 各写一遍，浮点、null 处理、去重策略稍有不一致，两边的数就对不上。这部分的细节见[实时链路那篇](./dw-realtime-pipeline.html)。

## 容易踩的坑

- **ODS 做业务清洗**：原始证据被抹掉，出问题没法回溯。
- **DWD 存汇总、DWS 存明细**：层级失去意义，最后所有查询都回到 DWD，DWS 变成摆设。
- **ADS 里重写口径**：一个人的一行 `where` 就能让口径重新散开。
- **不按业务日期分区**：补一天数据变成全量重跑，这是"补数慢"最常见的根因。
- **把维度表混在 DWD**：维度是"属性会变"的慢变数据，和事实的写入节奏、更新方式完全不同，混在一起两头都别扭。
- **分层当成目的**：为了"规范"把一个简单指标拆成四张表，链路长了、故障点多了，收益却是零。分层是权衡，不是教条。

## 小结

- 分层的目的是把**数据来源、加工步骤、责任归属**固定下来，解决口径漂移、复用为零、变更冲击、无法回溯四类问题。
- ODS 留原始证据、DWD 存最细粒度的业务过程明细、DWS 做主题级轻度汇总、ADS 面向具体应用，DIM 承载一致性维度。
- DWD 的粒度定得越细，后续分析的复用上限越高；粒度定错，上面几层全部锁死。
- 允许的依赖只有一条：ODS → DWD → DWS → ADS，跨层跳跃和反向依赖都是口径失控的开始。
- 湖仓和实时链路改的是存储与实现，**分层本身和"一处定义口径"的原则不变**。
