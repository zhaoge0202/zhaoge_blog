# HDFS、YARN、Hive、HBase 到底各管什么？现在还有必要学吗？

> 这四个东西不是四个"数据库"，而是一条链上的四段职责：**数据放哪、作业去哪跑、表长什么样、随机读写靠谁**。面试问它们，本质是在确认你知不知道"我写的那行 SQL 到底被翻译成了什么"。

[分层那篇](/database/datawarehouse/dw-overview.html)讲的是"表怎么摆"，这篇补的是"表底下压着什么"。分工要先分清：分层是方法论，组件是实现，混着讲就会变成背名词。

## 先回答后半句：不必会运维，但三件事绕不过去

"现在云上一键就起集群了，Hadoop 还用学吗"——这话对一半。**不用学的是运维**：NameNode 怎么做 HA 切换、YARN 队列权重怎么配、HBase region 怎么 split、`hdfs fsck` 怎么修块，这些是平台团队的事，你能看懂监控面板、会提单就够。

但下面三件事躲不开，因为它们**直接写在你每天提交的 SQL 里**，决定这条查询跑 5 分钟还是 5 小时：

| 真正要懂的       | 为什么和你的 SQL 有关                                                              | 到什么程度算够                                       |
| ---------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 存储格式与压缩   | 列存只读用到的列，行存要读整行；压缩决定 I/O 总量、文件能不能被切开并行读          | 建表会选 ORC/Parquet，知道 snappy 与 zstd 的取舍     |
| 分区、分桶与谓词 | 分区裁剪决定扫 1 天还是扫 3 年；分桶决定 join 要不要 shuffle                       | `where` 里写裸分区列，知道分桶要 join 两侧同列同桶数 |
| 执行引擎差异     | Hive 起作业是分钟级、Trino 是秒级、Spark 的内存与落盘行为不同，同一句 SQL 代价不同 | 知道三者的延迟量级、语法差异和"什么活不该交给谁"     |

再补一件"看起来是运维、其实是契约"的事：**元数据**。表定义存在 Hive Metastore 里，Spark、Trino、Flink 全都读同一份。你把一个字段类型改了、把一个分区目录手工删了，影响的不止 Hive——这条比上面三条更容易在跨团队协作时炸。

## 四个组件各管一段

先给速查表，再逐个说边界。第三列是重点：**大部分面试答飘，都飘在这一列**。

| 组件  | 职责                               | 关键概念                                                         | 你以为它管，其实不管                               |
| ----- | ---------------------------------- | ---------------------------------------------------------------- | -------------------------------------------------- |
| HDFS  | 把文件切块、多副本落到机器上       | NameNode（元数据）、DataNode（块）、128MB 块、3 副本             | 不管计算、不管表结构、不支持随机修改               |
| YARN  | 把集群的 CPU/内存分给各个作业      | ResourceManager、NodeManager、ApplicationMaster、Container、队列 | 不管数据、不管 SQL，只认"这个作业要多少 container" |
| Hive  | 把 SQL 翻译成分布式作业 + 管表定义 | Metastore、分区/分桶、内部表/外部表、可换执行引擎                | 不存数据（数据在 HDFS）、不做调度、不是 OLTP       |
| HBase | 按 RowKey 做毫秒级随机读写         | RowKey、列族、Region、MemStore/HFile、WAL                        | 不做分析聚合、无 SQL/join、二级索引基本没有        |

### HDFS：块、副本、一次写多次读

HDFS 干的事很朴素：文件切成固定大小的块，每块存多份，元数据单独放。三个数字要记住，但更要记住**数字背后的权衡**。

- **块 128MB**（Hadoop 2.x 起，之前是 64MB）：它同时是"一个 map task 默认读多少数据"。块太小 → task 数暴涨，调度和启动开销压过计算；块太大 → 并行度不够，最后几个 task 拖着整个作业收尾。128MB 是这两头的折中，不是物理限制。
- **3 副本**（`dfs.replication` 默认 3）：存储成本是 3 倍。HDFS 3.x 的纠删码（RS-6-3）能把冷数据压到约 1.5 倍，代价是读取要解码、不支持那套 append 语义。所以"副本数"从来不是固定答案，而是"热数据要本地性、冷数据要便宜"的取舍。
- **一次写入、多次读取**：文件 `create` 之后只能追加，不能 seek 到中间改。这条直接解释了数仓的一个习惯——**改数据只能整分区重写**，`INSERT OVERWRITE` 不是洁癖，是物理限制逼出来的写法。

小文件常被一句话带过："每个文件在 NameNode 占内存，百万小文件压垮元数据服务。" 这句话方向对，量级不对，值得掰开：NameNode 里每个文件、目录、块大约占 150 字节，**一百万个小文件 ≈ 300MB 元数据**，这个量本身不致命。真正痛的是三处：

1. 每次 `open` 都是一次 NameNode RPC，海量小文件把 RPC 队列打满，表现为"集群没在算东西，但提交作业一直卡"；
2. 元数据对象上亿时堆很大，一次 Full GC 就是分钟级停顿，所有作业一起等；
3. 计算侧一个文件一个 task，几十万次 task 启动，这条在[倾斜与小文件那篇](/database/datawarehouse/dw-skew-and-tuning.html)里有量化。

所以结论不是"别存小文件"，而是"**别在生产表里留小文件**"——落地时的碎文件可以接受，进 DWD 之前必须合并。

### YARN：负责分配资源，不碰数据

YARN 是"集群的操作系统"，四个角色各管一段：

| 角色              | 干什么                                                     |
| ----------------- | ---------------------------------------------------------- |
| ResourceManager   | 全局资源账本，按队列分配；作业卡在 `ACCEPTED` 通常就是它   |
| NodeManager       | 单机代理，管本机 container 的启停与资源上报                |
| ApplicationMaster | 每个作业一个，负责向 RM 要 container、监控 task、失败重试  |
| Container         | 内存 + vcore 的运行时封装，一个 task 跑在一个 container 里 |

队列是面试常问的点：Capacity Scheduler 支持层级队列、权重、单队列上限、单用户上限。**提交时选错队列**是很真实的事故——同一个 SQL 在 `default` 队列排两小时，在 `etl` 队列十分钟跑完，SQL 一个字没改。

YARN 今天的位置要说清，否则容易答成"过时了"：**在自建集群里它仍是主流**，Spark on YARN 仍是很多公司的默认提交方式，Hive on Tez 也跑在 YARN 上；新集群和云上则越来越多直接把 Spark、Flink 提交到 K8s（Namespace + ResourceQuota 做隔离，HPA/弹性节点池做伸缩）。判断标准很简单：算力和数据同机房、要复用现成 HDFS 集群 → YARN 更省事；要按需弹性、要和其他在线服务混部 → K8s 更顺。两套的资源模型都对不齐"申请量"和"实际用量"，所以都会出现"队列排满但机器空闲"。

### Hive：翻译层 + 元数据服务

Hive 最容易被误解成"一个数据库"。它实际由三块拼起来，各在一块地盘上：

- **翻译层**：SQL → 逻辑计划 → 物理计划 → 提交到 YARN/Tez/Spark 执行。它自己不算数据。
- **Metastore**：存库、表、分区、列、存储路径、SerDe 信息，底层是 MySQL/PostgreSQL。**这是整个生态的地基**：Spark、Trino、Flink 读的都是它，所以 HMS 挂了，所有引擎一起报"表不存在"。
- **HiveServer2**：对外提供 JDBC/ODBC，Java 后端接数仓一般走它或走 Trino 的 JDBC，具体接法见[Java 业务系统怎么对接数仓](/database/datawarehouse/dw-bigdata-java-integration.html)。

内部表和外部表的差别只有一句要背，但边界要说全：

| 操作               | 内部表（MANAGED）   | 外部表（EXTERNAL）       |
| ------------------ | ------------------- | ------------------------ |
| `DROP TABLE`       | 删元数据 + 删数据   | 只删元数据，数据留在原地 |
| 谁负责数据生命周期 | Hive                | 你或上游系统             |
| 典型用途           | 中间表、DWD/DWS/ADS | ODS 贴源、多引擎共享的表 |

两个常见误解：外部表**不是只读**，照样能 `INSERT`；"外部表删表不删数据"也救不了误操作——`ALTER TABLE ... DROP PARTITION` 会连目录一起删，删错分区和数据说再见是一样的。

分区和分桶是两种完全不同的切分：**分区是目录**（`dt=2024-06-01/`），分区字段是虚拟列，不写进数据文件；**分桶是按 `hash(列) % 桶数` 切成固定数量的文件**，目的是让 join 两侧桶对桶、免掉 shuffle。分桶数建表时定死，后期改起来很痛，所以不要拿它当"分区用"。

执行引擎可换是 Hive 的架构红利：`hive.execution.engine` 取 `mr` / `tez` / `spark`，老集群默认 MR，Hive 2 之后的发行版多数默认 Tez。换引擎不用改 SQL，但会改两件事——延迟量级，以及一些方言细节（比如某些窗口帧、`DISTRIBUTE BY` 的行为）。另外 Hive 3 起管理表默认是 ACID 事务表（只支持 ORC、后台跑 compaction），别因此把它当 OLTP：行级 `UPDATE` 语法上有，但一次更新就是一次作业，延迟仍是分钟级。

### HBase：一个由 RowKey 决定命运的数据库

HBase 是 LSM 结构：写先落 WAL + MemStore，MemStore 满了 flush 成 HFile，读要跨 MemStore 和多个 HFile 合并。它只有**一个索引**，就是 RowKey，RowKey 按字典序全局有序，所以：

- **点查和前缀 scan 很快**：`scan` 带 `startRow`/`stopRow` 前缀，能定位到少数 Region。
- **组合条件查询很慢**：没有二级索引，`where city = 'x' and age > 30` 这种条件只能全表扫，或者你自己按查询维度冗余出多份 RowKey 表。Phoenix 的二级索引、Coprocessor 都是补丁，不是免费午餐。
- **RowKey 设计就是 schema 设计**：单调递增的 RowKey（时间戳、自增 id 打头）会把写入全压到最后一个 Region，形成写热点，解法是加盐前缀（`hash(key) % N`）或反转；RowKey 越短越好，因为每一行都要存一份。

它擅长的场景很具体：**稀疏宽表 + 随机读写**。用户画像这种"每人几百个标签、绝大多数为空"的数据，列族里没值的列不占存储，天然合适；计数、去重标记、会话状态这类按 key 读写也合适。不擅长的同样具体：多表 join、聚合分析、事务性更新。把它当"大号 MySQL"用，第一次做多条件查询就会撞墙。

## 存储格式才是性能的分水岭

组件决定"作业能不能跑起来"，格式决定"跑多久"。这是整篇里最该带走的一节，也是面试里最容易拉开差距的地方。SQL 写法层面的取舍（窗口函数、去重取最新、补齐日期）不在这里展开，见[数仓 SQL 怎么写才不踩坑](/database/datawarehouse/dw-sql-patterns.html)。

| 维度     | 行存（TextFile / Avro）      | 列存（ORC / Parquet）                       |
| -------- | ---------------------------- | ------------------------------------------- |
| 物理布局 | 一行连续存放                 | 按列分块存放，块内再按行组织                |
| 读 3 列  | 读整行再丢列，I/O 不减少     | 只读这 3 列，I/O 按列比例下降               |
| 压缩率   | 一行里类型混杂，压缩比一般   | 同列同类型，字典/RLE/差分编码，压缩比高     |
| 统计信息 | 基本没有                     | stripe / row group 级 min-max、bloom filter |
| 适合     | 贴源落地、全列导出、行级交换 | 明细层、汇总层、一切会被反复查询的表        |

看一个具体对比。假设 `dwd_order` 有 200 列、单天未压缩 800GB：

```sql
select city, sum(pay_amt) from dwd_order
where dt = '2024-06-01' group by city;
```

- **TextFile + gzip，没有分区**：扫三年 ≈ 365 × 800GB ≈ 285TB，按集群有效带宽 2GB/s 算，光 I/O 就是 40 小时量级；而且 gzip 的整文件不可切分，一个文件只能一个 task 读，并行度还被压住。
- **ORC + 命中分区 + 只读 3 列**：3/200 × 800GB ≈ 12GB，snappy 再压 3 倍 ≈ 4GB，几十秒到两分钟。

差距不在"引擎快不快"，全在**扫描量**。列存之所以快，是四件事叠起来的：

1. **列裁剪**：只反序列化用到的列。这也是为什么 `select *` 在列存上一样慢——它把列裁剪直接废掉了。
2. **高压缩比**：同一列类型一致、重复度高，字典编码 + RLE 效果远好于行存；压缩省的不只是磁盘，还有网络和反序列化 CPU。
3. **块级统计 + 谓词下推**：ORC 的 stripe、Parquet 的 row group 都带 min/max，条件不命中就整块跳过；bloom filter 还能跳过"肯定不存在"的等值查询。
4. **向量化读取与延迟物化**：先按行号过滤，最后才去取其他列的值。

这些优化都有前提，**谓词写在裸列上**：

| 写法                                     | 后果                                           |
| ---------------------------------------- | ---------------------------------------------- |
| `where dt = '2024-06-01'`                | 分区裁剪命中最优                               |
| `where substr(dt, 1, 7) = '2024-06'`     | 分区列被函数包住，退化成扫全部分区             |
| `where cast(dt as date) >= '2024-06-01'` | 同上；改写成 `dt between '2024-06-01' and ...` |
| `where my_udf(col) = 1`                  | 统计信息用不上，下推失效                       |
| `where dt = 20240601`（分区是 string）   | 隐式转换，不同引擎行为不一致，可能全扫         |

分区和分桶的定位也要分清：

| 手段 | 作用                       | 生效前提                                    | 典型失效                       |
| ---- | -------------------------- | ------------------------------------------- | ------------------------------ |
| 分区 | 只读命中的目录             | `where` 有裸分区列，且粒度与查询粒度一致    | 函数包列；按小时切导致分区爆炸 |
| 分桶 | 同桶 join 免 shuffle、采样 | join 两侧同列同桶数，且开启 bucket map join | 桶数不一致；写入未按桶分发     |

分区不是越细越好：Metastore 里每个分区一行元数据，分区上百万时 `show partitions`、`msck repair table` 都能拖到分钟级，NameNode 那边也是一堆目录。按天够用就别按小时。

压缩算法按"热冷"和"能不能切"来选：

| 算法   | 压缩比 | 速度 | 文件级可切分 | 典型用途                             |
| ------ | ------ | ---- | ------------ | ------------------------------------ |
| Snappy | 中     | 快   | 否           | 热数据、中间结果，默认首选           |
| ZSTD   | 高     | 中   | 否           | 冷数据、存储敏感场景                 |
| Gzip   | 高     | 慢   | 否           | 归档；配 TextFile 是灾难组合         |
| Bzip2  | 高     | 很慢 | 是           | 可切分但太慢，基本只剩"必须切"的场合 |

关键细节：**文件级可切分性由外层容器决定**。ORC/Parquet 内部本来就按 stripe / row group 切分并行读，所以"列存 + zstd"照样能并行；而"TextFile + gzip"必须整个文件读完才能解压，等于把并行度锁死。同理，压缩要和"文件至少有一个分片大"一起考虑，否则再好的编码也救不了碎文件。

## 一条离线作业的真实路径

```mermaid
flowchart LR
  S["业务库 / 日志 / 埋点"] --> L["落地：HDFS 或对象存储<br/>/warehouse/ods/db/table/dt=..."]
  L --> M["Hive 外部表映射<br/>Metastore 记路径与列"]
  M --> P["分区表写入<br/>INSERT OVERWRITE dt=D"]
  P --> O["调度：Airflow / DolphinScheduler<br/>按 DAG 依赖触发"]
  O --> E["查询引擎：Hive / Spark / Trino"]
  E --> A["ADS 结果表"]
  A --> B["报表 / 数据接口 / 导出"]
```

这条链上每段的责任人要分清，出问题才知道找谁：

| 环节         | 谁负责          | 出问题的典型表现                       |
| ------------ | --------------- | -------------------------------------- |
| 落地与存储   | 平台/存储团队   | 写不进去、块损坏、目录权限             |
| 外部表映射   | 数仓开发        | 字段错位、分隔符不对、分区没登记       |
| 分区写入     | 数仓开发        | 数据翻倍、分区写错日期、小文件堆积     |
| 调度编排     | 数仓开发        | 依赖没配、上游没就绪就跑了、补数乱序   |
| 查询引擎     | 平台 + 开发     | 队列排满、shuffle 失败、OOM            |
| 结果表与消费 | 数仓开发 + 业务 | 空分区被下游当成"零"、口径与报表不一致 |

注意图中没有"Hive 调度"这一环：**Hive 只负责"这一次执行"，编排是调度器的事**。把这两件事混在一起答，会被追问到答不上来。链路的幂等、补数与 SLA 细节在[离线管道那篇](/database/datawarehouse/dw-offline-pipeline.html)。

## 查询引擎怎么分工

同一份 HDFS 上的 ORC 数据，五个引擎都能读，但代价完全不同：

| 引擎              | 定位         | 强项                                     | 弱项                                          |
| ----------------- | ------------ | ---------------------------------------- | --------------------------------------------- |
| Hive on MR/Tez    | 批处理老将   | 超大规模、容错成熟、成本低、跑几小时不怕 | 慢，起作业分钟级，交互式基本没法用            |
| Spark SQL         | 通用计算引擎 | 复杂多轮 ETL、迭代计算、UDF、流批一体    | 内存与 shuffle 调优有门槛，稳定性靠参数       |
| Trino / Presto    | MPP 交互查询 | 秒级到分钟级 ad-hoc、跨源联邦查询        | 超大 ETL 不稳（失败即整查询重来），写入生态弱 |
| ClickHouse        | 列式 OLAP    | 单表大宽表聚合极快、日志与行为分析       | 大表 join 弱，点更新弱，运维要懂合并          |
| Doris / StarRocks | MPP OLAP     | 报表、宽表、主键 upsert、物化视图        | 极高并发点查不如 KV，导入要设计               |

三条选型判断：

- **能等、怕失败重跑** → Hive / Spark。它们有落盘 shuffle 和 task 级重试，跑六小时的作业挂一个 task 只补那一个。
- **人坐在那儿等结果、要反复改 SQL** → Trino。它把整条查询当一个整体，快是真快，但一个节点 OOM 就整条重来。
- **固定看板、高并发、要多条件过滤** → Doris / ClickHouse，或者干脆把结果同步进 MySQL/ES 给业务查。

顺带说清一件事：**同一份数据、不同引擎，结果可能不同**。浮点求和顺序、`count(distinct)` 的近似实现、null 与空串的处理、时区与日期函数，都有差异。所以"离线用 Hive 算、实时用 Flink 算、对账对不上"往往不是 bug，是引擎语义差异，得靠统一口径 + 定期对账兜住。

## 演进：三件套没死，只是不再是唯一答案

- **存算一体时代**：HDFS + MapReduce + YARN 三件套，数据在哪算力就在哪，扩容要一起扩。
- **存算分离**：数据放对象存储（S3/OSS/COS），计算集群按需起停。存储便宜、算力弹性，代价是 list/get 延迟高、元数据操作按次计费，小文件问题反而更疼。
- **湖仓表格式**：Iceberg / Hudi / Paimon 在对象存储上补出事务、快照、schema 演进和增量读，把"数据湖"拉到能当数仓用。这部分单独见[湖仓一体那篇](/database/datawarehouse/dw-lakehouse.html)。

现实是三者并存的：大量公司还在跑 Hadoop 2.x/3.x 老集群，Hive 表几万张，日报照常出；新业务往湖仓上搬，迁移周期以年计。所以 JD 里写 Hive/Spark 不是历史遗迹，**要学的是那套心智：分区怎么切、列存怎么压、元数据放哪、作业在哪排队**——这套心智换个引擎照样用，而 `hdfs dfs -put` 的具体参数忘了随时能查。

## 容易踩的坑

- **小文件只在事后清理**：`rm` 完下周照样堆。要在写入端控（控制 reducer 数、开 merge、动态分区限流），治理细节见[倾斜与小文件那篇](/database/datawarehouse/dw-skew-and-tuning.html)。
- **全表扫描而不自知**：分区列被函数包住、类型不匹配、动态分区字段顺序写反，都会静默退化成扫全表。上线前先看执行计划里的扫描分区数。
- **用 HBase 做多条件查询**：没有二级索引，两个条件的组合查询就得全表扫或冗余多份 RowKey 表。查询模式没定下来之前，别急着选 HBase。
- **把 Hive 当 OLTP 用**：没有行级索引、没有真正的点更新，每次查询起一个作业，延迟分钟级。要做接口查询就落 MySQL/ES/Redis。
- **副本数当成固定值**：3 副本就是 3 倍存储。热数据保 3 副本换本地性，冷数据用纠删码或降副本换成本，账要算清。
- **以为列存能救 `select *`**：列裁剪失效，200 列全读；宽表加字段后 `select *` 还会让上下游列顺序错位。
- **手工改 HDFS 上的表目录**：绕过了 Metastore，分区没登记，Hive 看不见、Spark 可能看得见，两边对数开始打架。

## 面试怎么答这条线

不要一个组件一个组件背定义，按**一条数据流**讲，天然有层次：

1. **存储**：数据落在 HDFS 或对象存储，切块、多副本、一次写多次读，所以改数据靠分区重写。
2. **资源**：作业提交到 YARN（或 K8s），RM 按队列给 container，AM 负责这次作业的申请与重试。
3. **表与元数据**：Hive 提供 SQL 翻译和 Metastore，表定义一处存放，Spark/Trino 共用同一份。
4. **格式**：真正的性能分水岭是列存 + 压缩 + 谓词下推，`select *` 和函数包分区列会把优化全废掉。
5. **引擎**：批处理看 Hive/Spark，交互看 Trino，固定报表看 Doris/ClickHouse，按"能不能等、要不要重跑"来选。

收尾补一句自己的判断，比复述定义有分量：**这类问题最后都会落到"扫描量"上**——分区裁剪决定读几个目录，列存决定读几列，压缩决定读多少字节，三者相乘就是这条 SQL 的成本；引擎只是把这个成本兑现得快一点或慢一点。

## 小结

- HDFS 管存储（块 + 多副本 + 一次写多次读）、YARN 管资源（RM/NM/AM/Container）、Hive 管 SQL 翻译与元数据、HBase 管按 RowKey 的随机读写，四者职责不重叠。
- 不必会运维，但必须懂三件事：存储格式与压缩、分区/分桶与谓词、执行引擎差异——它们直接决定扫描量和作业延迟。
- 性能分水岭在格式：列存只读需要的列、压缩率高、有块级统计能下推；前提是谓词写在裸列上，`select *` 和函数包分区列会让优化全部失效。
- Hive 不是数据库而是翻译层 + Metastore，数据在 HDFS、执行在 YARN；内部表删表删数据，外部表删表留数据，但删分区两边都删。
- 三件套 → 存算分离 → 湖仓是演进不是替换，老集群长期共存；换的是存储与引擎，不变的是分区、列存、元数据这套心智。
