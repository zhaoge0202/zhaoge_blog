# Java 工单 Agent 怎样分阶段接入，并定义每一步的验收？

> 每次只接入一项新能力，用真实业务状态定义验收条件，再逐步加入模型、证据、确认和恢复。

## 为什么模块都设计好了，还是不知道先接哪一块？

假设 alice 属于 north 租户，要查询本人名下的工单 T-1048。工单正在等待供应商反馈；如果符合当前政策，她还希望申请升级。

一次把检索、模型、工具、审批和异步恢复全部接上，出错时就难以分清：身份错了，还是证据过期、工具重复执行、状态没有提交？

更容易定位问题的顺序，是先让一条可信的只读请求走到底，再增加一个变量。

本文给出教学实施方案与验收条件，不提供可启动工程，也没有运行 Java 服务、数据库或模型。职责划分见[模块与接口设计](./ai-agent-java-project.html)，这里集中说明接入顺序。

## 第一步：先写清成功条件，哪些事实不能让模型决定？

先把需求从“回答得像客服”改成可以核查的业务约束：

- 查询只能读取当前主体有权访问的工单。
- 状态解释必须对应业务查询结果，政策解释必须有可见且有效的证据。
- 升级先生成草稿，取得可信确认后才能提交。
- 同一业务操作重复提交，不能产生多条升级记录。
- 外部结果未知时先核查，不能直接宣布失败并重新创建操作。

例如，返回“已经升级”还不够。验收应检查升级记录确实存在、归属正确，并能通过操作号查到最终结果。

同时保存版本组合：应用提交、JDK、Spring Boot、AI 框架、模型接口、工具 Schema、提示词和政策版本。实现时选定兼容组合，不能将不同版本教程中的代码拼在一起便认为可用。

第一阶段的产物是任务约束、接口契约和版本清单。缺少其中一项，就先补齐，不急着接真实模型。

## 第二步：没有真实模型时，能否先完成只读链路？

先实现这条最短路径：

```text
认证请求 → 可信主体 → 工单查询 → 结构化查询结果 → 对外响应
```

浏览器提交工单编号；租户、用户和数据范围来自认证上下文，不能由请求体或模型参数指定。

可以让模型替身固定提出 `query_ticket` 调用，再返回解释。它只替换模型边界，工单查询、授权和运行状态仍经过实际应用逻辑。

替身不应直接返回“最终成功”以及预先填写的数据库计数，否则测试只是在确认预设答案。

这一阶段保存 `runId`、主体引用、目标工单、查询时间和状态来源。敏感正文按需要留存，不默认全部写入日志。

应验证的失败分支至少包括：工单不存在、用户无权访问、同号工单属于其他租户、下游查询失败。对外如何隐藏对象存在性，遵循统一的业务安全策略。

验收条件是：正常请求得到正确状态，越界请求没有取得正文；失败也能留下可区分的内部原因，而不是全部包装成“模型暂时不可用”。

## 第三步：怎样把模型接进来，又避免工具执行两次？

接入模型后，仍沿用已经确定的查询能力。变化的是“由谁提出调用”，不是查询服务获得了更大的权限。

模型适配器需要保留完整工具名、参数、调用标识和结束状态。执行器只接受注册过的工具，并检查类型、必填项、对象范围和当前授权。

下面只表达调用顺序，不对应某个 SDK 的实际接口：

```text
取得完整模型结果
  → 判断是否正常完成、截断、拒答或出错
  → 对完整工具调用进行参数与权限校验
  → 在预算内执行允许的工具
  → 按原调用标识回填结果
  → 进入下一轮，或按规则结束
```

流式参数只收到半截时不能执行；未知工具不能通过“名称相近”自动匹配。

还要选定执行责任：框架自动执行工具并回填时，应用在回调入口落实约束；应用自行管理循环时，应关闭或避开相应自动路径。不能两条路径各执行一次。

这一阶段保存模型尝试标识、工具调用标识、结果类型和预算消耗。验收应覆盖非法参数、未知工具、截断、重复调用和达到轮次上限，确认每种情况都有明确出口。

## 第四步：知识证据怎样接入已能工作的查询流程？

现在查询已经能返回 `WAITING_VENDOR`，再增加政策检索，用它解释等待原因和升级条件。

检索输入应包含可信的授权范围。结果至少携带文档标识、版本、片段位置和必要正文，进入模型上下文前再次确认其当前可见性。

假设政策第 12 版允许等待三天后升级，第 13 版新增了“必须附供应商反馈”的条件。只检索到“三天”便作结论，会遗漏决定性限制。

因此，接入证据后应分别检查：

1. 当前主体可见的正确版本是否进入候选。
2. 必要条件是否进入实际模型上下文。
3. 回答是否保留条件，引用是否支持结论。
4. 缺少反馈材料时，是否正确追问，而不是直接生成批准结论。

这一阶段保存证据引用及版本，不把一段历史回答永久当作当前政策。撤权、改版或会话续接时，都需要重新检查证据是否可用。

证据不足不是系统异常，可以作为正常结果返回。具体组织方式见[知识证据与工具调用](./ai-agent-java-knowledge-tools.html)。

## 第五步：从“建议升级”到“提交升级”，中间怎样接起来？

先生成升级草稿，再进入等待确认状态。草稿应该让用户看清操作对象、理由和关键参数，不能只有一个含糊的“是否继续”。

确认记录需要绑定主体、租户、工单、`operationId`、参数摘要、相关对象版本和有效期。用户修改参数后，应形成新的待确认意图，不能沿用原来的授权。

等待确认时持久化必要状态并释放执行资源，不为等用户点击而长期持有数据库事务。

确认请求到达后，重新检查当前权限、草稿绑定关系和业务前提。若对象版本或政策已经改变，先重新评估，必要时再次展示草稿。

对于升级记录与审批记录都由同一数据库管理的设计，可以将以下工作放入短事务：

```text
检查审批及业务前提
  → 按稳定 operationId 创建或取得已有升级记录
  → 更新执行记录
  → 提交事务
```

唯一约束应覆盖操作号的正确作用域，重复操作还需核对关键参数，不能用同一个号提交不同内容。

如果升级由外部系统执行，本地事务不能包办两边的原子性。应保存待执行意图，通过受控调用提交，再核查外部结果；通知等后续动作也有独立的可靠投递要求。

这一阶段的验收重点是：无确认不写入、重复确认只对应一个操作、过期或参数不匹配的确认被拒绝。具体状态与事务边界见[审批与恢复](./ai-agent-java-approval-recovery.html)。

## 第六步：提交后超时，恢复程序应该先做什么？

假设升级系统已经创建记录，但响应丢失。应用看到超时，只能确认“没有拿到结果”，不能确认“没有执行”。

恢复应沿原操作号核查：

| 核查结果               | 后续处理                               |
| ---------------------- | -------------------------------------- |
| 已确认提交成功         | 关联已有业务记录，更新任务并向用户说明 |
| 确认尚未执行且允许重试 | 沿用原操作号与已授权参数有限重试       |
| 仍在处理中             | 保存状态，按约定继续查询               |
| 无法判断是否执行       | 保留结果未知，转入对账或人工核查       |

这些是应用与业务系统的状态语义，不要求照搬某套框架的枚举。

恢复时同时检查执行租约或状态版本，避免两个 worker 各自推进同一任务。重新进入节点，也不能为同一业务意图生成新操作号。

取消同样需要核查边界：尚未提交的后续动作可以停止；已提交的升级不因浏览器关闭自动撤销。需要撤销时，应按新的业务规则处理。

验收应覆盖“提交成功后丢响应”“进程在提交前后退出”“两个恢复者同时接手”和“取消时动作正在执行”。每种情况检查业务终态及操作数量，不只检查任务表显示什么。

## 第七步：怎样逐层验收，避免一层通过就宣布全部完成？

接入顺序与验收层次可以放在同一张表里：

| 阶段     | 新增能力         | 应取得的验收证据                 |
| -------- | ---------------- | -------------------------------- |
| 可信只读 | 身份与工单查询   | 正确结果、越界拦截及对象归属     |
| 模型工具 | 参数解析与循环   | 调用回填、停止原因及执行次数     |
| 政策证据 | 检索与引用       | 正确版本、必要条件及引用依据     |
| 受控写入 | 草稿、确认与事务 | 授权绑定、升级记录及防重         |
| 故障恢复 | 核查、续接与取消 | 重启后的终态、操作数量及对账状态 |

模型替身测试适合检查确定性的分支，但不能证明真实模型能正确选择工具。

接口测试检查认证、序列化和错误映射；数据库测试检查目标数据库上的约束与事务；独立进程恢复测试检查状态能否在重启后继续使用。它们不能相互替代。

真实模型评测另用版本化问集，衡量事实、拒答、工具选择、延迟和费用。供应商不可用时，也不应让所有业务逻辑测试失去执行条件。

应按阶段记录尚未验证的层次。具体划分见[Java Agent 测试分层](./ai-agent-java-evaluation.html)，不能把设计清单当成已通过的测试报告。

## 小结

1. 先确定身份、业务终态和版本组合，再沿可信只读链路逐项接入模型与证据。
2. 模型提出调用，应用验证完整参数与授权；框架自动执行和应用自管循环要明确分工。
3. 写操作经过草稿、可信确认和短事务，审批绑定主体、参数、版本、期限与稳定操作号。
4. 超时不等于未执行，恢复先按操作号核查；取消不能自动回滚已提交的业务动作。
5. 替身、接口、数据库、进程恢复和真实模型分别提供验收证据，一层通过不代表全链路成立。
