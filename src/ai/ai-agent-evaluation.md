# 怎么评测 Agent 真的完成了任务？

> 用业务环境里的结果确认任务完成，再检查权限、执行过程和多次运行的稳定性，不能只给最终回答打分。

## 说“工单已升级”，后台就真的有记录了吗？

假设用户要求为自己的 `T-1048` 创建升级工单，原工单状态是 `WAITING_VENDOR`。
助手回答“已经创建”，但后台可能没有升级记录，也可能创建了两条，或者顺便修改了别人的工单。
这三种情况的文字都可以很流畅，业务结果却都不合格。

因此，评测任务要同时定义初始数据、用户授权和期望变化。
本例要求原工单保持不变，只产生一条绑定经授权 `operationId` 的升级记录，且没有越权写入。
每项完成标准先由业务方确认，再实现可独立检查的断言。

## 为什么每次试验都要从干净的环境开始？

评测一次完整执行称为一次 trial。同一道任务应运行多次，每次恢复同一初始快照。
工单数据库、用户身份、审批状态、操作号和工具缓存都要隔离，避免第二次直接读到上次创建的记录。
模型版本、工具 Schema、工具文档、提示词、数据快照和执行器版本也要记录，否则无法归因变化。

可以先用替身工具控制结果，再在隔离测试服务里核对真实接口契约。
替身要模拟权限拒绝、超时和写入状态，不能只对任意调用都返回“成功”。
评测环境的评分器与标准答案还应对 Agent 隔离，防止它修改断言或直接读取答案。

覆盖题目至少包含正常查询、获批升级、未授权写入、他人工单、下游超时和重复请求。
每道题还要有一个确实能通过的参考实现，排除权限配置、题意或评分器本身有错。
固定随机种子可以减少部分变量，但不能保证不同供应商或基础设施下完全复现。

## 终态与执行轨迹，分别检查什么？

| 检查对象     | 工单任务的判据                       | 适合的评分方式               |
| ------------ | ------------------------------------ | ---------------------------- |
| 业务终态     | 恰好一条升级记录，目标与操作号正确   | 直接查询测试数据库           |
| 不可省的顺序 | 验证归属和有效授权后才提交写入       | 服务端审计事件与状态断言     |
| 副作用范围   | 原工单和其他用户的数据未被误改       | 比较前后快照、统计越权写入   |
| 执行资源     | 工具次数、Token、耗时未超任务预算    | 运行记录与计量数据           |
| 最终解释     | 正确说明结果与证据，信息不足时不虚报 | 规则加经校准的人工或模型评分 |

不要把专家的一条工具序列写成唯一答案。
先读取政策再查工单，或先查工单再读取政策，都可能合格。必须执行的授权先后关系仍需严格检查。
可观察轨迹包括调用、参数、结果、审批事件与状态变化，不要求记录模型内部隐藏推理。
断点和审批如何恢复，见[可恢复工作流](./ai-agent-workflow-recovery.html)。

## 写入后响应丢失，评测器怎样抓住重复操作？

在测试工具中注入固定故障，比随机断网更便于重现和比较。

| 故障场景                   | 合格行为                                         |
| -------------------------- | ------------------------------------------------ |
| 创建之前超时               | 不虚报成功，在权限与预算内有限恢复               |
| 创建成功后丢弃响应         | 按操作号查状态，重试也只保留一条升级记录         |
| 补充输入后重新进入节点     | 复用同一业务意图，检查授权仍有效且没有重复副作用 |
| 用户撤回审批或换成他人工单 | 拒绝执行，即使最终回答因此不能宣称完成           |

工具成功率和任务成功率应分别报告。工具请求超时但确认到了正确终态，任务仍可能完成。
没有查到可靠终态时应记为结果未知，后续核查清楚再归类，不能为了提高分数直接算成功。
副作用计数必须来自环境或服务端审计，而非 Agent 自己返回的统计。

## 多运行几次，“成功率”应该怎么算？

`pass@k` 关注一个任务在 k 次尝试中是否至少成功一次，`pass^k` 关注这 k 次是否全部成功。
下面用三道虚构任务，各运行三次。成功判定同时查看业务终态与越权计数。
记录假设由测试环境读取，代码可直接用 Node 执行，不会调用模型或修改外部系统。

```javascript
const trial = (escalationCount, unauthorizedWrites = 0) => ({
  terminal: { ticketId: "T-1048", status: "WAITING_VENDOR", escalationCount },
  unauthorizedWrites,
});
const tasks = [
  [trial(1), trial(1), trial(1)],
  [trial(1, 1), trial(1), trial(2)],
  [trial(0), trial(0), trial(0)],
];
const succeeded = ({ terminal, unauthorizedWrites }) =>
  terminal.ticketId === "T-1048" &&
  terminal.status === "WAITING_VENDOR" &&
  terminal.escalationCount === 1 &&
  unauthorizedWrites === 0;
const results = tasks.map((runs) => runs.map(succeeded));
const fraction = (count) => `${count}/${results.length}`;
console.log({
  "pass@1": fraction(results.filter((runs) => runs[0]).length),
  "pass@3": fraction(results.filter((runs) => runs.some(Boolean)).length),
  "pass^3": fraction(results.filter((runs) => runs.every(Boolean)).length),
});
```

三行判定分别为 `[true, true, true]`、`[false, true, false]`、`[false, false, false]`。
输出是 `pass@1 = 1/3`、`pass@3 = 2/3`、`pass^3 = 1/3`。
第二题第一次虽然有升级记录，却存在越权写入，第三次有重复记录，都不能通过。

这里按每题固定顺序的前 k 次尝试计算经验比例，`pass@1` 只看第一列。
若把全部九次运行混合统计，单次通过率是 `4/9`，这是另一个统计口径。
基于候选抽样的 pass@k 估计器也有不同计算方式，报告必须说明采样与聚合口径。

对同一道任务，只有在每次独立且成功概率固定为 p 时，才可写出 `pass@k = 1 - (1-p)^k`、`pass^k = p^k`。
共享缓存或环境故障会产生相关性，不同任务的成功概率也不同，不能把所有任务的平均 p 直接代入。
三题样本只能演示算法，实际比较要按任务类型分层、报告样本量与波动，并统计每任务成本和尾部耗时。
允许多试几次也会消耗额外预算，而且“至少一次成功”并不说明其余尝试没有破坏数据。

## LLM Judge 适合判哪些事，怎样避免分数骗过自己？

数据库终态、授权与副作用优先用代码验证，解释是否清楚、证据是否充分再使用 Judge。
给 Judge 具体评分细则、参考证据和分档例子，要求证据不足时返回无法判断。
先由人工标注一批样本检查一致性，对分歧回看原始记录，不能只因模型更强就相信分数。

答案对比时交换展示顺序，检查位置偏差。加入长短不同但事实相同的样本，检查是否偏爱冗长回答。
评测结果里分别报告业务通过率、安全违规、未知结果、解释质量、调用次数、预算与时延，不能用一个平均分盖掉越权事件。
局部完成可以计分用于诊断，但没有满足全部业务硬约束，就不能标记整项任务成功。

CI 可先跑确定性核心用例，扩大样本后再比较质量与成本。门槛应在看见新结果前确定，具体发布流程见[灰度与评测准入](./ai-feature-rollout-guard.html)。
Trace 回放要使用隔离环境或记录下来的只读工具结果。重新执行真实创建工具可能发出第二次升级请求，外部数据变化也会让“回放”变成另一个任务。

## 小结

1. 任务完成要从业务终态确认，最终回答、工具成功和环境正确是不同判据。
2. 每次 trial 恢复环境并固定版本，覆盖应该执行与必须拒绝的场景，再检查评分器本身是否可靠。
3. 允许多条合法工具路径，授权先后顺序和副作用范围仍是硬约束。
4. `pass@k` 看至少一次成功，`pass^k` 看稳定成功，必须同时说明采样、任务分层和预算。
5. Judge 用于辅助主观质量评分，代码检查与人工校准不能省，真实写工具不能随意回放。
