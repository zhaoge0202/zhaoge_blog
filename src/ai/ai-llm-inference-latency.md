# 大模型为什么首字慢，后续生成也会慢？

> 把等待首个输出和后续逐步生成分开测量，再沿排队、输入计算、生成和传输逐段定位。

## 同样查一张工单，为什么有人秒回，有人等很久？

假设助手查询本人 `T-1048`，后台已经返回 `WAITING_VENDOR`，但总结迟迟不出现。
可能是多塞了几十页历史，也可能是服务排队或代理缓冲。另一次很快出字，却每隔很久才增加一句，瓶颈又可能不同。
只看一个接口总耗时，无法判断该减少上下文、限制并发，还是检查流式传输。

本文用经典自回归、decoder-only Transformer 解释推理阶段，并假定采用完整历史注意力和 KV Cache。
混合架构、滑动窗口、推测解码和不同推理模型的实现会有差异，不能把这套简化执行图当作所有模型的内部流程。

## Prefill、Decode 和 KV Cache 各做什么？

模型先处理输入序列，这一阶段通常称为 prefill。输入中的各个位置可参与批量计算，但仍受因果注意力约束。
随后按照已知前缀生成后续 Token，称为 decode。朴素自回归循环每轮追加一个 Token，再开始下一轮。
工具调用参数同样需要生成，不能因为结果暂时不是自然语言回答，就从生成耗时里消失。

KV Cache 保存历史位置各层注意力计算需要的 Key、Value，中间状态可在后续生成中复用。
因此 decode 不必在每步重新计算全部历史位置的 K、V，但仍要访问相关历史缓存，历史越长可能带来更多访存和注意力计算。

| 阶段           | 主要工作                     | 值得核对的变量                        |
| -------------- | ---------------------------- | ------------------------------------- |
| 请求准备与排队 | 路由、预算、等待调度         | 并发、队列长度、配额、调度策略        |
| Prefill        | 处理输入，建立或复用历史状态 | 实际输入长度、缓存命中、硬件与批次    |
| Decode         | 基于前缀继续生成             | 实际输出长度、活跃请求、KV 容量与带宽 |
| 传输与展示     | 序列化、网络、代理、前端渲染 | flush 时间、分片聚合、网络抖动        |

完整注意力的输入计算包含随序列长度平方增长的注意力工作，但模型还包含其他计算。
缓存后的逐步生成、不同注意力架构和批处理方式也各有成本，不能据此把整个推理延迟一律写成 `O(N²)`。
复杂度描述更不能直接换算成“输入翻倍，实测耗时一定四倍”。

## 首字延迟和吐字速度，怎样定义才不会混淆？

先选测量点。用户端 TTFT 可定义为发出请求到第一个可展示文本片段到达的时间。
它包含应用与网关处理、排队、输入计算、首个相关输出生成，以及网络和缓冲，不等于纯 prefill 时间。
推理引擎的 TTFT 可能从请求进入引擎开始计时，结束于首个模型输出，和用户端并不是同一个范围。

响应头、心跳、角色标识和空分片都不能当作可见文本。
有些模型先产生内部推理或工具事件，可见回答到达更晚，应根据供应商提供的用量和时序字段解释，不假设能读取内部推理。

ITL（Inter-Token Latency）描述相邻输出 Token 的时间间隔。
若在同一观测点取得 N 个输出 Token 的时间戳，N 至少为 2，本文把平均 TPOT 定义为 `(最后时间 - 首个时间) / (N - 1)`。
只有一个 Token 时没有这个平均间隔。服务端指标可能采用不同边界，应核对实现再比较。

SSE 分片可能一次带多个 Token，两个分片的间隔只能称为分片间隔，不能直接冒充 ITL。
也不能用包含内部推理的输出用量除以可见文字的到达间隔，更不能把中文字数当作 Token 数。

例如，假设一个可精确观测的教学环境中，四个可见 Token 到达时间分别为 `2000、2050、2100、2200ms`。
则用户端 TTFT 为 `2000ms`，三个 ITL 为 `50、50、100ms`，平均 TPOT 约 `66.7ms`。
从请求发出到最后一个 Token 到达共 `2200ms`。这些是假设数据，不是模型压测结果。

## 模型放得进显存，为什么并发一高仍会排队？

模型权重在服务运行时占用一部分显存，KV Cache 则随活跃请求、序列长度、KV 结构与存储精度变化。
还要预留算子工作空间、激活和运行时开销，不能把“显存减去权重大小”全部算成可用请求容量。
更长输入、更长输出或更多并发，都可能挤占 KV 空间，使调度等待、抢占或缓存迁移增多。

PagedAttention 借鉴分页思路管理 KV 块，减少内存碎片和重复存储，并支持更灵活的复用。
它改善的是缓存内存管理，不会赋予无限显存，也不会突破模型的位置编码和上下文长度限制。
量化权重、量化 KV 和调整并发是不同杠杆，影响的容量、精度和性能需要分别验证。

## 相同前缀缓存命中了，为什么长回答依然慢？

Prefix Caching 复用相同前缀的 KV 状态，减少重复输入计算，每次仍然生成新回答。
它通常改善重复 prefill 的开销，不直接减少后续 decode 工作。长输出占主导时，整体改善可能有限。
缓存命中的内容仍属于逻辑上下文，不能借缓存绕过输入或总窗口限制。

稳定的系统指令和工具定义放在可复用前缀，有助于获得命中机会。
实际还受模型、输入渲染、缓存边界、路由、保留策略和淘汰影响，文字看起来相同也不保证命中。
应统计实际命中 Token、输入量、写入开销与请求时延，不能把某家产品的折扣和缓存时长当通用规律。

缓存还要尊重隔离边界，避免跨租户的复用行为泄露私有内容是否出现过等侧信号。
vLLM 文档中的 `cache_salt` 是其具体实现能力，可将复用限制在相同盐值的请求之间。
可信服务端应按用户或租户的信任范围决定隔离值，不能只相信客户端自报。这也不能替代实际的数据授权。
上下文装配和压缩怎样影响前缀，见[Agent 上下文工程](./ai-agent-context-engineering.html)。

## 怎样用三个实验找到主要瓶颈？

固定模型与权重版本、硬件、量化、推理参数、调度配置和测量点，再一次只改变一个主要变量。
缓存冷、热请求分组记录，预热、网络路由和请求分布保持可比较，避免把不同负载混成一个平均值。

| 实验       | 控制方式                                     | 重点观察                             |
| ---------- | -------------------------------------------- | ------------------------------------ |
| 改输入长度 | 短输出、固定并发，逐步增加历史或证据         | TTFT、prefill、输入量与缓存命中      |
| 改输出长度 | 固定输入与并发，用可比较任务生成不同实际长度 | decode、TPOT、总时长及实际输出 Token |
| 改并发     | 固定输入输出分布，逐级提高同时活跃请求       | 排队、KV 使用、TTFT 与 ITL 的尾部    |

只调高最大输出上限，不保证模型真的生成更长文本，必须记录实际输出量。
每组报告样本数、冷暖状态、p50/p95，并分别统计请求延迟和 Token 间隔。
多请求总吞吐是观测窗口里的总生成量除以时间，它不能直接作为单请求吐字速度，也不能用它推导 p95 ITL。

自建 vLLM 可结合等待请求数、队列耗时、prefill/decode 耗时、KV 使用与前缀命中定位，指标名称以部署版本为准。
托管 API 没有暴露引擎细节时，应保留请求 ID、输入输出用量、首个有效分片和结束时刻，避免仅凭 TTFT 猜测显卡内部故障。
若上游已及时出字，但页面仍等很久，继续沿[流式输出与代理缓冲](./ai-streaming-sse-backend.html)排查。

## 小结

1. Prefill 处理输入，decode 持续生成，KV Cache 复用历史状态，三者的成本不能合成一个平方复杂度结论。
2. 用户端 TTFT 包含队列、计算与传输，和引擎首个输出可能有不同边界，应明确时钟和测量点。
3. ITL、平均 TPOT、分片间隔和系统吞吐统计对象不同，比较时要说明 Token 数与采样方式。
4. 权重与 KV 都占显存，分页管理和前缀缓存各有作用，缓存命中不会消除输出生成或逻辑窗口限制。
5. 输入、输出、并发分别做受控实验，记录冷暖缓存与尾部指标，拿实际链路证据决定优化方向。
