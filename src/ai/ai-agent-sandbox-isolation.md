# 代码工具怎样限制文件、进程、凭据和网络出口？

> 把模型可提出的操作限制成明确能力，再由执行环境控制它能接触的数据、进程、凭据、网络和资源。

## 工单助手只需要分析文件，为什么不能直接给一把 Shell？

假设用户上传 T-1048 的处理记录，请助手统计供应商等待时长。
任务需要读取指定文件并做计算，通常不需要修改宿主文件、安装包或任意访问网络。
优先提供有范围的解析和统计工具，能减少执行环境需要承担的权限。

确实需要代码执行时，仍应限定输入、输出和作业范围。
模型在独立对话里运行，只隔开了部分消息上下文，没有隔开文件、进程或凭据。
提示注入如何影响操作选择，见[提示注入与工具投毒](./ai-agent-prompt-injection.html)。

## 路径没有 ../，为什么还可能读到工作区以外？

字符串前缀检查容易混淆同名目录，路径规范化通常也只处理字面上的点段。
工作区内的符号链接仍可能指向范围外，授权目录本身也可能由不可信进程替换。
打开已有文件前，需要核对可信根目录和目标的真实路径、文件类型与访问模式。

“检查过真实路径，再按原路径打开”还有检查与使用之间的竞态，常称为 TOCTOU。
两步之间如果目标被替换，实际打开的文件可能已经变化。
应结合平台提供的安全打开方式与目录句柄，并保护授权目录不被非信任主体改写。
创建新文件还要核查父目录和打开选项，不能要求不存在的目标先解析成真实文件。

更稳的任务边界可以只挂载本次审核过的输入，使用只读模式，并单独提供有配额的输出目录。
不要挂载整个用户主目录、仓库根、SSH 目录或宿主敏感设备，再把路径校验当作唯一保护。
文件内容进入模型前仍需检查当前用户的访问权限，挂载范围与业务授权是两层约束。

## 超时后，为什么只中断一个 Java Future 不够？

代码工具可能启动 Shell、解释器和更多子进程。
取消等待线程不代表这些进程已经结束，只终止父进程也可能留下继续执行的后代。
启动器需要记录作业所属的进程组或隔离单元，超时后终止整个作业，再确认资源已回收。

运行时应分别限制墙钟时间、CPU、内存、进程数、文件描述符、临时磁盘和输出字节数。
CPU 配额限制使用速率，不能代替总截止时间；内存上限也不会自动限制宿主日志占用。
标准输出和错误输出都要持续读取并设上限，避免管道堵塞或无界收集。

子进程以专用非特权身份运行，只保留必需的系统能力。
命令采用经过校验的可执行文件和参数数组，避免把模型文本拼进 `sh -c`。
即便使用参数数组，解释器代码、配置文件和可执行文件本身仍然需要相应的执行边界。

## 凭据和网络，怎样避免跟着主进程一起交出去？

子进程环境按允许项从空配置构建，不直接继承主服务全部环境变量。
能通过受控业务代理完成的查询，就让代理持有凭据，代码工具只得到当前任务需要的结果。
必须注入凭据时限定受众、范围和期限，限制子进程读取与输出，并在作业结束后撤销或清理。

凭据不写入镜像层、命令行参数或模型上下文。
环境变量只是传递手段，不能防止同权限进程读取或工具把它打印到结果中。
日志脱敏也不能追回已经发送到外部服务的数据。

无需联网的任务默认关闭外网。
确需联网时，可以经受控出口代理按目的地址、协议、端口和身份放行，阻止未经允许的直连旁路。
元数据返回的地址和重定向都要验证，DNS 解析后的地址也须遵守限制，避免检查域名后实际连接到其他地址。
每次跳转重新检查，不把 HTTPS 本身当成目标可信的证明。

## 容器、Rootless 和独立虚拟机分别增加什么边界？

Linux 容器通过命名空间、cgroup 和访问控制机制提供隔离与限额，但仍共享所在 Linux 宿主的内核。
桌面容器产品可能先运行 Linux 虚拟机，也不代表每个任务都有独立内核。
为高风险任务采用独立虚拟机，可以增加内核边界，挂载、网络、凭据和镜像更新仍需正确配置。

Rootless 让 Docker 守护进程及容器在非 root 身份下运行，降低部分高权限风险。
它不会自动消除应用漏洞、敏感挂载或出站访问，也不保证所有资源限制在当前宿主上均有效。
需要核查 cgroup、运行时和操作系统支持，并用实际作业确认限额生效。

不要向工具容器暴露 Docker socket，或允许它自行提交任意容器配置。
连接守护进程的权限可能使它创建更高权限的任务或读取额外挂载。
把 socket 文件只读挂载，也不会把 Docker API 的操作能力变成只读。

## 一个离线解析容器，可以怎样表达最低需要的配置？

下面仅演示待复现的配置形状，没有实际执行。
镜像、摘要、宿主目录和工具入口都是占位，实施时先核对镜像来源、平台和确切摘要，再替换相应值。

```bash
task_sandbox_image='registry.example.invalid/tool-runner@sha256:<已核验的64位摘要>'
docker run --rm --init \
  --user 10001:10001 \
  --cap-drop ALL \
  --security-opt no-new-privileges=true \
  --read-only \
  --network none \
  --pids-limit 64 \
  --cpus 1 \
  --memory 256m --memory-swap 256m \
  --tmpfs /tmp:rw,nosuid,nodev,noexec,size=32m \
  --workdir /tmp \
  --mount 'type=bind,src=/absolute/path/to/reviewed-input,dst=/input,readonly' \
  --entrypoint /app/tool \
  "$task_sandbox_image" --input /input/report.csv
```

配额数值是教学起点，需按解析任务测量，并保留适用的 seccomp 与宿主安全策略。
不要为解决兼容问题直接加 `--privileged` 或关闭过滤。
`--init` 帮助转发信号和回收进程，作业截止与强制清理仍由启动器负责。
临时目录的 `noexec` 也不能阻止解释器读取其中的脚本并执行。

这个配置只适用于离线任务，不能拿它验证需要外部服务的完整 Agent。
容器启动成功后还要核查真实挂载、身份、能力、限额与网络，而非只检查命令里有没有出现这些标志。

## 只读 SELECT 加上 LIMIT，为什么仍不能叫完整沙箱？

`SELECT` 也可能经函数、扩展、外部数据源或文件读取触及更多能力，具体取决于数据库实现。
顶层 `LIMIT` 限制返回行数，无法普遍限制扫描、排序、聚合成本，也不限制单个超大字段的字节数。
需要同时控制可查询对象、函数与扩展、数据库身份、文件和网络权限、执行时间及结果体积。

Shell 关键词黑名单也难以覆盖等价表达和工具间组合。
对于工单助手，能限制为查询本人记录、计算明确指标时，就让确定性工具完成这些动作。
业务工具自身的授权与幂等仍沿用[内部接口接入约束](./ai-tool-calling-business-api.html)。

## 怎样证明限制生效，并区分宿主测试与容器测试？

| 验收场景                       | 应观察的结果                         |
| ------------------------------ | ------------------------------------ |
| 输入指向范围外文件或符号链接   | 实际读取被拒绝，无范围外内容进入结果 |
| 检查后替换路径目标             | 安全打开策略仍保持在授权范围         |
| 进程超时并存在后代进程         | 整个作业结束，后代不再存活           |
| 内存、进程数或输出超过限额     | 触发受控失败，并记录真实退出原因     |
| 请求外部地址、内网地址或跳转   | 按出口策略阻断，不能绕过代理直连     |
| 尝试读取或打印任务不需要的凭据 | 凭据不可见，错误与日志也不泄漏       |
| 作业结束或被取消               | 临时目录、句柄与进程清理符合保留策略 |

测试应在隔离的合成环境执行，保留身份、挂载、限额、退出码、拒绝记录与清理结果。
宿主 Java 的业务权限测试可以证明特定工具拒绝越权，无法单独证明容器逃逸防护、内核隔离或网络出口策略。
镜像或内核更新后，还应重跑相应边界测试，不能长期沿用一次成功的结果。

## 小结

1. 先收窄任务能力，再分别控制文件、进程、凭据、网络与资源范围。
2. 路径规范化和真实路径检查仍需考虑符号链接、目录权限与检查使用竞态。
3. 超时处理覆盖整个作业，资源配额、输出限制和临时数据清理各自验收。
4. 容器、Rootless 和虚拟机提供不同边界，敏感挂载与守护进程权限可能削弱保护。
5. 用实际拒绝与清理证据验证隔离，提示词、只读 SQL 和独立对话不能替代系统级边界。
