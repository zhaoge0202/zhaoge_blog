# 模型权重和 KV Cache 怎样估算显存，量化能省多少？

> 权重决定一部分固定开销，缓存随请求变化，运行时还需要额外空间；装得下模型，不等于扛得住业务并发。

## 单人查询正常，为什么多人进来就可能显存不足？

假设工单助手使用一个约 7B 参数的模型。短问题能够正常回答，但多名客服同时带着长历史提问，服务开始排队，甚至出现显存不足。

只算“模型参数量乘以每个参数的字节数”，会漏掉请求运行时的成本。可以先把预算分成三部分：

```text
推理显存需求
≈ 驻留权重
+ 当前请求的 KV Cache
+ 激活、算子工作空间、执行图、通信及其他运行时开销
```

三部分不一定同时达到各自峰值，实际分配也受到推理引擎影响。这是帮助定位的预算模型，不是任何服务都能直接套用的精确峰值公式。

下面的数字全部是教学假设与手算，不是部署或压测结果。

## 7B 模型的权重，到底需要多少空间？

先假设模型恰好有 70 亿个参数，全部以相同位宽存储，不考虑额外信息：

```text
裸权重字节数 = 参数量 × 每个参数的位数 / 8
```

| 假设编码     | 每个参数的理想占用 | 70 亿参数的裸权重   |
| ------------ | ------------------ | ------------------- |
| FP16 或 BF16 | 2 字节             | 14 GB，约 13.04 GiB |
| INT8         | 1 字节             | 7 GB，约 6.52 GiB   |
| INT4         | 0.5 字节           | 3.5 GB，约 3.26 GiB |

这里使用十进制 GB 和二进制 GiB：`1 GB = 10⁹` 字节，`1 GiB = 2³⁰` 字节。容量报告应注明单位，避免把不同口径直接相减。

FP16 与 BF16 都是 16 位浮点格式，但指数和尾数安排不同，数值范围与精度也不同。存储字节数相同，不代表算术表现完全一样。

量化制品通常还需要分组尺度、可能存在的零点、对齐填充等信息；部分层也可能保留更高精度。因此，INT4 表格中的数值只是全部参数理想打包后的裸数据量，不能直接当作加载后的显存。

权重文件大小与 GPU 驻留量也不必相同。加载过程、内存布局转换、适配器和运行时分配，都可能让两者出现差别。

## KV Cache 为什么会随上下文与并发增长？

在常见的 decoder-only Transformer 中，历史位置的 Key、Value 可以缓存下来，后续生成时复用，避免每一步重新计算这些历史状态。

先假设所有层都使用相同的 KV 结构，并保留完整历史。每层单个请求的 K、V，各可以理解为包含下面几个维度：

```text
KV 头数 × 当前保留的 Token 数 × 每个头的维度
```

将 K、V、层数和多个请求合起来：

```text
KV 字节数
≈ 2 × 层数 L × KV 头数 Hkv × 头维度 D
    × 每个 KV 元素的字节数 b
    × 所有请求保留 Token 数之和 ΣTi
```

前面的 `2` 表示 K 和 V。这里必须使用 **KV 头数**，不能不加区分地填写 Query 头数。

例如，GQA 可以让多组 Query 共享较少的 KV 头。模型有 32 个 Query 头，并不意味着也有 32 个 KV 头。

这条公式估算逻辑张量的数据量，没有包含分页元数据、对齐、暂存区与预分配空闲块。

## 用一组具体参数，怎样看出长上下文的代价？

假设一个教学模型具有：

- 32 层完整历史注意力。
- 每层 8 个 KV 头，每个头维度为 128。
- K、V 都采用每元素 2 字节的编码。
- 请求之间没有共享缓存。

每增加一个保留 Token，KV 数据量约为：

```text
2 × 32 × 8 × 128 × 2
= 131,072 字节
= 128 KiB
```

因此，一条保留 8,192 Token 的序列，KV 数据量约为：

```text
8,192 × 128 KiB = 1 GiB
```

八条这样的独立序列，就是约 8 GiB。这里的序列长度包含输入和生成过程中实际保留的历史，不只是用户刚输入的那一句话。

现在再假设有 24 GiB 可供进程使用，权重采用前面的 FP16 裸数据估算：

```text
24 - 13.04 - 8 ≈ 2.96 GiB
```

剩余部分还要承担其他开销，不能据此宣布“保证支持八并发”。完整模型的结构和各阶段峰值尚未计入，真实可用容量也要核对。

当前缓存占用较小，也不代表请求之后不会增长。准入时需要考虑后续生成的预留，或采用有界的动态调度与过载策略。

## 为什么不能把同一个 KV 公式套给所有模型？

上面的算例明确限定了完整历史、相同层结构和独立缓存。真实系统可能存在不同情况：

| 实现或结构             | 对估算意味着什么                                 |
| ---------------------- | ------------------------------------------------ |
| 前缀共享               | 相同且允许复用的前缀可能共享部分物理缓存         |
| 分页管理               | 改变分配、复用和碎片情况，不会消除 KV 数据本身   |
| 滑动窗口或分块注意力   | 部分层达到窗口后，不再按完整历史持续增长         |
| 静态缓存               | 可能按预定容量分配，实际显存不能只看当前有效长度 |
| 混合注意力、MLA 等结构 | 需要按实际缓存表示重新推导                       |

所以，模型标称最大上下文、请求实际长度、逻辑 KV 数据量和引擎已分配显存，是四个相关但不同的量。

前缀缓存复用计算与存储，也不会让这些内容从逻辑上下文中消失，更不能让模型突破自身窗口限制。

推理过程与缓存命中的延迟边界，见[推理阶段与首字延迟](./ai-llm-inference-latency.html)。

## 权重量化、激活量化和 KV 量化，分别节省什么？

量化不是一个覆盖所有内存的统一开关。

权重量化改变参数的存储或计算表示，主要影响驻留权重；KV 量化针对历史缓存；激活量化则涉及计算过程中的中间表示与相应算子。

例如，`W4A16` 通常描述 4 位权重、16 位激活，并没有因此保证 KV 也使用 4 位。具体格式、覆盖层和运行方式仍要按实现核对。

即便采用更低位宽，也不能直接把整体显存按同一比例缩小：

- 未量化部分、尺度和工作空间仍然存在。
- KV 可能保持原来的编码。
- 引擎可能把节省的空间继续用于缓存池。
- 激活与执行图等开销不会自动按权重比例下降。

量化也不必然加速。反量化、额外处理、硬件与内核支持都会影响性能；短上下文或低并发时，节省的内存可能没有转化为更低延迟。

业务质量同样需要检查。平均分相近，仍可能在工单编号、金额、否定条件或工具参数上出现变化。容量收益和质量损失必须分开观察。

## 多卡和 MoE，为什么也不能只做一道除法？

将权重或计算分布到多张卡，可以改变单卡需求，但不能机械地用总显存除以卡数。

张量并行、流水线并行与其他部署方式对权重、KV 和中间结果的划分不同；某些配置还会复制 KV 头或其他状态。通信缓冲和负载不均，也会占用空间。

容量判断应看每张卡的实际峰值，尤其是最紧张的一张，而不是只看所有卡加起来还有多少空闲。

MoE 的每次激活参数较少，也不意味着只需要存放这些参数。专家权重如何驻留、卸载或分片，以及路由与通信成本，仍会影响资源需求。

模型架构、训练方式和部署表示的区别，见[训练、偏好优化与蒸馏](./ai-training-alignment-distillation.html)。

## 真正做容量对照时，应该怎样组织记录？

先固定模型与 Tokenizer 版本、硬件、引擎、权重格式、KV 编码和调度配置，再设计对照。不要同时换量化方式、上下文长度和并发，然后把变化全部归因于量化。

可以按下面的顺序规划：

1. 比较相同输入输出分布下的权重格式，分别观察质量与显存。
2. 固定权重格式，逐步改变实际保留长度，检查 KV 增长。
3. 固定长度分布，改变到达率与并发，检查排队、拒绝和尾延迟。
4. 单独比较缓存冷热，记录是否真正命中。
5. 验证取消、结束和过载后，任务与资源是否按预期释放。

记录显存时，应注明测量工具、采样时刻，以及观察的是有效分配、保留池还是整个进程占用。请求结束后显存数字没有立即下降，不一定意味着泄漏，也可能是引擎继续保留内存池。

最终报告同时提供任务质量、成功与失败数量、首字等待、总时延、吞吐和资源峰值。具体负载与过载验证见[模型服务部署与容量](./ai-model-serving.html)。

## 小结

1. 权重、KV Cache 与运行时开销共同决定显存，裸权重大小不能直接代表并发容量。
2. KV 估算使用真实的缓存结构与 KV 头数，普通完整历史公式不能套给所有架构。
3. GB、GiB、逻辑数据量和引擎分配量需要分清，容量规划还要考虑后续生成与峰值。
4. 权重、激活和 KV 量化各有作用，低位宽不自动保证等比例省显存或加速。
5. 多卡和 MoE 需要逐卡检查驻留、复制与通信，用质量和负载对照验证最终收益。
