# 连续批处理怎样调度长短请求，吞吐与首字延迟如何取舍？

> 在生成过程中重新安排批次成员，可以减少空闲等待；实际收益仍取决于输入处理、缓存容量和请求之间怎样分享资源。

## 一个长报告，为什么可能拖慢旁边的短问题？

假设模型服务处理几类请求：

- A 带着长篇材料，需要生成一份较长报告。
- B 只有一句状态查询，希望尽快得到简短回答。
- C 在 A、B 开始处理后才到达，也是一个短问题。

如果批次成员固定到整批结束，B 完成以后留下的计算位置可能无法及时交给 C，后来的请求继续排队。

这里不能简单理解成“静态批处理一定要等所有请求结束，才能返回任何答案”。有的实现能够先返回 B 的结果，但批次成员和计算资源仍未必能够立即重新安排。

连续批处理主要改变后一个问题：在允许的调度边界移出已完成请求，再接纳新的工作。

本文使用教学轨迹说明调度原理，没有运行模型、GPU 服务或性能实验。

## 连续批处理，是不是把很多请求一直放在一起算？

常见自回归生成需要多轮计算。普通 decode 迭代通常为活跃序列继续生成后续 Token，直到结束条件满足。

请求级批处理较多地围绕完整请求组织批次；迭代级调度则允许在生成过程中重新选择下一轮参与计算的工作。

```text
固定成员：A、B → 多轮生成 → 整批结束 → 接纳 C

动态成员：A、B → B 完成 → 接纳 C → A、C 继续
```

这不意味着可以随时打断一个正在执行的 GPU 内核。调度器在实现允许的边界作决定，已经提交的计算仍受执行机制约束。

也不意味着每个请求每轮都处理相同数量的 Token。prefill、decode、分块处理和推测验证可能具有不同粒度。

ORCA 的迭代级调度提供了理解这一思想的起点，具体引擎的队列、执行和返回机制仍需分别核对。

## Prefill 和 Decode，为什么会互相影响？

Prefill 处理输入并建立必要的历史状态；decode 根据已有状态持续生成。两者的计算形态不同，却可能竞争同一组设备资源。

长输入的 prefill 如果一次占用较长执行时间，已经开始回答的 B 可能迟迟收不到下一个 Token，ITL 因而变差。

反过来，如果始终优先推进所有 decode，新到达的 C 可能一直无法完成自己的输入处理，首字等待也会增长。

因此，吞吐更高并不自动意味着每个用户更快。服务要同时考虑正在输出的用户和仍在等待首字的用户。

分阶段耗时的定义见[推理延迟](./ai-llm-inference-latency.html)，不能把整个请求统一解释成注意力的平方计算。

## 分块 Prefill，怎样给正在生成的请求留出机会？

分块 prefill 把较长输入拆成多次可调度的处理工作，在每轮预算内与 decode 配合推进。

下面是一条**教学调度轨迹**，只描述先后关系，不代表某个引擎的实际批次或耗时：

| 轮次 | 本轮安排的工作                     | 调度后发生什么               |
| ---- | ---------------------------------- | ---------------------------- |
| 1    | A 的部分 prefill，B 的完整 prefill | B 的输入已就绪，可以开始生成 |
| 2    | B 的 decode，A 的后续 prefill      | A 的输入继续推进             |
| 3    | B 完成，A 完成剩余 prefill         | B 退出，C 此时已到达         |
| 4    | A 的 decode，C 的 prefill          | C 完成输入处理               |
| 5    | A 与 C 的 decode                   | 两个请求继续生成             |

本例将输入就绪与后续生成分开表达，首个输出是否在 prefill 步骤的末尾产生，以实现为准。C 被接纳以后仍然要处理自己的输入，连续批处理没有跳过必要计算，也没有保证它一到达就能立即出字。

本次读取的 vLLM V1 文档介绍了一种优先 decode、再用剩余 Token 预算安排 prefill 的策略；放不下的长 prefill 会被分块。

这是具体实现示例，不应写成所有推理引擎必须采用的规则。

## 几个看起来相似的容量参数，分别限制什么？

| 约束                  | 主要控制什么                | 不能直接推导什么               |
| --------------------- | --------------------------- | ------------------------------ |
| 活跃序列数量          | 同时调度多少条序列          | 每轮总工作量一定相同           |
| 每轮批处理 Token 预算 | 本轮可以安排多少 Token 工作 | 系统每秒一定生成多少 Token     |
| 单请求上下文上限      | 一条请求允许的逻辑长度      | 当前有足够缓存容纳它           |
| KV 缓存容量           | 可以保存多少历史状态        | 所有请求都能继续增长到最大长度 |
| 队列与等待上限        | 尚未进入执行的积压          | 活跃请求一定满足时延目标       |

这些约束共同生效，不能只调高“最大并发”就宣布容量增加。

A 已经占用长历史，后续还要继续生成；新接纳 C 时，需要考虑缓存将来的增长，而不只是当前剩余空间。

有的引擎预留缓存块，有的动态分配或采用抢占。实际准入规则应与对应机制一致，不能用某个参数简单乘出保证并发。

资源估算见[权重与 KV Cache](./ai-model-memory-quantization.html)。

## 为什么批次更大，吐字速度反而可能变差？

更大的每轮预算可能让一次安排更多输入，提高部分负载下的处理效率；但单轮工作更重，也可能让已有回答等待更久。

本次 vLLM 文档将批处理 Token 预算与 ITL、TTFT 的取舍联系起来：较小预算可能减少 prefill 对 decode 的干扰，较大预算可能让输入更快处理完。

这些是调参方向，不能推广成必然规律。模型大小、硬件、实际长度、缓存命中和流量都会改变结果。

KV 不足时，抢占和重新计算还可能增加额外工作。系统没有立即失败，不代表尾延迟没有受损。

因此，看到 GPU 利用率更高时，还要检查用户首字、输出间隔、超时和重新计算情况。

## 长短请求怎样公平，才不会有人一直等？

FIFO、短请求优先、decode 优先与业务优先级各有取舍。

短请求优先可以改善部分交互体验，但长报告可能持续被推迟；只保护 decode，又可能让新请求迟迟无法开始。

应用可以按租户限制在途量，区分交互与批处理，并为等待较久的请求增加调度机会。这些是需要验证的策略，不是某个框架天然提供的保证。

还应有明确的过载出口：

- 队列长度和最长等待时间有界。
- 新请求超过准入能力时排队、拒绝或按产品规则降级。
- 重试服从剩余截止时间，避免所有客户端同时重新冲入。
- 用户取消后停止后续工作，并核查实际执行与资源释放。

取消了展示，不等于后端立即停止。缓存被归还给引擎池，也不代表进程显存数字马上下降，更不能据此直接判断泄漏。

## 吞吐、首字和有效吞吐，应该怎样分别报告？

先明确每个指标的测量对象：

| 指标             | 一种可采用的口径                             |
| ---------------- | -------------------------------------------- |
| 用户端 TTFT      | 请求发出到首个可展示文本到达                 |
| ITL              | 同一观测点相邻输出 Token 的间隔              |
| 平均 TPOT        | 有足够 Token 时间戳时，首末间隔除以间隔数    |
| Token 吞吐       | 明确观测窗口内生成的 Token 总量除以时间      |
| 请求吞吐         | 窗口内完成的请求数除以时间，并说明成功范围   |
| 有效吞吐 goodput | 单位时间内同时满足预设质量和时延条件的请求数 |

用户端 TTFT 包含应用、排队、计算和传输，不等于纯 prefill 耗时；引擎指标可能采用不同起止点。

SSE 分片也可能包含多个 Token，分片间隔不能直接当作 ITL。平均 TPOT 无法推出 p95 ITL。

报告成功时延时，还要同时给出请求总数、超时、拒绝和取消数量。否则，把慢请求全部超时踢掉，成功请求的均值反而可能更漂亮。

有效吞吐的时延与质量条件应提前确定，不能测完以后挑一个最有利的定义。

## 怎样设计对照，才能知道变化来自哪里？

固定硬件、模型修订、精度、引擎、缓存状态和采样配置，再一次改变一个主要变量。

问集应保留实际任务需要的输入输出长度分布：短查询、长输入短回答、短输入长回答和混合到达，分别观察。

最大输出参数只是上限，不能替代实际生成长度。重复同一句短问题得到的吞吐，也不能直接代表 A、B、C 混合负载。

可以依次规划以下比较：

1. 固定长度和流量，比较不同批处理预算。
2. 固定预算，改变到达率，观察等待队列和拒绝比例。
3. 加入长 prefill，检查已开始回答请求的 ITL。
4. 分开记录缓存冷热、抢占、重新计算和取消。
5. 在相同质量及时延条件下比较有效吞吐。

这套方案需要真正执行后才能判断收益。本文没有运行对照，也不提供任何硬件上的性能结论。

推测解码与阶段分离处理的是另外一些瓶颈，继续看[推测解码与 Prefill/Decode 分离](./ai-inference-speculation-disaggregation.html)。

## 小结

1. 连续批处理在允许的迭代边界调整成员，减少固定批次的空闲，不代表能任意打断内核。
2. 长 prefill 与持续 decode 会相互竞争，分块和优先级需要同时照顾首字及输出间隔。
3. 序列数、Token 预算、上下文上限和 KV 容量共同约束并发，还要考虑后续生成。
4. 大批次和高利用率不自动意味着更好体验，抢占、重算、排队与公平性都需要观察。
5. 分开报告 TTFT、ITL、吞吐和有效吞吐，保留失败与超时，用固定条件对照调度收益。
