# RAG 答错了，怎么区分召回、排序和生成问题？

> 沿着证据进入候选、进入上下文、被答案引用的路径查，才能知道哪一步需要修改。

## 工单状态查对了，升级建议为什么仍然错？

假设用户询问自己的工单 T-1048 能否升级处理，工具返回当前状态 `WAITING_VENDOR`。
助手还要对照普通升级规则 `policy-v3` 和供应商等待例外 `exception-v2`，才能解释适用条件。
这两份资料及下文的规则标识都是教学假设。

如果助手只找到普通规则，可能漏掉例外，给出过早升级的建议。
最终回答看起来相同，证据实际可能在不同位置丢失。

| 观察到的证据                     | 应优先检查的位置                   |
| -------------------------------- | ---------------------------------- |
| 授权语料里没有有效规则           | 原文、解析、索引发布与文档权限     |
| 规则已入库，但不在候选中         | 查询表达、过滤条件、召回与近似索引 |
| 规则在候选中，但重排靠后         | 融合、重排模型和候选截断           |
| 重排靠前，最终上下文却没有       | 去重、合并、压缩和 Token 裁剪      |
| 上下文含完整规则，回答仍错       | 生成约束、适用条件理解与引用       |
| 当前身份没有充分证据，仍给出结论 | 拒答或追问的判断与验收规则         |

内部诊断还要区分“原文不存在”和“当前用户无权访问”。
用户侧按访问策略回答，不能借一次排障暴露其他租户的文档内容。

## 为什么先固定语料和问题，再调整检索参数？

准备一组由业务人员复核的问题，每条保存原问题、可信身份范围、数据观测时间、预期结论和必要证据 ID。
还要记录语料快照、文档版本、解析与切分规则、embedding、索引、重排及生成配置。
否则同一天修改文档、切分和模型后，分数变化无法归因。

黄金证据由原文与业务要求确定，不能直接把本次检索结果当作标注。
T-1048 的规则问答需要两份证据，召回其中一份只能说明部分事实已找到。
若多份等效材料都能支撑答案，可以标注可接受的证据集合，避免错误惩罚合法答案。

把“应当拒答”的问题单独保留，记录缺少哪类证据或权限。
这一类样本不适合硬算一个分母为零的证据召回率，而应检查是否给出无依据结论。
调参集和最终验收集也要分开，防止只记住已见问题的措辞。

## BM25、向量和 RRF 分别帮助定位什么？

工单编号、状态枚举和产品版本容易依赖精确词匹配，BM25 可以作为关键词基线。
“供应商还没回复”和“等待外部响应”这类表达差异，适合检查向量召回是否覆盖。
两路应采用一致的身份与版本约束，再比较各自找到了哪些必要证据。

RRF 按各路名次累计 `1 / (c + rank)`，名次从 1 开始。
它无需直接相加 BM25 分数和向量相似度，常数 `c` 会影响靠后名次的相对贡献。
下面采用等权两路、`c = 60` 的教学配置，实际收益与候选窗口仍需用业务问集测量。

还应检查近似检索是否漏候选。
pgvector 的近似索引可能先扫描候选再应用过滤，即使 SQL 有 `WHERE`，结果数量也可能不足。
在相同授权语料的有界样本中对照精确距离检索，可以帮助区分近似扫描损失和 embedding 匹配问题。
精确近邻只保证距离排序的基准，业务相关性仍由黄金证据判断。

## Hit@K 命中了，为什么 Recall@K 还不够？

设必要证据为 `policy-v3`、`exception-v2`，前两条结果为 `policy-v3`、`faq-v1`。
单题 Hit@2 为 1，因为至少找到了一份必要证据。
单题 Recall@2 为 `1 / 2 = 0.5`，尚未找到例外规则。
在多题上汇总时，平均 Hit@K 才成为命中率，不能把“命中过”当成“证据完整”。

下面的代码可独立交给 Node 执行，输入已经按证据 ID 去重并限制在可访问集合中。
这个示例只验证计分与融合，不执行真实检索。

```javascript
function metrics(gold, retrieved, k) {
  const expected = new Set(gold);
  if (!expected.size) throw new Error("无黄金证据的题目另评拒答");
  const top = new Set(retrieved.slice(0, k));
  const matched = [...expected].filter((id) => top.has(id)).length;
  return { hit: Number(matched > 0), recall: matched / expected.size };
}

function rrf(rankings, c = 60) {
  const scores = new Map();
  for (const ranking of rankings) {
    [...new Set(ranking)].forEach((id, index) => {
      scores.set(id, (scores.get(id) ?? 0) + 1 / (c + index + 1));
    });
  }
  return [...scores].sort((a, b) => b[1] - a[1] || a[0].localeCompare(b[0]));
}

const gold = ["policy-v3", "exception-v2"];
const keyword = ["policy-v3", "faq-v1"];
const vector = ["exception-v2", "policy-v3"];
console.log(metrics(gold, keyword, 2));
console.log(rrf([keyword, vector]).map(([id]) => id));
```

第一行得到 `{ hit: 1, recall: 0.5 }`，融合后顺序为 `policy-v3`、`exception-v2`、`faq-v1`。
这说明本例两路互补，不能据此推导所有查询都需要混合检索。
记录粗召回、重排和最终上下文的必要证据覆盖率，才能看到证据在哪一阶段消失。

## 怎样证明错误发生在排序、裁剪还是生成？

给每份证据保留稳定标识、源版本和必要位置，追踪候选排名、融合排名、重排排名、入上下文状态及被裁原因。
若 `exception-v2` 从未进入候选，先检查入库和召回。
若它在候选中而排名落后，再检查重排输入、语言适配和候选窗口。

重排只会重新评价现有候选，无法生成候选池中缺失的例外条款。
若它已经排到前面却没进入模型请求，应检查父子块合并、重复判断和预算分配。
压缩后也要核对原文的限制条件是否仍在，仅保留“允许升级”会改变规则含义。

可以另做一组黄金证据注入实验，直接把人工确认的完整证据交给生成环节。
固定问题、模型与生成配置，检查此时是否仍误读条件或引用错误，这常被称为 oracle 对照。
移除其他候选同时改变了噪声和长度，一次答对只能帮助缩小范围，仍需逐步对照原上下文。
若原文缺失、互相冲突或不适用于当前版本，应明确不确定性，不能补造所谓黄金答案。

关于规则更新和撤权后的旧证据，继续看[知识库索引与权限生命周期](./ai-rag-index-lifecycle.html)。

## 修复之后，怎样避免只对这一个问题有效？

按精确编号、同义改写、跨文档条件、历史版本、权限不足和应拒答问题分组回放。
每组同时记录问题数量、必要证据覆盖、答案依据和引用准确性，检查提升是否只来自某一类问题。
生成存在波动，重要问题需要多次运行并保留各次结果。

还要测粗召回、重排和生成的耗时、端到端 p95、上下文 Token 与单次成本。
在相同语料、缓存和并发条件下比较方案，扩大候选窗口带来的覆盖收益才有可比的代价。
这些指标的实际值必须来自测量，不能照搬其他模型或文档集的提升比例。

业务事实、权限与引用可以优先用确定性检查验收，开放表达质量再用人工校准过的评分器辅助。
把每次确认的失败样本纳入回归集，具体验收设计见[Agent 评测](./ai-agent-evaluation.html)。

## 小结

1. 先固定授权语料、问题和必要证据，再沿候选、排名、上下文和答案逐段定位。
2. BM25、向量和融合各有适用条件，重排不能补回候选中不存在的事实。
3. Hit@K 衡量是否命中，Recall@K 衡量必要证据的覆盖比例，回答复杂规则需要检查完整性。
4. 黄金证据对照帮助区分供给与生成问题，裁剪、噪声和版本变化也要分别控制。
5. 回归要按问法和风险分组，同时观察证据、答案、延迟与成本，并验证无证据时的拒答。
