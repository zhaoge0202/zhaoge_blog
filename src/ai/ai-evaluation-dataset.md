# AI 评测集怎样保存证据、权限和状态，避免数据泄漏？

> 一条评测用例不仅要保存问题，还要冻结影响答案的证据、身份、初始状态和判据，并让被测系统与评分器看到各自该看的内容。

## 昨天能答对的同一道题，今天为什么不能直接比较？

假设客服问：“T-1048 现在为什么还不能升级？”昨天工单缺少供应商反馈，今天材料已经补齐；昨天政策为第 12 版，今天第 13 版又增加了确认条件。

如果只保存问题与一段参考答案，两次输出不同，并不说明模型退步。真实工单、政策版本、权限和观察时间都可能已经改变。

所以，评测数据集应描述一项可重建的任务；运行记录则描述某个应用版本在该任务上的一次尝试。两者分开，才能知道变化来自模型、应用、数据还是执行环境。

本文只设计数据结构和评测流程，示例均为教学构造，没有创建样例工程、运行评测或调用模型。发布门槛与统计判断见[CI 评测准入](./ai-eval-ci-release-gates.html)。

## 用例、运行记录、评分结果为什么要分开？

| 对象       | 需要回答什么               | 典型内容                                 |
| ---------- | -------------------------- | ---------------------------------------- |
| 用例 case  | 要解决什么，怎样才算完成？ | 输入、身份、环境引用、预期结果与禁止行为 |
| 尝试 trial | 哪套系统实际做了什么？     | 配置版本、工具轨迹、终态、用量与错误     |
| 评分 grade | 根据哪版判据作出什么判断？ | 规则结果、语义评分、依据与无法判断项     |

同一用例可以运行多次，每次有不同的 `trialId`。评分器修改后，也可以重新解释已保存的输出，但这不等于重新执行了任务。

不要把 `expectedSuccess: true` 当成被测应用返回的真实状态。预期是评分依据，实际结果必须从本次运行的环境中取得。

任务成功还应允许多种合法路径。例如，已有充分证据时直接回答与补一次获准查询后回答都可能正确。只有业务确实要求的步骤，才应规定先后关系；不必强求完整轨迹与一条参考轨迹逐项一致。

## 一条工单用例，最少应该绑定哪些材料？

先固定一个查询任务：north 租户的 alice 查询本人 T-1048。它当前为 `WAITING_VENDOR`，政策第 13 版要求补充供应商反馈，用户没有要求提交升级。

可以用下面的 **JSON 设计示意**组织用例，字段不是某个评测平台的标准格式：

```json
{
  "caseId": "ticket-query-001",
  "sourceGroup": "ticket-family-1048",
  "split": "regression",
  "input": {
    "question": "T-1048 为什么还不能升级？",
    "callerFixture": "north-alice-support"
  },
  "environment": {
    "businessFixture": "tickets-v3",
    "corpusRelease": "policy-release-13",
    "authorizationFixture": "acl-v5",
    "clock": "2026-11-21T02:00:00Z",
    "toolScenario": "normal-read"
  },
  "oracle": {
    "requiredFacts": ["WAITING_VENDOR", "缺少供应商反馈"],
    "evidence": [{ "docId": "escalation-policy", "version": 13, "section": "4.2" }],
    "forbiddenEffects": ["any_business_write"],
    "requiredOutcome": "ANSWER_WITH_EVIDENCE"
  },
  "rubricVersion": "ticket-rubric-v2"
}
```

`callerFixture` 只是测试环境中指向身份材料的引用。执行器应通过被测系统规定的认证方式取得主体，不能让模型直接认领这个身份。

`oracle` 保存评分依据，**不能整体拼进模型上下文**。被测应用应通过自己的检索与工具取得允许看到的工单和政策；若直接给它黄金片段，就只能说明“给定证据后能否生成”，不能据此声称检索已经通过验证。

对照数据也要准备到位：另一个租户可以有同号工单，语料中可以有旧版条款和无权访问的正文。这样才能检查系统是否选对对象、版本与授权范围，而不是因为环境只剩正确答案而自然答对。

## 资料、权限和业务状态怎样保持可重建？

用例引用的每一份材料都要有清楚的版本边界：

- 语料保存文档标识、源版本、位置、内容摘要值及有效期；检索实验还要记录解析、切分、编码和索引配置。
- 权限材料保存主体、资源范围、策略版本，以及撤权等事件的发生时刻。
- 业务夹具保存工单初始值、唯一约束与必要关联记录，不能只记录最终答案。
- 时间相关任务保存时区、业务日历和观察时钟，避免“等待三天”随执行日期改变。
- 工具场景保存正常响应、故障触发条件和外部操作的可核查状态。

摘要值只能检查材料是否变化，不能代替材料本身。完整正文可以放在受控存储中，公开仓库只使用脱敏或合成内容，并保留对应引用。

撤权实验应在隔离环境里改变逻辑时间和授权状态，检查旧缓存、旧对话与引用读取是否仍受约束。恢复历史夹具并不意味着允许在真实系统恢复用户已经失去的权限。

## 评测题怎样切分，才不会只是把同一道题换个说法？

把“工单什么时候能升级”和“这单能不能升级处理”随机分到开发与测试两侧，看起来是两条记录，实际可能共享同一份原文、同一对象和同一错误模式。

应先定义分组依据，再切分数据：同一工单的派生题、同一政策的近重复版本、同一模板生成的问题，分别维护来源关系；根据要验证的泛化目标决定哪些关系必须留在同一组。

例如，要验证对新工单的适应能力，就按工单家族切分；要验证政策改版后的表现，就按版本与时间设计留出，并明确旧版资料允许在哪一侧出现。分组不是一个适用所有目标的固定键。

可以维护三类集合：

| 集合       | 主要用途                     | 维护边界                                         |
| ---------- | ---------------------------- | ------------------------------------------------ |
| 开发集     | 诊断问题、修改 Prompt 与流程 | 允许反复分析，但不能当最终泛化证明               |
| 回归集     | 检查已修复缺陷是否再现       | 每次加入前确认判据，持续执行会让它逐渐成为已知题 |
| 保留测试集 | 在方案冻结后估计未见样本表现 | 限制查看与调参使用，记录评估次数                 |

回归集很有价值，但团队长期围绕它优化后，高分不能直接代表未知问题也能解决。保留集一旦被反复用来挑方案，也会逐渐失去独立性，需要更换或另留新样本。

数据泄漏也不只发生在训练里。参考答案进入 Prompt、评分标准被写进工具结果、模型生成合成题时看过测试答案，都可能把评测变成答案复述。

## 黄金证据与评分标准，应该由谁确认？

用户点赞、客服采用、模型互相同意都可以提供线索，却不能直接当真值。用户可能没有发现漏掉的条件，客服也可能在使用前修改了回答。

对正常题，标注可接受结论、必要条件和支持它的证据集合；对无法作答题，标注缺少的事实、冲突来源或权限原因。答案不必逐字一致，但关键事实与限制要一致。

对重要或容易分歧的样本，可以让审核者独立判断，再记录分歧及裁定依据。若业务本身没有明确政策，先标成“尚不可用于自动评分”，不要强行给它一个漂亮的标准答案。

评分分两层：

1. 对对象归属、写入数量、引用版本、字段和数值等明确条件，用环境检查或规则判断。
2. 对解释是否清楚、必要条件是否表达完整等语义质量，用有证据的人工或经校准的模型评分辅助。

Judge 也需要版本和适用范围。先用人工确认样本检查假通过、假失败与位置偏差，不能因为输出了 JSON 分数就认为它是可靠的验证器。模型自评的边界见[幻觉与拒答](./ai-hallucination-abstention.html)。

## 一次尝试怎样从同样的起点开始？

```mermaid
flowchart LR
    A[载入用例与版本清单] --> B[重建隔离状态]
    B --> C[通过认证入口执行应用]
    C --> D[保存轨迹与实际终态]
    D --> E[按判据评分]
    E --> F[汇总并检查环境清理]
```

并行用例需要独立命名空间或等价隔离，不能共享同一条会被修改的工单。一次尝试失败后重新运行，也要先恢复初始状态，避免前一次已经写入的结果使后一次碰巧成功。

业务操作号需要同时处理两个边界：**同一次尝试内的业务重试保持原操作号；不同尝试隔离操作空间**。否则幂等记录可能让新尝试跳过原本要测的创建逻辑。

写工具连接隔离环境或受控替身；外部通知也由测试接收端接管。记录下完整轨迹，不代表应该把生产写请求重新发一遍。各层测试能证明什么，见[Java Agent 测试分层](./ai-agent-java-evaluation.html)。

最后区分业务失败与评测环境失败。例如，预设下游超时后应用重复写入，是待测缺陷；评测机断网导致夹具未加载，则是运行基础设施问题。两者都应报告，但修复方向不同。

## 失败样本怎样回流，才能扩大覆盖而不污染结论？

可以沿这条链路处理新问题：

```text
采样或投诉线索
→ 脱敏与使用范围检查
→ 确认失败原因及业务判据
→ 按来源关系去重、归组
→ 加入开发或回归集
→ 更新数据版本与变更说明
```

不要把每一次失败输出自动写成标准答案，也不要把一条投诉的十种改写当作十种独立风险。保留来源关联，汇总时才不会夸大样本量。

每份发布报告至少记录用例与材料版本、应用和模型配置、评分器版本、题目及尝试数量、各组通过情况、环境失败和缺记录情况。成功样本的延迟与费用之外，还要报告失败尝试及用量未知项。

固定“100 题”或“正常题占一半”只能作为教学规划，不能证明评测充分。样本规模与分层应围绕业务分布、关键风险和期望判断精度决定，重复运行同一道题也不能替代更多独立任务。

## 小结

1. 用例定义任务与判据，尝试保存实际行为，评分记录判断依据，三者应分别版本化。
2. 证据、身份、业务初态、时间和工具场景共同决定答案，只存问题与参考答案无法可靠复现。
3. 黄金证据与答案留给评分器，模型通过被测检索和工具取得材料，避免把评分依据泄漏给应用。
4. 按来源家族与泛化目标切分，回归题和保留测试题承担不同责任，失败回流不能反复污染保留集。
5. 每次尝试隔离并重置环境，区分业务失败、环境失败和记录缺失，用业务终态验证真实结果。
