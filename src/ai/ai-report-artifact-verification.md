# AI 生成报告，怎样保证数字、引用和文件版本一致？

> 先冻结数据与计算结果，再让模型解读；最终文件必须能追到同一份事实、引用和产物版本。

## 报告看起来完整，为什么数字仍可能对不上？

假设系统为财务人员生成月度费用报告。正文写“本月费用 17.50 元”，表格却使用上一次查询的金额，饼图又来自另一批数据。

单独看，每个数字都可能计算正确，但它们不属于同一份报告。用户下载文件时，还可能拿到重试之前的旧版本。

问题涉及数据、模型和文件三个层次：计算用了什么记录，文字怎样引用结果，最终交付了哪些字节。只检查模型是否生成完整文本，无法覆盖整条链路。

本文使用合成数据讲解报告设计，没有查询数据库、调用模型或生成真实文件。异步执行机制见[任务流水线](./ai-async-task-pipeline.html)。

## 计算之前，先固定哪些口径？

假设某月的可见记录只有两笔同币种费用：

| 记录 | 分类 | 金额     |
| ---- | ---- | -------- |
| E-01 | 差旅 | 1,250 分 |
| E-02 | 采购 | 500 分   |

总费用为 1,750 分，展示为 17.50 元。差旅占比为 `1250 / 1750`，按一位小数展示约为 71.4%。

这些数字成立，需要先明确记录归属、币种、统计时间窗、时区、观察截止和舍入规则。不同币种不能直接相加，创建时间与入账时间也不能随意互换。

授权过滤必须发生在聚合之前。某用户只能看到这两笔记录，就不能先计算全公司的费用，再从报告中隐藏其他部门名称。

月结后的补录和更正也会改变结果。报告应引用可重建的数据批次或历史快照，而不只是保存“查询时间”。

指标口径与查询层的具体设计，见[自然语言查数](./ai-natural-language-analytics.html)。

## 为什么应该先生成事实清单，再生成解释？

让模型直接阅读大量原始记录并计算总额，会把理解、计算和表达混在一起。更容易核对的方式是由代码或结构化引擎计算，再向模型提供受控事实。

每项事实可以保留以下字段：

| 字段                       | 要说明什么                       |
| -------------------------- | -------------------------------- |
| `id`                       | 后续文字、表格和图表引用哪项事实 |
| `value`、`unit`            | 原始值及单位                     |
| `precision`                | 存储精度与展示规则               |
| `denominator`              | 比例使用的分母，非比例可为空     |
| `observedCutoff`           | 统计看到了哪个时刻               |
| `queryId`、`sourceVersion` | 怎样回查计算与数据版本           |
| `authorizationScope`       | 计算时采用的可信可见范围         |

例如，费用总额对应 `F-TOTAL`，差旅金额对应 `F-TRAVEL`，差旅占比对应 `F-TRAVEL-SHARE`。

占比事实同时关联分子和分母。分母为零时，应按指标约定显示“无可计算占比”等结果，不能让模型自行填成 0% 或 100%。

金额可以以整数分保存，展示时确定性转换成元。事实清单要区分原始精度与展示小数位，避免把“保留两位小数”误解成先对每条记录随意取整。

## 模型负责解读以后，怎样检查它没有改写数字？

可以要求模型围绕事实编号生成解释结构：

```json
{
  "sections": [
    {
      "title": "费用概览",
      "claims": [
        {
          "factIds": ["F-TOTAL", "F-TRAVEL-SHARE"],
          "text": "差旅费用占本期可见费用的主要部分。"
        }
      ]
    }
  ]
}
```

这是应用自定义的教学格式。渲染层从事实清单取得金额和占比，生成“17.50 元”“71.4%”等展示，不必让模型再次抄写每个数字。

模型提出新的计算结论时，应转交允许的计算逻辑核验。例如，“比上月增长两倍”需要可比的上月数据、增长定义和对应分母，不能只因语句通顺就采用。

检查报告中是否出现“17.50”，也不足以证明数值正确。它可能同时写着“差旅费为 17.50 元”，把总费用放到了错误对象上。

因此，核对对象应是完整断言：哪项指标、哪个范围、什么时间、什么单位、数值与依据是否相符。没有支持的因果解释，例如“上涨由差旅政策导致”，同样不能因为数字正确就放行。

## 引用编号存在，为什么还要检查它支持什么？

引用检查可以分成两层：

1. 引用是否能解析到允许访问的确定来源与版本。
2. 来源内容是否确实支持报告中的那条结论。

费用总额可以引用查询结果，报销规则可以引用政策段落。两种来源证明的内容不同：政策规定上限，不代表实际支出已经达到上限。

引用还需要保留位置。表格可以定位到工作表与区域，文档可以定位到页码与段落，结构化数据则关联查询和批次。

不能让模型编出一个可点击链接，再把“链接可以打开”当成证据。引文中的外部地址也不应自动触发下载、命令执行或新的数据授权。

表格、单位与来源关系的处理，见[表格证据](./ai-rag-table-evidence.html)。

## 正文、表格与图表，怎样避免混用不同批次？

报告应有一份版本清单，将事实、生成和渲染关联起来：

```text
reportId / reportRevision
数据快照与 factRelease
查询、指标和计算规则版本
授权作用域与必要的来源依赖
模型、Prompt 和输出 Schema 版本
模板、图表配置与渲染器版本
生成尝试标识
产物地址、字节摘要与校验状态
```

这些名称是设计示意，不是某个文档标准。

正文、图表、表格和脚注都使用同一个 `factRelease`。如果补写一个章节，需要先判断是否继续使用原快照；改用新快照时，应重新核对其他章节，不能悄悄拼接两个统计口径。

图表数据与刻度由计算和渲染层生成。模型可以建议图表形式，但不能另造一份数据，再让它与表格各自解释。

文件摘要用于确认下载内容对应哪些字节，不能证明计算、引用或版式正确。两个错误报告也可以各自拥有完全有效的摘要值。

## “生成完成”“校验通过”和“发布”，为什么要分开？

可以用下面的流程划分职责：

```mermaid
flowchart LR
    A[冻结事实与来源] --> B[生成解释草稿]
    B --> C[核对数字与引用]
    C --> D[渲染并检查文件]
    D --> E[按业务策略审批]
    E --> F[发布确定版本]
```

数字核验通过，只说明对应事实检查成立。文件仍可能缺页、表格越界、图例错误，或者正文与附录使用不同版本。

视觉检查应针对最终产物，覆盖分页、字体、表格、图表、脚注与引用位置。本篇只设计检查内容，没有进行渲染或版式验证。

人工审批是否需要，由业务发布策略决定；需要时，审批绑定确定的报告版本。模型自称“已审核”不能代替真实审批记录。

生成请求也不自动授权向其他人发送文件。对外发布和通知应经过相应的业务入口。

## 产物已经写好，数据库更新失败怎么办？

可以先保存不可变的草稿对象，再经过核验更新发布指针。每次尝试使用独立版本，不覆盖所有人都在下载的固定文件名。

发布时，在本地事务中检查当前报告版本、校验及审批状态，再条件更新发布指针，并追加发布事件。后续通知可以通过可靠投递处理，不能假定数据库与外部发送天然原子。

对象写入成功、数据库提交失败时，可能留下未被引用的草稿。它应进入受控核查与清理流程，不能因为文件存在就自动成为当前正式报告。

数据库已经发布后，下载入口应返回指针指向的确定版本。旧尝试迟到，只能形成自己的记录，不能无条件覆盖新版本的发布结果。

整条流程应能回答：草稿在哪里、哪些检查尚未完成、当前公开的是哪版，以及发布记录对应哪个产物。

## 撤权以后，已经生成的报告还能下载吗？

报告可能包含多份来源的派生内容。生成时有权访问，不代表下载时权限仍然有效。

发布与下载应按当前策略复核依赖范围。无法确认来源或授权时，不能只因报告保存在对象存储中就继续放行。

预签名 URL 也不是即时撤权机制。已发出的链接可能在有效期内继续使用；需要更严格控制时，可采用较短有效期或经过授权检查的下载入口，并明确实际交付边界。

已下载的内容也不会因服务端撤权自动从接收者设备上消失。权限、数据留存与派生内容的类似问题，见[企业知识库设计](./ai-enterprise-knowledge-base-design.html)。

## 输出成文件时，还有哪些内容需要当作数据处理？

模型生成的文字不能直接作为 HTML 模板代码执行，应按目标格式正确转义。

导出 CSV 或表格时，某些以 `=`、`+`、`-`、`@` 开头的文本可能被目标软件解释为公式。应区分真实数值、受允许的公式与普通文本，按导出规则处理，不能一律篡改合法的负金额。

报告里的链接和附件也应受控解析。文档可以引用资料，但不能因为模型写出地址，就自动取得抓取任意网络资源的能力。

这些处理保护的是文件生成和打开过程，仍然不能代替数字与事实核验。

## 应该怎样设计故障验收？

| 教学场景                       | 应核对的结果           |
| ------------------------------ | ---------------------- |
| 生成截断，缺少必要章节         | 不标记为完整报告       |
| 把分当成元，或占比使用错误分母 | 数值与单位检查失败     |
| 引用存在但不支持结论           | 保留对应事实错误       |
| 重试章节使用了新数据快照       | 不静默混入旧报告       |
| 旧尝试迟到，产物写入成功       | 不覆盖当前发布指针     |
| 发布前撤销来源权限             | 按当前策略阻止继续交付 |
| 文件摘要正确，但表格缺页       | 仍不视为版式检查通过   |

每项检查都要说明输入、判据与证明范围。事实检查、模型效果、对象存储一致性和最终排版分别验证，不能用“文件能下载”概括全部完成。

## 小结

1. 授权范围、指标、时间和快照先冻结，金额与比例由确定性计算产生，模型负责受证据约束的解读。
2. 数字核验要对应完整断言，引用可解析与来源支持结论分别检查。
3. 正文、表格、图表和脚注绑定同一事实版本，补写或重试不能静默混用批次。
4. 草稿不可变，校验、审批与发布分别记录，发布指针通过受控更新绑定确定产物。
5. 摘要值不证明事实或版式正确，下载仍需当前授权，已交付内容不能靠撤权自动收回。
