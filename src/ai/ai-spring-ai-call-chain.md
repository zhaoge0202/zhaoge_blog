# Spring AI 的请求怎样经过 Advisor、记忆和工具调用？

> 沿请求进入、工具往返和响应返回三条路径看清框架行为，才能把身份、记忆、预算与观测放到真正生效的位置。

## 一句工单查询，为什么可能调用模型好几次？

alice 问：“T-1048 还在等什么，按当前政策能升级吗？”

助手需要读取工单状态、取得政策证据，再解释适用条件。模型可能先提出查询工具，取得 `WAITING_VENDOR` 后继续生成回答。因此，一次 `ChatClient` 调用不一定只对应一次供应商请求。

本文按 2026-11-21 核对的 Spring AI `1.1` 系列文档讲解。这些页面随补丁版本更新，具体项目仍要锁定 BOM、Spring Boot 和供应商适配版本，不能把页面上的全部能力视为所有 `1.1` 版本共同支持。

下面的顺序、代码和验收均为教学设计，未启动项目或执行联调。接入选型见[Java 接入方式](./ai-java-integration-stack.html)。

## 请求进入 ChatClient 之前，先确定什么？

先核实调用者和会话，再装配模型请求。

浏览器可以提供会话定位信息，但服务端必须检查该会话是否属于当前用户与租户。拿到一个 `conversationId`，不等于获得读取其中历史的权限。

随后限定工单范围、允许的工具及任务预算。检索器和工具执行端仍要校验实际对象，不能只靠入口检查一次。

下面是省略类型和授权实现的调用示意：

```java
String answer = chatClient.prompt()
        .user(question)
        .advisors(a -> a.param(
                ChatMemory.CONVERSATION_ID,
                authorizedConversationId))
        .toolContext(Map.of("caller", authenticatedCaller))
        .call()
        .content();
```

`authorizedConversationId` 表示已检查归属的会话，`authenticatedCaller` 表示认证层核实的主体。变量名只是提醒，实际实现必须提供这些保证。

## Advisor 为什么请求正着走，响应反着走？

`ChatClient` 将调用整理为 `ChatClientRequest`，Advisor 可以检查或修改请求、调用后续链，也可以处理返回结果。同步与流式分别使用对应的 Advisor 接口。

所读文档中，顺序由 `getOrder()` 决定：**数值越小，越先处理请求，越后处理响应**。相同顺序值不保证相对次序，不能仅凭 `.defaultAdvisors(...)` 的书写顺序推断运行顺序。

假设三项教学 Advisor 的 order 分别为 10、20、30：

```text
请求：检查 10 → 记忆 20 → 检索 30 → ChatModel
响应：检查 10 ← 记忆 20 ← 检索 30 ← ChatModel
```

这是一种包裹关系。order 为 10 的组件最先进入，却要等里面的处理返回之后，才能完成自己的响应处理。

因此，“日志放最前面”可能只能看到尚未加入历史和证据的输入；“脱敏放最外层”则可能在返回时最后执行，内层持久化此前已经保存了原文。

没有适合所有应用的固定排序。应检查每个组件读什么、写什么，以及响应阶段是否保存消息，再决定位置。

## 记忆和检索加入后，预算应该在哪里核算？

`MessageChatMemoryAdvisor` 可以取得当前会话的消息并加入请求；RAG Advisor 再按配置检索资料、增强上下文。实际组件如何组合，取决于项目采用的链路。

如果只对最初一句问题估算 Token，历史、检索片段和工具 Schema 都可能漏掉。预算检查需要覆盖最终交给模型的完整内容，并考虑适配器包装与输出预留。

工具执行后，结果又会增加下一轮输入。不能把第一次通过预算检查，理解为后续所有轮次都已获准。

可以分别记录：

| 位置           | 值得观察的内容                         |
| -------------- | -------------------------------------- |
| 进入应用       | 主体、会话、目标与任务预算             |
| 上下文装配后   | 历史、证据版本及输入估算               |
| 每次供应商请求 | 模型、调用标识、实际用量与结束原因     |
| 任务结束       | 总调用数、总用量、业务终态与未完成事项 |

具体估算与多轮约束见[推理模型预算](./ai-reasoning-model-budget.html)。

## Advisor 短路后，哪些检查仍然不能省？

Advisor 可以不调用后续链，直接提供响应。例如，应用可能通过结果缓存返回已有答案。

这时不能继续记录成“完成了一次真实模型生成”。应区分缓存命中、供应商调用和最终交付。

缓存也需要核对当前主体、证据版本与有效期。alice 失去某份政策的访问权后，旧答案不能因为位于缓存中就继续交付。

短路还会改变后续组件是否执行。如果费用记录、审计或记忆更新依赖被跳过的组件，行为就可能与普通路径不同。应逐项定义短路路径需要保留哪些记录，而不是认为挂在链上的组件一定都会运行。

## ChatMemory 为什么不能代替完整历史和审计？

这三类信息承担不同职责：

| 信息             | 主要用途                       |
| ---------------- | ------------------------------ |
| ChatMemory       | 为后续模型调用保留适当上下文   |
| 完整会话历史     | 回看用户与助手的完整交流       |
| 运行审计与 Trace | 核查模型、工具、权限和业务操作 |

窗口记忆可能移除旧消息，因此不能承担完整历史留存。所读文档也提示，默认内部工具执行期间的中间消息存在保存限制，不能据最终记忆内容推导全部工具轨迹。

同次核对的 `1.1` 系列页面要求为记忆 Advisor 显式提供 `ChatMemory.CONVERSATION_ID`。项目应按锁定补丁版本核对参数要求，避免沿用旧示例中对默认会话的假设。

同一个会话同时收到两个请求时，还可能出现历史交错或更新覆盖。可以按会话串行推进，或者采用状态版本检查与明确的消息合并规则。仓储支持并发访问，不等于多轮对话已经具备正确的并发语义。

跨会话记忆的来源与撤销，另见[Agent 记忆](./ai-agent-memory.html)。

## 工具循环在 ChatModel 里面，还是在 Advisor 里面？

Spring AI 文档介绍了几种控制方式，需要先选择执行责任。

**框架在模型内部管理。** `ChatModel` 取得工具调用后，通过 `ToolCallingManager` 找到并执行相应 `ToolCallback`，回填结果，再请求模型。外层最终拿到的可能已经是完整回答。

```text
ChatClient 与外层 Advisor
  → ChatModel
      → 模型请求
      → 工具执行
      → 后续模型请求
  ← 最终响应
```

内部多次请求不一定重新经过全部外层 Advisor。因此，一条外层日志不能证明已经记录每次工具往返和供应商用量。

**由 ToolCallAdvisor 管理。** 所读工具文档还提供 Advisor 层工具循环：它关闭模型内部执行，将迭代放入相应链路。其他 Advisor 能观察哪些阶段，与它们的位置和实际迭代方式有关，仍需按版本确认。

**由应用自行管理。** 在支持的调用选项中关闭内部工具执行，应用检查工具调用、执行、回填并继续请求。此时应用也要承担轮次、预算、取消和错误分类。

三种方式不能不加区分地叠加。框架已经完成工具执行后，外层再根据同一响应执行一次，就可能造成重复操作。

## ToolContext 不发送给模型，为什么仍要检查来源？

工具参数由模型提出，`ToolContext` 则可以携带应用提供的额外执行信息。所读文档说明，这部分上下文不直接发送给模型。

但这不是自动的身份认证机制。把浏览器提交的租户 Map 原样塞进去，仍然是在信任未经核实的数据。

正确做法是由可信服务端构造主体范围，工具内部据此校验资源，再将裁剪后的业务结果返回。若应用主动把 `ToolContext` 拼进 Prompt 或全量日志，原有的不发送边界也会被破坏。

工具调用标识、执行防重和审批继续沿用[知识与工具调用](./ai-agent-java-knowledge-tools.html)及[审批恢复](./ai-agent-java-approval-recovery.html)中的规则，不能由框架类型代替。

## 流式调用时，为什么“拿到 Flux”还不代表完成？

响应式调用通常在订阅时执行。返回一个 `Flux`，不能据此判断供应商请求已经发出；对同一调用流多次订阅，也可能触发重复生成，具体取决于流及适配器的实现。

应用不应为了分别记录日志和向前端输出，就随意建立两个独立订阅。观测应接入同一受控消费链，并明确重试或重新订阅是否意味着新调用。

流中的文本分片、工具参数和最终消息也要区分。参数没有接收完整之前不能执行工具，部分正文不能作为完整答案进入后续记忆。

对于错误或取消，应明确记忆策略：是否保存带状态的草稿，哪些内容可以再次进入上下文，哪些仅保留在运行记录中。不能把半截回答当作已经完成的助手消息继续使用。

收到取消或 `doFinally` 的终止信号，只能说明本地链路发生了相应事件，不能证明供应商已停止生成、费用为零，或业务写入已经回滚。流式链路详见[SSE 与后端缓冲](./ai-streaming-sse-backend.html)。

## 怎样设计检查，确认调用链符合预期？

可以用可控模型与工具替身记录事件，设计以下判据：

- 三个不同 order 的 Advisor，应呈现预定的进入与返回顺序。
- 缓存短路时，不应出现供应商调用记录，但授权复核和交付审计仍应存在。
- 两个用户使用相似会话标识，也不能读到对方的记忆。
- 一次工具调用只由选定的执行路径处理，并保留可核对的调用标识。
- 流式异常、取消与重复订阅，应有明确记录，不把未完成回答记成成功。

真实模型的选工具效果、数据库持久化和进程恢复属于其他验证层，不能由内存中的事件顺序一并证明。这些只是验收设计，本文未执行相应检查。

## 小结

1. Advisor 按 order 从小到大处理请求，再反向处理响应，短路和同序值都会影响实际执行。
2. 历史、检索和工具结果都会改变模型输入，预算与观测需要覆盖每次实际调用。
3. ChatMemory 服务于上下文，不代替完整历史和审计；会话归属与并发更新由应用控制。
4. 模型内部、Advisor 和应用自管工具循环应明确选责，ToolContext 也必须来自可信来源。
5. 流式订阅、完成、取消和业务终态分别判断，部分消息与本地终止不自动代表完整交付。
