# 什么时候需要微调，Prompt、RAG 和微调怎么选？

> 先确认失败发生在证据、任务行为、输出契约还是业务执行，再用固定的验收集比较改进收益与维护成本。

## 工单助手答错了，为什么不能马上开始训练？

假设助手处理 alice 的工单 T-1048，真实状态为 `WAITING_VENDOR`。
一次回答引用旧政策，一次输出了非法分类，另一次正确解释了状态，却擅自提出升级请求。
这些失败分别涉及证据时效、输出契约和执行权限，修复位置并不相同。

先保留问题、可访问的证据、工具结果、模型版本与最终业务状态。
如果上下文根本没有新版政策，训练更好的措辞无法说明当前事实。
如果工具允许未经确认的写入，模型更常遵守提示也不能成为授权依据。

选型需要从可复现的失败样本出发。
RAG 的分段归因方法见[检索与生成排障](./ai-rag-retrieval-diagnosis.html)。

## Prompt、Schema、RAG 与微调分别改变什么？

Prompt 为本次调用提供任务、约束和示例。改变提示与上下文，不需要更新模型参数。
对少量稳定要求，先把输入、步骤和缺失信息的处理方式说清楚，便于快速迭代。

Schema 描述输出或工具参数的结构。
支持相应能力的 API 可以在生成阶段施加约束，后端仍需检查格式、业务含义和权限。
JSON 合法不表示工单号存在，更不表示属于当前用户。

RAG 在回答时取得外部证据，可以按身份、版本和相关性选择材料。
其收益取决于原文、解析、召回、上下文和生成共同工作，错误引用与越权仍需独立防护。

微调通过训练更新模型的部分或全部参数，改变后续输入对应的输出分布。
它可以改善任务行为、领域表达，也可能改变知识表现，不能限定成“只改说话风格”。
但参数中的知识没有天然的逐条来源和撤销入口，实时状态仍应从业务系统取得。

## 面对四种需求，可以怎样选择起点？

下面的需求和结果均为教学设计，不是已执行的模型比较。

| 需求                             | 先建立的方案                                 | 何时再评估微调                               | 必须保留的边界                       |
| -------------------------------- | -------------------------------------------- | -------------------------------------------- | ------------------------------------ |
| 工单分类字段偶尔缺失或枚举错误   | 明确分类说明，使用适用的结构约束和服务端校验 | 格式合法后，分类语义仍在固定任务集持续失败   | 非法结果不能直接落库                 |
| 查询当前状态与刚发布的处理规则   | 业务查询工具，加按版本检索的政策证据         | 证据已充分提供，领域任务行为仍有可重复缺陷   | 当前状态、权限和引用仍由外部系统核实 |
| 大量工单需要稳定的分诊与摘要     | 测试基础模型、提示、少量示例和证据供给       | 有质量合格的任务样本，独立验证能比较行为收益 | 保留边界题、拒答和通用能力回归       |
| 用户要求未经确认直接创建升级工单 | 服务端审批、对象授权与状态机                 | 训练不是替代这些控制的方案                   | 未获可信授权时，写入次数必须为零     |

一种系统可以同时使用几种机制。
例如微调模型学习分诊方式，RAG 提供当前政策，查询工具取得工单状态，业务服务负责执行升级。
组合方案也增加维护面，应分别验证每个组件的作用，再保留确有收益的部分。

## SFT、LoRA 和偏好优化，是三个互斥选项吗？

SFT 是监督微调任务，使用输入与目标输出等监督信息，让模型学习目标序列。
它关心用什么样本和训练目标改变行为。
对话模板、损失覆盖哪些 Token 等细节，会影响实际学到的内容。

LoRA 是一种参数适配方法。
它冻结预训练权重，并学习低秩更新矩阵，减少需要训练和保存的参数量。
因此可以用 LoRA 完成 SFT，也可以针对适用任务采用全参数更新。
二者并不处在同一个选择维度。

偏好优化另有目标与数据要求，例如 DPO 利用偏好对学习输出倾向。
已有一批输入和合格答案，不代表同时具备可靠的偏好标注。
选训练任务之前，应先确认目标和数据，而非只根据方法名字选工具。

LoRA 减少可训练参数，并不消除基础模型、激活、优化器与评测的资源需求。
是否合并适配权重、怎样加载多个适配器，也会影响部署管理与推理开销。
原论文中的参数和显存收益属于其特定模型与实验，不能直接作为项目预算。

## 什么证据能说明现在值得投入微调？

先冻结一个可重复的基线，包括模型、提示词、Schema、检索配置、工具定义和评测数据。
区分知识供给错误、条件理解错误、分类错误与执行违规，再确定本轮要改善哪一类。

接着比较成本更低或维护更简单的改动。
补全规则、加入合格示例、修复检索、选择另一个基础模型，都可能改变结果。
如果训练候选无法优于这些基线，就不应仅凭训练损失下降决定上线。

独立验证集应覆盖不同表述、产品版本、长尾任务和应该拒绝的请求。
同一工单的改写或近重复记录不能分别放入训练和验收两边，让模型靠记忆获得高分。
具体的数据划分和训练验收见[监督数据与 LoRA 评测](./ai-fine-tuning-data-evaluation.html)。

在看见结果前确定通过条件。
可以要求任务通过率改善，同时约束无依据结论、越权、重复副作用、时延和单次成本。
模型更会生成符合风格的解释，也不能抵消业务硬约束失败，验收方法见[Agent 评测](./ai-agent-evaluation.html)。

## 怎样算训练之外的长期成本？

预算应包含数据清洗与标注、训练尝试、独立评测、模型制品、推理部署和持续回归。
保留 RAG 时，索引更新与检索成本也仍然存在。
不能只比较一次训练账单与某个月的输入 Token 费用。

质量收益和推理费用可能一起变化。
更短的提示、较小的模型或更少的重试，有时能降低单次任务成本，但要由同一任务分布的测量证明。
LoRA 文件较小，也不保证线上每次请求都更快。

基础模型升级、政策变更和工具 Schema 调整都会触发回归。
模型、Tokenizer、对话模板、适配器和训练数据版本应能对应，部署需要可验证的回退入口。
还要检查新任务上的过拟合、旧能力退化以及错误拒答，不能只保存最有利的分数。

## 哪些情况下，应该暂缓训练？

来源或使用权限不清的聊天记录、密钥、个人敏感信息，不能因为“有很多数据”就直接放进训练集。
日志里的模型回答也不天然是正确标签，需要重新核验事实与行为。

频繁变化的工单状态、逐用户变化的权限和需要立即撤销的信息，更适合保留在可查询和可控制的外部系统。
删除一条训练样本或原文，不会自动撤销既有模型参数学到的内容。
若没有能力处理数据与模型版本的后续生命周期，应先解决治理条件。

缺少独立验收集、基线尚未查明、样本只覆盖成功案例，都会让训练结果难以判断。
此时先补数据、失败归因和验收，训练才可能成为一个可比较的工程选择。

## 小结

1. 先定位证据、行为、结构和执行环节，再决定改提示、检索、模型还是业务代码。
2. 微调能改变行为和知识表现，但不天然提供实时事实、引用、权限或事务保证。
3. SFT 描述监督训练任务，LoRA 描述参数适配方法，可以组合使用。
4. 投入训练需要可靠样本、固定基线与独立验收，同时比较质量、风险、延迟和持有成本。
5. 数据权利、敏感信息、版本与回归条件不足时应暂缓训练，业务安全约束始终在服务端落实。
