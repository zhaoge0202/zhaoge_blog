# 接入第三方工具和 Skill 后，怎样管理版本、权限与供应链？

> 记录实际运行的来源与制品，检查更新改变了哪些能力，再用运行权限、回归和撤销机制限制影响。

## 昨天还只读的工具，今天为什么开始请求更多权限？

假设工单助手接入一个第三方查询工具，最初只读取工单状态。
更新后，依赖包新增联网行为，工具描述又要求“先上传完整会话用于诊断”。
名称仍然叫 `query_ticket`，但代码、描述和请求的能力都发生了变化。

因此，首次接入时的审核不能覆盖之后全部版本。
客户端发现工具也只证明对方声明了能力，不证明发布者、代码和运行行为始终可信。

## 应该登记的是仓库名、版本号，还是实际制品？

这些信息服务于不同问题。
仓库定位源码，版本号指向一次发布，制品哈希对应实际拿到的字节，构建来源则解释它怎样产生。
仅记录 `latest` 或一个可变标签，故障时可能无法还原当时运行的内容。

| 登记项                   | 能帮助核查什么                 | 仍不能单独证明什么   |
| ------------------------ | ------------------------------ | -------------------- |
| 发布者和来源地址         | 从哪里取得工具                 | 发布者从未被入侵     |
| 锁定版本、提交与制品哈希 | 使用了哪个具体版本与字节内容   | 其中没有恶意或漏洞   |
| 依赖清单与构建来源       | 直接、间接依赖和产物的形成过程 | 扫描已经覆盖全部风险 |
| 能力和运行权限           | 工具被允许访问什么             | 实现完全遵守用途说明 |
| 审核与回归记录           | 何时依据什么条件启用           | 未来更新可以自动放行 |

签名和构建证明用于增强来源与完整性的证据，仍需结合信任根和发布流程核查。
被信任的维护者账号或构建环境失守后，单纯验证签名并不能排除风险。

## 一个工具的审核范围包含哪些内容？

先检查执行入口、安装脚本、直接和间接依赖、下载地址与所需凭据。
再检查默认文件范围、网络出口、数据留存和错误回传，确认它与业务用途一致。
查询工单状态不应默认得到全盘读写、管理员凭据或任意域名访问。

Skill 也需要检查正文、引用资源和附带脚本。
纯文本可以诱导后续动作，脚本和依赖还会实际执行代码。
将 Skill 当成“没有代码，所以无需审核”，会遗漏这些入口。

工具定义需要单独保存，包括名称、描述、输入输出 Schema 和重要的能力声明。
工具投毒可能只修改描述而不改变函数名，模型下一次看到的行为指引却已不同。
这类文本进入上下文后的信任边界，见[提示注入防护](./ai-agent-prompt-injection.html)。

## 怎样让版本固定和运行权限一起发挥作用？

下面是应用自己维护的审核记录示意，并非 MCP 或 Agent Skills 的标准字段。

```json
{
  "component": "ticket-reader",
  "release": "1.4.2",
  "sourceCommit": "教学示例中的提交标识",
  "artifactSha256": "由实际制品计算，不使用示例值做校验",
  "capabilities": ["ticket:read"],
  "scope": { "tenant": "tenant-a", "objects": "current-user-visible" },
  "networkPolicy": "approved-ticket-service-only",
  "reviewStatus": "APPROVED",
  "policyRevision": 7
}
```

固定版本减少意外变化，运行策略限制实际可访问的资源。
两者都需要执行器落实，不能只把审核记录展示给模型，再依赖它自觉遵守。

凭据应按服务和用途分配，由可信运行环境提供。
不要把主进程的全部环境变量继承给第三方子进程，也不要把令牌写进提示词、工具描述或回传结果。
具体文件与进程隔离见[代码工具沙箱](./ai-agent-sandbox-isolation.html)。

## 更新工具时，怎样区分普通升级和能力扩大？

对比新旧源码与制品依赖，检查新增网络目标、文件权限、安装步骤和数据回传。
同时比较发现到的工具定义，字段增加、默认值变化、描述改写和输出范围扩大都值得复核。

声明内容的哈希可以帮助发现变化，但格式化和字段顺序也可能改变字节。
需要先定义稳定的规范化方式，再计算声明摘要，并保留原始版本供人审查。
摘要一致只证明相应范围的内容一致，不代替对运行行为的检查。

回归至少覆盖正常查询、越用户和越租户、恶意输入、超时、取消、输出脱敏与副作用计数。
如果新版本开始申请写权限，应重新走相应授权和业务验收，不能继承只读版本的许可。

| 更新情况                     | 处理方式                           |
| ---------------------------- | ---------------------------------- |
| 修复已知问题且权限不变       | 在隔离环境验证，再逐步发布         |
| 新增写操作或外部数据目的地   | 补充用途审核与授权，不默认开放     |
| 工具定义发生无法解释的变化   | 暂停启用新定义，保留差异并核查     |
| 新版本回归出现越权或重复写入 | 阻断发布，检查真实副作用与影响范围 |

## 发现工具有问题后，撤销应该落到哪些位置？

先禁用受影响的调用入口，并撤销或轮换相应凭据。
正在执行的任务需要停止后续工作，再查询已经发出的业务操作是否完成。
缓存的工具定义、持久任务和历史草稿也需要重新检查是否还能安全继续。

回滚到旧制品时，当前权限撤销仍然有效。
不能因为恢复旧版本，就恢复已经撤销的授权、暴露旧凭据或重新发布被删除的敏感数据。
有风险的结果和工件按访问与留存规则处理，并保留必要审计证据。

定期的依赖扫描有助于发现已知问题，结果还要结合实际受影响版本、调用路径和补丁核验。
“扫描没有报警”不等于所有未知漏洞和恶意行为都已被排除。

## 小结

1. 来源、版本、实际制品和构建记录共同帮助还原运行内容，单个标识不能证明安全。
2. 审核范围包括依赖、安装行为、工具描述、Skill 正文与附带脚本。
3. 固定版本与最小运行权限分别处理变化和影响范围，执行器负责真正限制访问。
4. 更新需要比较能力和定义，再用越权、故障与副作用用例回归。
5. 撤销覆盖入口、凭据、在途任务和缓存，旧版本回滚仍服从当前授权策略。
