# 推理模型的思考预算、输出上限和调用状态怎样管理？

> 把思考强度、可计量的生成量和业务截止时间分别管理，再根据完整调用状态决定交付、续接还是结束。

## 只要回答一句“能不能升级”，为什么还会等很久？

客服问：“工单 T-1048 已经等待三天，按当前政策能升级吗？”如果只是读取状态，查询工具就能给出结果；如果还要核对工作日、产品版本和例外条款，模型需要处理更多条件。

推理模型可以在生成回答之前、输出之间或工具调用之间进行额外计算。这个过程可能消耗推理 Token，却没有立即出现用户能看到的正文。因此，“只要求一句话”不等于“只生成一句话的成本”。

先判断任务需要哪一种能力：确定性的时间计算交给代码，工单状态交给业务接口，当前政策交给检索。剩余的条件组合与解释才是模型的工作。增加思考预算不能补出没有提供的事实，也不能替代授权。

## 思考档位、Token 上限和超时，各控制什么？

| 控制项             | 主要约束                                     | 不能据此保证什么                         |
| ------------------ | -------------------------------------------- | ---------------------------------------- |
| 思考档位或思考预算 | 模型被允许投入的推理工作，具体语义由接口定义 | 每次恰好消耗相同 Token，或必然答对       |
| 最大输出 Token     | 这次调用允许生成的总量，计入范围以接口为准   | 同等长度的可见答案，或固定响应时间       |
| 请求与任务截止时间 | 应用愿意等待和继续调度的时间                 | 超时后供应商一定停止，或已执行动作会回滚 |
| Agent 总预算       | 多轮模型、检索和工具操作的累计资源           | 每轮都能用满各自的单次上限               |

OpenAI Responses API 使用 `reasoning.effort` 表达思考档位，`max_output_tokens` 限制生成总量。其他接口可能使用离散等级、Token 预算或自动策略。这些字段不是同一个单位，不能把某家的 `high` 直接换算成另一家的固定 Token 数。

档位的支持范围、默认值以及采样参数能否同时设置，都应随模型和 API 路径登记。**“所有推理模型都忽略 temperature”不是通用契约**：有的组合支持，有的拒绝，有的有额外条件。具体参数要按目标版本验证。

## 输出预算怎样给内部推理和可见答案留空间？

对输入与输出共享窗口的接口，可以先用下面的关系检查容量：

```text
完整输入 I + 预留生成量 O + 估算安全余量 M ≤ 上下文容量 C

O 的计入范围可能包含：
推理 Token + 可见回答 Token + 工具参数及其他生成格式开销
```

这里的 `I` 应包含历史、证据、工具定义及消息包装。`M` 处理估算误差，不是已经生成的 Token，更不是要额外计费的一项。若目标接口把推理消耗计入总输出上限，就不能再把它重复加一遍。

假设某次教学请求的输出上限为 3,000 Token，其中推理已经消耗 2,800。此时不能承诺还会得到完整的 200 Token 正文：其他生成内容可能也占预算，模型也可能在正文出现前就结束。更不能根据网页只显示几十个字，认定供应商多计了全部差额。

使用响应中的实际用量明细核对。例如 OpenAI Responses 提供 `output_tokens` 和 `output_tokens_details.reasoning_tokens`。两者的差值也不能未经核对就当成精确的可见正文长度，格式与其他不可见生成内容可能参与计量。

输出上限是护栏，不是收费承诺。失败、取消或无可见答案的请求仍可能产生用量，缺少 usage 时应记为未知，不能记成零费用。通用预算分配见[上下文装配](./ai-agent-context-engineering.html)。

## HTTP 200，但没有答案，应用应该怎么判断？

先解析接口的完成状态与原因，再处理正文和工具调用。不能把“有响应对象”“流正常结束”“JSON 能解析”依次替换成任务成功。

下面是 **OpenAI Responses 风格的合成响应片段**，只演示处理边界：

```json
{
  "status": "incomplete",
  "incomplete_details": { "reason": "max_output_tokens" },
  "output": [],
  "usage": {
    "input_tokens": 1200,
    "output_tokens": 3000,
    "output_tokens_details": { "reasoning_tokens": 3000 }
  }
}
```

它表示生成预算耗尽且没有可交付正文，不表示模型已经确认“不能升级”。应用应把它记成预算截断，保留尝试标识与用量，返回可理解的未完成状态。

| 观察到的情况             | 应用接下来做什么                                 |
| ------------------------ | ------------------------------------------------ |
| 已完成且有正常正文       | 检查证据、输出结构与业务语义后交付               |
| 已完成且有完整工具调用   | 验证参数、权限、预算和调用标识，再进入工具执行   |
| 达到生成上限             | 保存部分结果；判断是否有剩余预算支持新尝试或续接 |
| 拒答或内容过滤           | 按对应原因处理，不能当成格式错误反复修复         |
| 接口错误、取消或连接中断 | 区分已收到的结果与未知部分，核查外部动作状态     |

流式到来的工具参数可能只是一段 JSON 前缀。即使已经能猜出工单编号，也不能提前执行，更不能在调用整体被截断后补齐参数并提交写入。

## 多轮工具调用时，推理状态应该怎样续接？

对话正文、工具调用结果和供应商维护的推理状态是不同对象。

有的接口要求回传完整的响应项；有的可以通过前一次响应标识续接；有的返回带签名或不透明内容的状态。应用应遵循所选 API 的续接契约，保存必要的调用标识和兼容状态，不能只抽取最后一段正文。

```mermaid
flowchart LR
    A[模型返回工具调用与续接状态] --> B[应用验证并执行工具]
    B --> C[按调用标识回填工具结果]
    C --> D[使用兼容状态继续模型调用]
    D --> E[验证最终交付结果]
```

这里的“保存推理状态”不意味着应用能读到完整内部思维。摘要、可见解释与不透明状态都不能直接视为模型计算过程的完整记录。

也不能笼统采用“所有 `reasoning_content` 都手动拼回历史”的方案。是否接收这些字段、如何重放、跨轮保留哪些状态，取决于供应商、模型族、接口和版本。跨模型切换应重新做兼容判断，禁止改写签名或把不透明字段当普通文本拼接。

需要跨供应商恢复时，可以保留可验证的任务事实、工具结果和业务操作号，按新接口重新装配上下文。它与原推理计算的原样恢复不是同一个保证。相关边界见[供应商契约](./ai-llm-provider-contracts.html)。

## Java 后端怎样让配置和预算保持一致？

模型注册表可以表达应用真正依赖的能力，而不是只存模型名：

```text
模型配置：
  provider / api / modelRevision
  支持的思考控制方式与合法取值
  输出上限字段与计入范围
  支持的采样参数、工具、Schema 与续接方式

任务策略：
  总截止时间、剩余调用数、费用上限
  当前场景允许的思考档位与单次输出上限
  截断、拒答、断流与结果未知的处理规则
```

这是配置设计示意，不是某个 Java SDK 的实际类型。适配器将它转换为目标接口支持的字段；不支持时按已定义的策略拒绝或选择其他配置，并记录实际采用值，不能静默删字段后继续声称“高思考档位已生效”。

每次尝试记录请求 ID、实际模型版本、思考配置、输入输出与推理用量、首个有效输出时间、结束原因。Agent 继续下一轮之前重新检查剩余预算，避免每一轮都重新获得完整的任务额度。

超时后传播取消，并核查工具是否已经执行。若升级操作的结果未知，先按业务操作号查询；不能为了更快给出回答就换一个模型再次提交。写操作规则见[审批与恢复](./ai-agent-java-approval-recovery.html)。

## 怎样判断增加思考真的值得？

保持任务、证据、工具环境和验收标准相同，只比较目标模型支持的几个配置。将状态查询、复杂政策判断、信息不足和长上下文问题分别统计。

至少同时观察：

- 业务任务通过率，以及越权、无依据结论等硬约束。
- 首个可见内容和任务总时延的分布，超时与无答案比例。
- 输入、输出、推理用量及缺失 usage 的次数。
- 每个任务和每个成功任务的总成本，包括所有重试与续接。

如果更多思考只让状态查询变慢，没有改善复杂题，就按任务分流；若失败来自缺少必要证据，先修证据供给。评测时给每个配置相同的任务级预算，防止一组无限重试后再宣称效果更好。

“先用便宜配置、失败再升级”也要有明确失败判据。模型自称不确定不一定可靠，第二次调用还会增加时间与费用。只有在独立样本上验证了整体收益，才值得采用级联策略。

## 小结

1. 思考档位、输出上限、超时与任务总预算分工不同，不能用一个参数代替其他护栏。
2. 推理与其他生成内容可能共享输出额度，耗尽预算时可以没有可见答案，但仍产生用量。
3. 先判断完成状态与原因，再验证正文或完整工具调用；部分参数与 HTTP 成功都不能授权执行。
4. 续接需要遵守模型与接口的状态契约，不透明推理项不应任意拼接、修改或跨模型复用。
5. 思考配置按任务评测，用成功率、无答案率、时延和每次成功成本共同判断收益。
