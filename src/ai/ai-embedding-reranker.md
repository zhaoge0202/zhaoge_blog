# Embedding 和 Reranker 有什么区别，怎样用业务样本选型？

> Embedding 支持预先编码文档并快速召回，Reranker 对查询与候选共同打分，两者都需要用实际任务验证。

## 查到“升级工单”，为什么还没有回答升级条件？

假设 alice 询问“工单 T-1048 正在 `WAITING_VENDOR`，满足什么条件才能升级”。
知识库同时有取消升级的操作说明、升级条件和供应商处理 FAQ。
这几份文档使用大量相同的词，语义接近，却只有升级条件能直接支撑当前回答。

检索模型需要从大量文档中找到可能有用的候选，再判断候选能否回答问题。
语义相似只是可利用的信号，不能直接当成业务相关性或事实正确性。
实时状态还应来自工单系统，政策文档只解释相应规则。

## 双塔和 Cross-Encoder 怎样处理同一个问题？

常见的双塔检索将查询与文档分别编码，再计算向量相似度。
文档向量可以在入库时计算，用户提问时只计算查询向量，并通过索引寻找近邻。
“双塔”描述两侧独立编码，具体实现也可能共享编码器参数。

Cross-Encoder 把查询与一份候选一起输入，输出这对输入的相关性分数。
两边的 Token 可以参与联合建模，因而能利用更细的条件和交互信息。
查询改变后，需要对相应候选重新计算，不能直接复用一份与查询无关的文档得分。

| 环节               | 主要工作                           | 应检查的边界                             |
| ------------------ | ---------------------------------- | ---------------------------------------- |
| Embedding 召回     | 独立编码查询和文档，再按距离找候选 | 模型空间、输入格式、截断、索引与过滤     |
| Cross-Encoder 重排 | 对查询与候选的组合评分             | 成对输入长度、候选数量、领域相关性与耗时 |
| 最终上下文         | 选择能支撑回答的证据               | 权限、来源、版本、条件完整性和预算       |

Cross-Encoder 是常见重排实现，规则和生成模型也可以参与重排。
“Reranker 一定更准”需要在具体数据和候选集上证明，不能只由模型结构推出。

## 用小向量能看出哪些区别？

下面用人工设置的二维向量演示相似度排序，不加载真实 Embedding 模型。
三份文档均假定已通过当前身份和版本检查。
代码可直接用 Node 执行。

```javascript
const query = [1, 0];
const documents = [
  { id: "cancel-guide", vector: [0.9, 0.1] },
  { id: "upgrade-policy", vector: [0.8, 0.2] },
  { id: "vendor-faq", vector: [0.1, 0.9] },
];
function cosine(a, b) {
  const dot = a.reduce((sum, value, i) => sum + value * b[i], 0);
  return dot / (Math.hypot(...a) * Math.hypot(...b));
}
const candidates = documents
  .map((doc) => ({ id: doc.id, score: cosine(query, doc.vector) }))
  .sort((a, b) => b.score - a.score);
console.log(candidates.map(({ id, score }) => [id, score.toFixed(3)]));

// 人工假设的重排分数，仅用于演示换序，不是模型预测。
const pairScores = { "cancel-guide": 0.12, "upgrade-policy": 0.88, "vendor-faq": 0.08 };
console.log(candidates.map(({ id }) => id).sort((a, b) => pairScores[b] - pairScores[a]));
```

这里向量维度一致且均非零，第一轮结果约为 `0.994、0.970、0.110`。
以升级条件为业务标准，人工示意分数把 `upgrade-policy` 放到了第一位。
它只说明两类评分可以产生不同次序，不证明某个真实 Reranker 一定能够修正这个案例。

如果粗召回只保留第一条，升级条件已经丢失，后续重排也无法把它找回来。
分段检查必要证据的方法见[RAG 诊断](./ai-rag-retrieval-diagnosis.html)。

## 为什么换了编码接口，结果就可能变化？

有些模型对查询和文档使用不同的前缀、指令或路由。
这与模型训练方式有关，应遵守对应模型说明，不能统一给所有输入加同一个 `query:`。
Sentence Transformers 当前文档建议检索任务使用 `encode_query()` 与 `encode_document()`，由其处理模型配置中的相应提示与任务类型。
不带专门配置的模型，两者也可能与一般编码行为一致。

还要检查 Tokenizer 和长度限制。
文档尾部的“仅当已取得供应商反馈”若被截掉，向量或成对评分就无法利用这个条件。
Cross-Encoder 的查询与文档共享成对输入的容量，长查询也可能挤占文档部分。

验收时保留实际送入模型的范围、截断标记和原文引用。
需要调整切块或抽取范围时，应回到数据处理链路，不能只靠提高候选数量掩盖缺失信息。
领域缩写、错误码、中文英文混排和否定条件，也应分别进入评测样本。

## 向量维度、归一化和索引为什么要一起管理？

不同模型即使输出维度相同，也不意味着向量处于同一个可比较的空间。
编码器版本、池化、输入前缀、归一化和约定的维度都应随索引配置保存。
更换配置时使用匹配的新文档向量和查询编码流程，再验证索引切换。

非零向量都按 L2 归一化时，内积等于余弦相似度。
单位向量的欧氏距离平方为 `2 - 2 × 内积`，也具有对应的排序关系。
未满足这些条件时，不能直接把三个度量的分数互换。

度量还要与向量库查询和索引配置配套，并通过执行计划或实际检索验证。
维度较高可能增加存储、计算和索引成本，是否提升相关性仍取决于模型训练和业务数据。
不应仅按“超过多少条就换数据库”或维度大小决定方案。

Cross-Encoder 的分数同样有契约。
有些模型返回 logits，有些经过激活处理，不能把任意 `0.8` 都解释为“80% 正确”。
跨模型或跨任务阈值，需要另做校准。

## 怎样让业务样本选型具有可比性？

先固定有权限的语料快照、版本、问题和黄金证据，区分开发调参集与最终验收集。
工单场景至少覆盖精确编号、同义改写、领域缩写、跨文档条件、否定问题和应当拒答的问题。

负例应包含与正确规则很像、却不满足问题的材料。
例如“取消升级操作”和“升级条件”构成较难区分的候选。
人工标注需要说明错在哪里，并检查重复文档或等效答案，避免把合理的替代证据误标为错误。

先比较 Embedding 的必要证据 Recall@K，再固定候选集比较重排后的证据位置与覆盖。
使用分级相关性时可以看 NDCG，查看首个合格结果时可以看 MRR，仍要同时检查复杂问题是否找齐必要条件。
重排模型比较不能一边拿完整候选，另一边使用更短的截断文本却忽略这一差异。

记录模型版本、硬件或 API 配置、批次、输入长度、候选数量、p50/p95 和费用口径。
公开榜单帮助筛候选，最终选择要看本项目问集与预算。
模型质量与近似索引损失可以分别对照，避免换编码器实际只改变了索引参数。

## 分数最高的候选，什么时候仍然不能使用？

候选必须满足当前身份、文档有效版本和来源要求，进入重排服务或生成模型前还要检查相应权限。
若一份规则已经撤回，相关性再高也不能覆盖当前的可见性判断。
版本发布和缓存失效见[知识库生命周期](./ai-rag-index-lifecycle.html)。

重排后仍应保留证据 ID、页码或段落位置，以及当前问题所需的例外条件。
缺少可信证据时说明缺口，不通过相似度或单个阈值推导出业务已经可以执行。

## 小结

1. 双塔可预先编码文档并按向量召回，Cross-Encoder 对查询与候选联合评分。
2. 语义相似不自动等于业务相关，重排也无法修复候选集中不存在的证据。
3. 输入前缀、截断、编码空间、归一化和索引度量共同影响结果，维度不决定质量。
4. 选型固定授权语料与黄金证据，分别比较召回、重排、任务质量和资源成本。
5. 权限、版本和证据完整性独立于评分，最高分不能代替真实性或业务授权。
