# 表格和 Excel 怎样保住字段关系，并支持可靠查询？

> 表格证据需要同时保留字段、值、单位和来源位置，筛选与计算则应由受权限约束的确定性代码完成。

## 同一列的 1250，为什么可能被解释成错误金额？

假设 alice 问“我的工单费用共多少，其中等待供应商的有多少”。
合成样例 `tickets.csv` 中，T-1048 的 `costCents` 为 1250，单位是人民币分，状态为 `WAITING_VENDOR`。
如果解析时丢掉表头，模型可能把它当成人民币元、等待时间或其他行的数值。

文件里还包括 bob 和另一租户的工单。
即使金额计算正确，混入这些记录也会越权，并改变 alice 应得到的结果。
因此先确定可见记录和字段含义，再做统计，最后组织带来源的回答。

## 表头、合并单元格与类型怎样一起保存？

多级表头可以先还原为完整字段路径，例如“费用 / 已结算 / 人民币元”。
合并区域要保留原始范围，并按已确认的表格结构把标题关联到数据列。
不能将所有空白单元格直接向下填充，空白也可能表示未提供或不适用。

| 原始信息       | 应保留的含义                     | 需要防止的误读                 |
| -------------- | -------------------------------- | ------------------------------ |
| 工单号或产品码 | 标识字符串及原值                 | 前导零丢失，科学计数法改变标识 |
| 费用数值与币种 | 数值、单位、币种和精度           | 元与分混用，不同币种直接相加   |
| 日期与时间     | 日期格式、日期系统和业务时区约定 | 把数值直接当 Unix 时间戳       |
| 空白、缺失与零 | 分别记录未知、无值和实际零       | 空值被强制转换成零             |
| 合并表头       | 层级和覆盖区域                   | 一份标题错误套到无关列         |

Apache POI 的行和单元格迭代器可能跳过未定义的位置。
需要完整列结构时，应按预期列范围读取，并显式选择缺失或空白单元格的处理策略。
单元格的显示文本和实际类型也要分开，`DataFormatter` 的输出适合展示，不必然适合直接做数值计算。

## 公式文本、缓存结果和重新计算各能证明什么？

Excel 文件可以同时保存公式和先前算出的缓存结果。
读取 `SUM(...)` 这样的公式文本，不代表已经得到数值；读到缓存值，也不能保证它对应文件当前依赖的数据。
修改过输入单元格但没有重新计算时，缓存可能仍然是旧结果。

如果需要重新计算，应记录采用的引擎、版本、可支持的函数与所用依赖。
POI 提供公式计算能力，但不能因此承诺与所有 Excel 函数、外部工作簿和运行环境完全等价。
不支持的公式、缺少依赖和单元格错误要显式返回，不能替换成零继续求和。

外部工作簿引用需要按可信来源提供依赖，不能让解析器为了补齐引用任意读文件或联网。
只要求 Excel 在下次打开时重新计算，也不能证明当前服务端取得的结果已经更新。
本篇的实际 CSV 计算不涉及 Excel 公式引擎。

## 表格太大或跨页时，怎样保留可引用的区域？

一整张表可能超过输入窗口，可以按业务区域或行分组切分，并在各组重复必要表头、单位、表身份和来源。
只说“表格永远不能拆块”，会让大表无法处理；关键是切分后仍能正确解释每一行及其上下文。

跨页表要结合表标题、列结构、续表标记、边界坐标和内容判断是否延续。
重复表头可作为结构信息处理，但不能因此误删真实的数据行。
缺少依据时保留两份区域与待确认关系，不自动把相邻页面拼成同一张表。

Excel 证据可以携带文件标识或哈希、`sheet`、`cellRange`、`revision` 及适用权限。
跨页 PDF 表格还需要页码和区域，CSV 则记录源版本与逻辑记录号，不能伪造工作表坐标。
检索命中后再按这些标识回查原件，正文解析的方法见[PDF 与 OCR 证据](./ai-rag-document-parsing.html)。

## 怎样用一个小例子核对权限过滤和金额统计？

下面把四条合成记录直接放进代码，不依赖配套工程或外部文件。
示例主体是可信上下文的教学占位，真实接口必须从认证层取得相应身份。

```javascript
const rows = [
  {
    ticketId: "T-1048",
    tenantId: "tenant-a",
    ownerId: "alice",
    status: "WAITING_VENDOR",
    costCents: 1250,
  },
  { ticketId: "T-1049", tenantId: "tenant-a", ownerId: "alice", status: "OPEN", costCents: 500 },
  {
    ticketId: "T-1050",
    tenantId: "tenant-a",
    ownerId: "bob",
    status: "WAITING_VENDOR",
    costCents: 9000,
  },
  {
    ticketId: "T-2048",
    tenantId: "tenant-b",
    ownerId: "carol",
    status: "WAITING_VENDOR",
    costCents: 3000,
  },
];
const principal = { tenantId: "tenant-a", userId: "alice" };
const visible = rows.filter(
  (row) => row.tenantId === principal.tenantId && row.ownerId === principal.userId,
);
const total = visible.reduce((sum, row) => sum + row.costCents, 0);
const waiting = visible
  .filter((row) => row.status === "WAITING_VENDOR")
  .reduce((sum, row) => sum + row.costCents, 0);
console.log({ totalCostCents: total, waitingCostCents: waiting });
```

可见工单为 T-1048 和 T-1049，总费用为 1750 分，其中等待供应商的费用为 1250 分。
显示为元时分别是 17.50 与 12.50，不能把分直接贴到“元”后面。
bob 与另一租户的记录在计算前被排除，不能先对全表求和再从最终文本中隐藏它们。

本例假定金额已经按分转换成合法整数，所有记录币种相同。真实输入还应检查单位、币种、精度和非法值。
通用 CSV 解析必须处理带引号的逗号、嵌入换行和编码，不能用简单的字符串切分替代。
更大金额范围需要按业务精度使用十进制或适当的整数表示，并验证加总不会越界。

## 检索、SQL 引擎和模型应该怎样分工？

查询某条政策或定位一段异常说明，适合按证据检索。
对一批记录求和、分组或排序，适合让代码或结构化引擎在授权范围内计算。
模型可以帮助理解意图与解释结果，实际参与计算的记录、条件、单位和版本仍应可核查。

若允许模型提出 SQL，不能只检查开头是 `SELECT` 或补一条 `LIMIT`。
查询仍可能访问不允许的表、文件、网络函数或昂贵计算，输出限制也不会限制全部扫描成本。
应同时约束数据源与对象、函数、文件和出站访问、执行时间、内存及结果大小，并由服务端执行租户过滤。

汇总记录也应保留查询条件、授权主体、数据版本与来源范围，避免只留下一个无从核实的数字。
结果不完整、字段含义未确认或部分页解析失败时，应说明限制，不能把局部和当作全部。
图片中的表格或图表还需保留原图依据，见[视觉证据](./ai-rag-visual-evidence.html)。

## 怎样区分解析正确、计算正确和回答正确？

先用人工标定核对表头、行列、金额单位、空值、公式状态和源坐标。
再针对可信身份检查筛选记录及汇总，最后检查回答的数值、单位和引用是否与这些结果一致。
三步都要能定位到原始输入，检索和生成分段归因见[RAG 诊断](./ai-rag-retrieval-diagnosis.html)。

上面的四条记录可以手算核对，也可以单独执行片段验证。它只检查给定记录的筛选与求和。
真实 Excel 公式、跨页表和 OCR 是否正确，还需要各自的原件、标定答案和解析检查。

## 小结

1. 表头、单位、数据类型与行列位置共同组成表格含义，空白、缺失和零不能随意互换。
2. 公式文本、缓存值和重新计算是不同结果，错误或未支持公式需要保留状态。
3. 大表可以按区域或行分组，跨页续表需有依据，每份片段都保留字段上下文和可回查位置。
4. 权限筛选先于聚合，结构化引擎执行计算，模型依据结果解释，SQL 只读与结果限制不能代替完整隔离。
5. 解析、计算和回答分别验收，合成记录的计算通过不能证明真实 Excel 或 OCR 已经正确处理。
