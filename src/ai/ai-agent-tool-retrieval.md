# 工具上百以后，Agent 怎样检索并装配正确工具？

> 先限定当前主体可以发现的工具，再检索候选、加载完整定义；工具被找到或被模型选中，都不代表已经获得执行授权。

## 工具接得越多，为什么反而容易调错？

假设工单平台接入了工单、订单、知识库和运维系统，共有数百个工具。客服只问：“T-1048 能不能升级？”

如果把全部定义交给模型，查询、创建草稿、提交审批等相近工具会同时出现。它们既占输入预算，也增加混淆机会；名称都包含 `ticket`，不表示职责相同。

更合理的做法，是让本轮上下文只包含当前需要的能力。高频查询工具可以常驻，其他工具按需发现，再加载完整定义。

下面讨论的是教学架构，没有部署工具检索服务，也没有实际执行工具。基础运行过程见[Agent 运行时](./ai-agent-runtime-loop.html)。

## 找到工具、装入工具和执行工具，分别发生什么？

三个阶段需要分开：

| 阶段 | 要解决的问题                 | 产物               |
| ---- | ---------------------------- | ------------------ |
| 发现 | 当前主体有哪些相关能力可用？ | 经过过滤的候选引用 |
| 装配 | 本轮模型可以选择哪些工具？   | 完整定义与版本映射 |
| 执行 | 这次具体调用现在是否允许？   | 经过验证的执行结果 |

例如，客服可以发现“提交升级申请”工具，但只有拿到符合要求的确认，才能执行某次提交。工具可见性不等于对象权限，更不等于操作已经批准。

```mermaid
flowchart LR
    A[审核后的工具目录] --> B[按可信身份过滤]
    B --> C[检索相关候选]
    C --> D[加载完整定义]
    D --> E[模型提出调用]
    E --> F[执行器重新验证]
    F --> G[执行并回填结果]
```

## 工具目录应该登记哪些东西？

目录既要支持搜索，也要让执行器知道实际调用的是谁。只保存名称和一句描述，难以处理跨服务同名、版本变化和撤权。

下面是应用自行设计的目录记录，**不是 MCP 标准字段**：

```json
{
  "stableId": "ticket.read",
  "namespace": "support",
  "server": "approved-ticket-server",
  "version": "3",
  "schemaHash": "完整定义的实际摘要值",
  "description": "读取当前主体可访问的工单状态",
  "risk": "READ_ONLY",
  "policy": "ticket-read-policy",
  "status": "APPROVED"
}
```

`stableId` 标识业务能力，`server` 与 `version` 定位具体实现，摘要值检查定义是否变化。描述应说明用途、必要参数和不适用场景。

风险与审核状态由可信管理流程维护，不能因为第三方描述写着“只读、安全”便自动通过。定义、依赖和执行制品的关系见[工具供应链](./ai-agent-tool-supply-chain.html)。

## 为什么要先过滤，再搜索？

工具名称、描述和参数也可能泄露内部信息。例如，无权访问某项目的人，可能不应知道对应的事故处理工具存在。

因此，搜索前先依据可信主体、应用、租户和策略限定可发现范围，搜索结果也不能泄露被排除工具的元数据。

身份来自认证与执行上下文。用户输入“帮管理员查工单”只是查询意图，不能让搜索器切换到管理员目录。

可发现范围内，可以组合几种方法：

- 名称、编号和领域词较明确时，使用关键词匹配。
- 表达变化较大时，比较语义检索的补充价值。
- 已知业务入口时，先限定领域，再检索域内能力。

工具搜索器只查询受控目录，不根据模型给出的任意 URL 临时连接新 Server。新增接入仍需独立审核。

## 候选找到了，怎样安全地交给模型？

候选引用应解析到已审核版本的完整定义。不能为了省 Token，随意删掉必填参数、枚举或关键用途说明。

跨服务存在同名工具时，可以分配符合目标模型命名规则的别名，例如 `support_ticket_read_r3`。宿主保存准确映射：

```text
模型可见别名
→ 稳定能力标识
→ Server 与具体版本
→ 完整 Schema 摘要
→ 实际执行入口
```

这份映射属于本轮装配状态。模型返回别名后，执行器按保存的映射解析，不能临时从最新目录中随便找一个同名工具。

Anthropic 的公开方案展示了延迟加载：搜索先返回工具引用，再展开对应定义。`defer_loading` 属于其平台机制，不是所有模型或 MCP 宿主通用的字段。

无论采用哪种实现，都要分别计算搜索、加载和额外模型轮次的成本，不能只看第一次请求少了多少定义。

## Top K 很小，为什么可能丢掉必要步骤？

假设模型最先找到“提交升级申请”，但完整任务还需要查询工单、读取政策、生成草稿和取得确认。

如果机械地只保留最相近的两个工具，必要前置能力可能没有装入。接下来模型就容易猜参数，或反复请求不存在的动作。

可以将少量高频能力常驻，再按任务补充工具。稳定流程也可以声明允许的依赖关系，由应用检查前置能力是否齐全。

依赖展开必须继续服从授权与预算。某工具依赖管理员能力，不代表当前用户因此获得该能力，更不意味着加载后立即执行。

Skill 可以说明处理顺序，执行器负责落实约束，二者的分工见[技能与执行环境](./ai-agent-skills-harness.html)。

## 多轮运行时，什么时候继续找工具？

每次补查都应对应明确缺口。例如，已经取得工单状态，但尚未找到读取适用政策的能力，下一次发现就围绕这个缺口展开。

运行状态可以保存已装配工具、版本、已尝试查询、未满足需求、剩余定义预算和停止原因。

继续发现之前，检查是否还有新线索，而不是只把上一句搜索词改几个字。典型停止条件包括：

- 当前允许的能力已经足以推进任务。
- 缺少必要对象信息，需要用户补充。
- 当前授权范围不允许完成该步骤。
- 连续搜索没有新增有效候选。
- 调用次数、时间或上下文预算耗尽。

没有找到工具时，应区分内部原因，不能统一归结为“模型不会用”：

| 内部分类                | 主要问题                       |
| ----------------------- | ------------------------------ |
| `catalog_missing`       | 目录没有登记所需能力           |
| `retrieval_miss`        | 能力存在于允许范围，但未被召回 |
| `model_selection_wrong` | 定义已经装入，模型仍选错       |
| `arg_invalid`           | 工具正确，参数不符合契约       |
| `auth_revoked`          | 发现后权限发生变化，执行被拒绝 |

对外提示仍遵守元数据保密要求，内部诊断分类不能成为探测受限工具的入口。

## 目录更新和撤权后，旧候选还能用吗？

检索缓存至少关联目录版本、适当的授权作用域和检索配置；定义缓存还应绑定具体版本与摘要。

缓存命中只是减少查找工作，执行时仍要检查当前权限、工具启用状态、对象范围和业务前提。

假设工具在发现后被停用，执行器应拒绝继续使用。若 Schema 已变化，则按策略重新装配或报告版本失效，不能静默把旧参数交给新实现。

写操作的确认也要绑定实际操作意图与关键参数。工具升级改变了动作含义时，原确认不能自动覆盖新行为。

工具描述和结果都可能包含诱导性文本，检索排名不会提升它们的信任等级。相关运行约束见[提示注入](./ai-agent-prompt-injection.html)与[沙箱隔离](./ai-agent-sandbox-isolation.html)。

## 怎样判断这套检索真的有价值？

使用相同任务、权限、目录版本和总预算，比较固定工具集合与按需装配方案，逐层观察：

1. 所需能力是否存在于授权目录。
2. 必要工具是否进入候选并完成装配。
3. 模型是否选择正确工具并生成合法参数。
4. 实际业务终态是否正确，是否发生越界或重复动作。
5. 搜索次数、定义 Token、总延迟与费用是否改善。

对没有可用工具的任务，还要检查系统是否正确停止。空结果、检索服务故障和权限拒绝应分别记录。

目录规模只是一个变量。工具描述质量、任务差异与模型能力都会影响收益，不应拿某次公开实验的节省比例作为项目承诺。

## 小结

1. 发现、装配和执行是不同阶段，工具可见或被选中都不能替代具体调用授权。
2. 先限定可发现范围，再检索候选，工具元数据同样需要保护。
3. 加载完整定义并保存别名到具体版本的映射，不能通过同名工具静默替换实现。
4. 常驻能力与按需加载可以组合，必要依赖、循环和预算由应用控制。
5. 分别检查目录、召回、选择、参数与业务终态，用整体成本判断收益。
