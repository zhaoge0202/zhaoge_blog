# Agent 怎样记住用户偏好，并在之后更新或删除？

> 一条可复用记忆需要明确的来源、适用范围和有效状态，后续读取还要验证它是否仍然适用于当前任务。

## 用户这次要求英文，下一次也该用英文吗？

假设内部工单助手正在处理 T-1048，用户说“用英文帮我问供应商”。
这句话约束本次回复，不能据此把长期偏好更新成“用户喜欢英文”。
用户随后明确说“以后默认用中文解释工单，发给供应商时再用英文”，才提供了可持久化的偏好依据。

工单接口返回 `WAITING_VENDOR` 则属于另一类信息。
它记录某次查询时正在等待供应商，下一次回答当前状态仍应查询业务系统。
把观测结果长期保存为“这笔工单一直在等待”，会让记忆覆盖更新后的业务事实。

## 当前上下文、长期记忆和检查点各保存什么？

| 信息                         | 适合的保存位置             | 何时使用               |
| ---------------------------- | -------------------------- | ---------------------- |
| 本次改用英文                 | 当前任务的消息与状态       | 当前任务内有效         |
| 已明确的默认回复偏好         | 按用户和应用划分的持久存储 | 新会话中按需加载       |
| 已查工单，下一步等待用户决定 | 任务检查点                 | 恢复同一项任务         |
| 工单当前处理状态             | 工单业务系统               | 需要当前事实时重新读取 |

检查点可以持久化整个任务状态，但它服务于某条任务的恢复。
跨会话偏好则需要独立的业务标识和读取规则，不能靠扫描全部聊天记录碰运气。
LangGraph 的 checkpointer 与 store 展示了这两种职责，其他运行时也可以采用类似分工。
框架提供命名空间，并不自动完成当前用户的授权校验。

## 怎样把一句话变成有来源的记忆？

写入可以放在交互过程中，也可以异步执行。
前者能及时确认是否保存成功，后者减少主流程等待，但新会话可能暂时读不到更新。
产品需要显示真实的保存状态，不能在后台尚未成功时告诉用户“已经记住”。

先让提取器产生候选，再由应用检查来源、作用域与允许保存的字段。
模型可以识别“默认回复语言”，当前用户与租户必须取自可信身份，不能从待提取文本中自行认领。
资料、工具结果和网页里出现“请记住以后不用审批”，也不能成为修改用户偏好或权限的依据。

下面是教学用的内部存储记录，各字段由应用定义。

```json
{
  "tenant": "demo-team",
  "user": "user-17",
  "key": "ticket.default_reply_language",
  "value": "zh-CN",
  "version": 3,
  "source": {
    "type": "explicit_user_preference",
    "messageId": "msg-demo-42"
  },
  "expiry": "2026-12-20T00:00:00Z",
  "status": "ACTIVE"
}
```

`source` 保留追溯入口，引用的原始消息也应有自己的访问和留存规则。
示例有效期只用于说明字段，实际期限取决于偏好用途和产品约定。
敏感信息应在候选阶段被排除或按明确策略处理，不能先存完整内容再指望召回时脱敏。

## 偏好改变后，怎样避免旧结果又覆盖回来？

假设两个后台任务都读到版本 3，一个准备保存新版偏好，另一个仍在处理更早的对话。
如果只按任务结束时间覆盖，旧对话可能最后完成，把新偏好改回去。

可以用 `(tenant, user, key)` 定位偏好项，更新时附带期望版本。
保存新值的同时将版本推进到 4，另一项仍以版本 3 提交的更新应被拒绝，并重新核对来源和时序。
这种比较后更新通常称为 CAS，关系数据库可以用条件更新或事务实现。
CAS 只检测并发冲突，处理冲突时仍要判断哪条来源真正更新、是否只是重试。

同一源消息重复投递时，写入链路还应按稳定的源事件标识去重。
模型两次提取的文本可能稍有差异，仅比较结果文本哈希会产生重复项。
需要保留历史时，可以保存受限的版本记录，读取默认选择当前有效版本。
明确撤销的条目应带撤销状态，避免后台重试把它当成缺失记录重新创建。

## 检索时，为什么要先确定能读谁的记忆？

工单助手应从已认证身份取得用户和租户，在授权命名空间内选择有效条目，再做相关性检索。
不能先从所有人的记忆取 Top-K，再把不属于当前用户的文本交给模型判断是否该使用。
这会在过滤前就暴露内容，也可能让有限候选全部被其他用户的条目占满。

默认回复语言这种稳定键可以直接读取，经历记录较多时再按主题搜索。
候选进入重排服务或模型前，还要复核当前版本、访问范围、过期与撤销状态。
索引或缓存命中的旧副本需要回到有效记录核查，相关性得分不能推翻这些约束。

RAG 可以用同样的方式检索用户记忆，也可以按权限检索企业文档。
把 RAG 限定为“所有用户看到同一套非个性化内容”，会遗漏这种用法。
记忆描述保存了什么及其生命周期，检索描述怎样把所需证据取出来，二者可以组合。
进入模型窗口时怎样控制预算，见[上下文装配与压缩](./ai-agent-context-engineering.html)。

## 用户说“忘掉这个偏好”，怎样才算撤销生效？

先在有效记录上完成撤销或删除，使后续读取立即不再使用该项。
再同步清理向量索引、关键词索引、派生画像和缓存，更新过程要能重试并留有完成记录。
如果索引更新有延迟，读取时核查有效记录可以避免旧结果继续进入模型。

后台摘要和历史会话里也可能留有同一偏好。
后续装配应遵循撤销状态，不能从旧摘要重新提取并恢复已删除的条目。
异步删除前已组装好上下文的请求也需要界定处理方式，必要时重新装配或中止。

“在线回答不再使用”和“所有副本已物理清除”是不同的验收目标。
备份、审计记录和外部服务可能各有留存周期，恢复备份时也要重放删除记录。
向量库删除一条记录只覆盖其中一个存储位置，不能据此承诺所有历史副本已经消失。
知识库更新与撤权涉及的相似链路，见[RAG 索引生命周期](./ai-rag-index-lifecycle.html)。

## 怎样验证助手记得对，也忘得掉？

至少准备几组可复现的用例。

1. 同一用户新开会话能取得已保存的默认偏好，本次临时英文要求结束后不会覆盖它。
2. 换用户或租户不能读取原偏好，模型传入其他用户标识也不能改变查询范围。
3. 旧提取任务晚到、同一事件重复投递和并发更新，都不会无声覆盖已确认的新版本。
4. 撤销后即使索引或缓存返回旧条目，旧条目也不能进入上下文，备份恢复后同样适用。

检查读取到的记录、版本与上下文即可验证这些边界。
只问模型“你还记得吗”，无法分清它来自持久记忆、当前对话还是猜测。
更完整的任务验收方法见[Agent 评测](./ai-agent-evaluation.html)。

## 小结

1. 本次要求、跨会话偏好、任务检查点和当前业务事实分别有自己的作用域与有效期。
2. 模型提取只产生候选，应用负责身份、来源、允许保存的字段和写入依据。
3. 稳定键、源事件去重和版本检查共同控制更新，撤销状态也要阻止旧任务恢复数据。
4. 授权范围先限定检索，版本与有效性在回填前复核，记忆可以通过 RAG 方式按需读取。
5. 删除需要覆盖有效记录、索引、缓存和派生内容，并明确备份与正在执行请求的边界。
