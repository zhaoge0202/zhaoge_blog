# 业务模型怎么选，什么情况下值得换？

> 先确定每类任务的成功标准和准入条件，再用同一批样本比较实际交付的质量、延迟和成本。

## 工单助手要完成什么，才能算答对？

假设我们给客服做了一个工单助手。客服先问“T-104 等了多久”，有时接着问“按供应商的特殊条款，这单能不能升级？”
第一问要读到正确的工单和最新状态，第二问还要判断政策版本、适用条件和例外条款。两者都能生成一段通顺的话，成功标准却不同。

| 工单样本   | 评测时要核对的交付物                                                     |
| ---------- | ------------------------------------------------------------------------ |
| 状态与分诊 | 用合法的工单编号查只读接口，状态、队列或优先级符合预期，字段通过业务校验 |
| 政策适用   | 条件与例外讲全，引用能定位到该用户可见的正确条款                         |
| 信息不足   | 明确缺少哪个字段或哪份证据，正确追问或转人工                             |
| 无权访问   | 拒绝访问，且下游调用记录和输出都没有泄露其他租户的信息                   |

候选模型先过两类硬门槛。部署条件核对数据可发往的区域、供应商留存条款和租户许可。接口条件验证业务所需的工具、输出 Schema、流式行为和上下文空间。真实数据路径与功能能力都要按模型版本和接口配置登记。 [供应商能力与契约验证](./ai-llm-provider-contracts.html)

比如客服用“分诊建议”入口时，Java 后端需要可解析的队列和优先级。候选能返回合规 JSON，还要检查队列是否对当前租户开放。权限由业务服务校验，评测要同时检查模型行为和服务端拦截结果。通过这些条件的候选再比较质量、延迟和成本。

## 怎样保证两套配置做的是同一道题？

每条样本保存 `caseId`、输入、调用者身份、工单快照、政策版本和通过条件。高频题用于比较日常负载，专门选出的例外条款、超长输入和拒答题单独报告。用脱敏样本和隔离的工具替身复测，每次都从相同状态开始。先用一批样本调配置，再用留出的样本作比较，减少对已知题目的适配偏差。

一条 `caseId` 分别交给 A 和 B。两边收到同一任务和证据，应用使用同一身份、权限快照与截止时间。同一个工具请求需要还原同一份业务结果。

负载测试也采用相同的请求分布与并发计划，冷热缓存分别报告。候选请求可以交错运行，减少把时段和上游负载变化误算到某一版头上。

业务语义相同的适配可以保留，比如按各模型的接口编码同一份工具契约。若 B 同时换了 Prompt、检索或重试策略，报告应标明比较的是两套部署配置。

同一题重复跑时先汇总这道题的结果，保留按题配对的数据用于后续判断。涉及业务正确性的字段用程序判定，开放式解释按相同评分规则复核。 [CI 评测门槛](./ai-eval-ci-release-gates.html)

## 首字更快、单次更便宜，客服为什么还是等得久？

以一次业务请求为单位计时。从客户端提交到首个可展示文本是首字时延，从提交到客户端观察到成功、失败或超时终态是任务耗时。

上游首个分片、空心跳或工具事件可能先到，界面仍未出现文字。首字 P95 始终配上有首字的任务比例，便于发现大量请求还没开始回答就已失败。 [首字延迟的测量边界](./ai-llm-inference-latency.html)

设每套配置都跑同样的 200 个教学任务，其中 140 个是状态与分诊，60 个是政策适用。每个任务最多一次额外尝试，测试客户端到 6 秒就记录超时终态。任务终态 P95 使用全部 200 条的已观测耗时。首字 P95 使用已收到可展示文本的任务。下表是便于核算的假设结果。

| 指标                           | A         | B         |
| ------------------------------ | --------- | --------- |
| 状态与分诊成功                 | 133/140   | 135/140   |
| 政策适用成功                   | 41/60     | 55/60     |
| 全部任务成功                   | 174/200   | 190/200   |
| 收到首字的任务                 | 188/200   | 196/200   |
| 首字 P95                       | 0.70 秒   | 0.90 秒   |
| 任务终态 P95                   | 6.00 秒   | 4.20 秒   |
| 任务超时                       | 12/200    | 4/200     |
| 模型调用次数（含额外尝试）     | 250       | 220       |
| 单次模型调用均价               | 0.55 分   | 0.66 分   |
| 模型调用总费用                 | 137.50 分 | 145.20 分 |
| 平均每个成功任务的模型调用费用 | 0.79 分   | 0.76 分   |

在这组数字里，A 首字更早，有 12 条任务耗时到达 6 秒。把 200 条任务按耗时升序排列，按最近秩法取第 190 条，A 的终态 P95 已到了截止时间。只看成功任务的耗时会漏掉这 12 次超时。

按每次成功计算，A 是 `137.50 ÷ 174 ≈ 0.79 分`，B 是 `145.20 ÷ 190 ≈ 0.76 分`。A 单次便宜，多做了 30 次额外尝试，失败任务的花费也要摊到成功结果上。

实践中从任务 ID 追到每笔调用，再按实际计费项目加总。假设一条任务第一次调用花了 0.40 分并在交付前断开，第二次花了 0.70 分，最后交付成功。这条任务记一次成功、两次调用、1.10 分。两次都失败时，仍要把 1.10 分计入总花费，成功数不增加。

检索、重排或人工转接因候选方案而有明显差异时，也报告完整交付成本。断流后缺失的账目先挂待核对，给出未确认用量和估算范围。若一套方案没有成功任务，报告总支出与零成功，单位成功成本没有分母。 [多次调用的用量记录](./ai-llm-provider-contracts.html)

## 为什么升级某类工单，比全量切模型更好判断？

如果业务在请求进入时已经知道入口是“查询状态”还是“解释政策”，可以分别设置成功条件。例如状态组至少 94% 成功，政策组至少 90%，再各自通过延迟、超时和安全检查。用上表的点估计练习判断，A 的状态组为 `133/140 = 95.0%`，政策组为 `41/60 ≈ 68.3%`。B 的政策组为 `55/60 ≈ 91.7%`。这些差异支持把“状态走 A、政策走 B”纳入下一轮对照。

还可以检查分组账目。假设表内均价在分组中也成立，A 的状态组共 152 次调用，成功成本约 `83.60 ÷ 133 ≈ 0.63 分`。B 同组共 146 次调用，成功成本约 `96.36 ÷ 135 ≈ 0.71 分`。

如果入口能精准分组，沿用 A 的状态组与 B 的政策组，教学账上合计成功 `133 + 55 = 188` 条，花费 `83.60 + 48.84 = 132.44 分`。每次成功约 0.70 分，全量用 B 时约为 0.76 分。

混合方案的净成功数少 2 条。接受这项取舍前，要逐题检查它修好了什么、又答错了什么，特别是有没有退步发生在必须答对的场景。阈值从业务风险与可接受降级确定，实际样本量由关键分组和所需精度决定。

自然语言入口如果要先分类，再把分类也纳入评测。重点观察“把政策题误分到状态组”的代价，计入判别调用、额外等待和失败后升级的开销。在本业务问集上分别测状态组和政策组，才能知道多走强模型换回了多少质量。 [RouteLLM 的质量与成本对照](https://arxiv.org/abs/2406.18665)

若先用 A，再在证据规则或格式校验失败后转 B，应验证仍有时间预算、输出还可以完整交付、先前的尝试没有未确认的副作用。 [流式切换的边界](./ai-llm-provider-contracts.html)

## 哪类失败应该先修检索或工具？

比如正确答案需要两份证据。一份说“等待 24 小时可升级”，另一份说“指定供应商需等待 48 小时”。A 和 B 都选了 24 小时，先回看模型实际收到的输入，再做一个小对照。

| 回放结果                                   | 优先检查                                       |
| ------------------------------------------ | ---------------------------------------------- |
| 两版都收到一般规则，缺少例外条款           | 查召回、过滤、排序和证据装配                   |
| 两版输入都有正确证据，A 多次漏用有效例外   | 核对适配是否丢字段，再比较模型处理长上下文能力 |
| 两版都跟随了工具返回的旧状态               | 核对工具缓存、数据版本、权限和业务结果契约     |
| 样本里存在多个合理答案，评分规则只接受一种 | 复核标注和评分方式，再用同一道题对照           |

先用固定的正确证据和工具结果跑一轮，再放回完整链路看效果。换模型要解决的是候选配置中可重复的差异。有些问题只要补齐证据或校验工具参数就能修好，这类改动也应单独回放验证。 [RAG 逐段排障](./ai-rag-retrieval-diagnosis.html)

## 换版后怎样确认收益，出了问题怎样退？

一次候选发布记录模型标识、返回的实际版本、接口与 Prompt 版本、模板和工具契约、评测集与计价时间。

同一套配置离线过门槛后，再对目标任务稳定分组灰度。保持一组控制流量并行观测，把成功率、转人工、首字、总耗时与真实账单按场景拆开。除监测窗口外还要设关键场景的最小观察量。涉及权限或写入时，用隔离替身做旁路回放，避免复制真实请求的业务副作用。 [灰度与评测准入](./ai-feature-rollout-guard.html)

上线前就验证回退目标可用。候选超过止损线时，将新任务切回仍然可用且过验收的配置，已经启动的会话保持可追溯的版本，按约定结束或恢复。某些供应商滚动别名无法固定底层快照，观察到版本漂移时应重新确认候选与回退配置。如果旧快照已下线，使用提前验证过的备用模型或产品兜底。 [Google SRE 灰度发布](https://sre.google/workbook/canarying-releases/)

## 小结

1. 先按业务任务定义成功，确认数据边界、工具、输出与上下文能力，再比较候选。
2. 同题对照要固定证据、工具状态和预算。比较部署配置时，记录随模型一起改变的条件。
3. 首字与任务终态分别计时。每次成功的成本包含失败与额外尝试的花费。
4. 分组决定是否换模型。回放先确认失败出在检索、工具、评分还是模型行为。
5. 用分组灰度验证实际收益，保留已验收且当前可用的回退配置。
