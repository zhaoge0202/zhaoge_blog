# CPU 缓存和 MESI 协议是怎么回事？

CPU 每秒能执行几十亿条指令，但去内存拿一次数据要几百个时钟周期——这个速度差，就是 CPU 缓存存在的理由。而多核各自有私有的 L1/L2 缓存，又带来了“一个核改了、别的核还看到旧值”的缓存一致性问题，MESI 协议就是来解这个问题的。

## 为什么需要 CPU 缓存

两个原因合在一起：

- **速度差**：CPU 频率远高于内存，直接每次都读内存，CPU 大部分时间在等数据。
- **局部性原理**：程序访问的数据有局部性——时间局部性（刚访问过的还会再访问）和空间局部性（访问了一个地址，附近地址大概率也会被访问）。

把最近用到的数据连同邻近数据一并缓存到离 CPU 更近的 SRAM 里，命中率够高时，CPU 就基本不用等内存了。

## L1/L2/L3 和缓存行

现代多核 CPU 的缓存层级：

- **L1 / L2**：每个核**私有**，L1 还拆成 L1d（数据）和 L1i（指令）。
- **L3**：所有核**共享**，容量最大、速度最慢但比内存快。
- **缓存行（cache line）**：CPU 从内存读数据的基本单位，通常是 **64 字节**。即使你只读一个 int，也会把它所在的 64 字节整行搬进缓存——这是空间局部性的硬件体现。

| 层级 | 私有 / 共享 | 容量量级 | 访问周期 |
| ---- | ----------- | -------- | -------- |
| L1   | 每核私有    | KB 级    | ~2~4     |
| L2   | 每核私有    | 百 KB 级 | ~10      |
| L3   | 全核共享    | MB 级    | ~40      |
| 内存 | —           | GB 级    | ~200~300 |

## 写直达 vs 写回

缓存有了数据，写操作怎么同步回内存，有两种策略：

- **写直达（Write Through）**：写的时候同时写缓存和内存，简单但每次写都访问内存，慢。
- **写回（Write Back）**：写的时候只改缓存，标记这一行“脏”，等这一行要被替换时才写回内存。命中率高时性能好得多，现代 CPU 基本用写回。

## 缓存一致性问题：写传播 + 事务串行化

多核各有私有 L1/L2，写回策略下会出现经典问题：A 核把 `i` 改成 1 只写在自己缓存里，B 核去内存读 `i` 拿到的还是 0——两个核的缓存不一致，结果错。

要解决，必须做到两点：

- **写传播**：一个核改了缓存里的数据，要让别的核知道（通过总线广播）。
- **事务串行化**：所有核看到的“数据变化顺序”必须一致——不能 A 核看成先 100 后 200、B 核看成先 200 后 100。

> 有的资料把“事务串行化”类比成“引入锁的概念”，这个类比会误导：MESI 并不依赖传统意义上的互斥锁，而是靠**每个缓存行的状态机 + 总线消息**来约束状态流转，让所有核对同一缓存行的读写顺序达成一致。“锁”只在概念上帮助理解“同一时刻只允许一个核独占写”，但 MESI 的实现是状态机不是锁。

## 总线嗅探与 MESI

实现写传播最直接的方式是**总线嗅探（Bus Snooping）**：每个核监听总线上的广播，发现别人改了自己也缓存的数据就处理一下。纯嗅探的问题是广播太频繁、总线压力大。MESI 在嗅探基础上加了**状态机**，让很多写操作不需要广播，从而压低总线带宽。

MESI 是四种状态的首字母：

| 状态           | 含义                         | 这一行数据干净吗 | 是否独占         |
| -------------- | ---------------------------- | ---------------- | ---------------- |
| M（Modified）  | 已修改，和内存不一致（脏）   | 否               | 是（只有本核有） |
| E（Exclusive） | 独占，和内存一致             | 是               | 是（只有本核有） |
| S（Shared）    | 共享，和内存一致，多个核都有 | 是               | 否               |
| I（Invalid）   | 失效，不能用                 | —                | —                |

关键在于 **M 和 E 状态下，修改数据不需要广播**：因为只有本核有这行数据，改了别人也不知道有它，自然不用通知。只有 S 状态下要改，才需要先发“让你们都失效”的广播，把自己变 M 再改。这就是 MESI 比纯嗅探省带宽的原因。

一个典型流转：

1. A 核读入变量 `i`，只有 A 有这行 → **E**（独占、干净）。
2. B 核也读 `i`，A 把数据给 B，双方都有 → 都变 **S**（共享、干净）。
3. A 要改 `i`，广播让别的核失效 → B 的变 **I**，A 改完 → A 变 **M**（独占、脏）。
4. A 再改 `i`，还是 M，**不用广播**，直接改。
5. A 这行要被替换，M 状态先写回内存，再换。

## 伪共享：性能杀手

缓存行是 64 字节，而一个 `int` 只有 4 字节——意味着**相邻的多个变量很可能落在同一缓存行**。如果两个核分别高频写同一缓存行里的不同变量，按 MESI，每次写都要让对方那行失效，于是这行在两个核之间反复 invalidate / 重新加载，明明没共享变量却互相拖累，这就是**伪共享（false sharing）**。

解法是**让两个变量不在同一缓存行**——补齐填充，让它们各占一行：

- 手动 padding：在变量前后塞无用的字段凑够 64 字节。
- Java 里用 `@sun.misc.Contended`（JDK 8+，需加 `-XX:-RestrictContended`）让 JVM 自动填充。

Disruptor 就是靠缓存行对齐让生产者序号和消费者序号不落在同一行，避免伪共享，这是它高吞吐的关键之一。

## Store Buffer、内存屏障与 volatile

实际 CPU 为了不让“等总线 invalidate 广播”阻塞自己，在 MESI 之上又加了**Store Buffer**：写操作先写进 Store Buffer 就继续往下走，invalidate 消息异步发出去等别的核 ACK。这提升了单核性能，但也引入了**指令重排**——后续读到的是还没真正落地的旧值，顺序被打乱。

于是又引入**内存屏障**：

- **Store Barrier（写屏障）**：强制把 Store Buffer 刷到缓存，让之前的写对别的核可见。
- **Load Barrier（读屏障）**：清空 Load Buffer，确保读到的是最新值。

Java 的 `volatile` 就是靠插入内存屏障来保证可见性和有序性的：对 volatile 变量的写会插入 Store Barrier，读会插入 Load Barrier，于是别的核能看到最新值、禁止了相关重排。注意 volatile **不保证原子性**（`i++` 还是会丢更新），它管的是可见性和有序性，不是互斥。

## 小结

- CPU 缓存因“速度差 + 局部性”而存在，L1 / L2 私有、L3 共享，基本单位是 64 字节的缓存行。
- 写回策略下多核会出现缓存不一致，需要写传播 + 事务串行化；MESI 靠状态机而非传统锁来实现。
- M / E 状态下改数据不用广播，是 MESI 比纯总线嗅探省带宽的关键。
- 伪共享：同缓存行的不同变量被多核高频写会反复失效，靠 padding / `@Contended` 错开缓存行（Disruptor 典型案例）。
- Store Buffer 引入重排，内存屏障兜底；Java volatile 靠内存屏障保证可见性和有序性，但不保证原子性。
