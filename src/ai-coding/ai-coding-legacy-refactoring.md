# 怎样让 AI 重构遗留 Java 模块，同时保留原有行为？

> 先把需要保留的行为变成可核对的基线，再让 AI 小步调整结构；代码变短、测试变绿，都不能单独证明兼容。

## 一个导出 Service 太大，为什么不能直接让 AI 拆类？

假设订单系统有一个很长的 `OrderExportService`，同时负责权限过滤、读取订单、计算结算金额、拼接 CSV、保存文件和发送完成通知。

AI 很容易把它拆成查询器、计算器和渲染器，类名更清楚，方法也更短。但新版本可能把空结果从 `null` 改成空文件，把行内舍入改成汇总后舍入，或者改变相同时间订单的排序。

这些变化未必导致编译错误，却可能改变调用方行为或财务结果。

本文使用构造的教学案例，没有运行 Java 工程或测试。讨论的是怎样制定重构与验收方案，不是真实项目的执行记录。

## “保持行为不变”，应该先约定哪些行为？

重构通常是在约定的可观察行为保持不变的前提下改善结构。这里的行为不只是方法签名和接口字段。

先沿入口、调用者、查询、计算、存储与通知梳理链路：

| 边界       | 需要确认的行为                       |
| ---------- | ------------------------------------ |
| 身份与权限 | 谁能导出，允许哪些订单进入结果       |
| 请求与响应 | 参数默认值、空值、错误码和返回格式   |
| 计算       | 金额单位、舍入方式、税费与退款口径   |
| 排序与时间 | 时区、区间边界、稳定排序和同值次序   |
| 数据与事务 | 使用哪个快照，何时提交，失败是否回滚 |
| 外部副作用 | 文件写入、通知及重复请求如何处理     |
| 资源       | 分页、内存、连接与大结果处理方式     |

方法签名没变，但从逐页读取变成一次加载全部订单，也属于需要检查的变化。

这些约束应来自调用方、业务规则和已有代码证据。不能让 AI 根据“通常应该怎样”自行补全，再把补全后的设计称为兼容。

## 怎样建立行为基线，而不是复制一堆旧输出？

可以先为旧模块设计特征测试，也就是记录它面对可解释输入时的可观察行为。

本例至少准备：正常订单、空结果、权限不足、相同时间的多条订单、跨时区边界，以及存在舍入差异的金额。

每份夹具都要说明为什么存在，预期约束是什么。例如：

```text
用例：两个订单的业务时间相同。
要检查：旧契约要求按订单号继续排序，新实现不能随机换序。

用例：当前用户只能读取部分订单。
要检查：过滤发生在计算和文件生成之前。

用例：结算结果含三位小数。
要检查：按既定规则逐行舍入，再形成汇总。
```

固定时钟、输入快照、配置与必要依赖版本，避免同一检查随当前时间或数据库内容变化。

完整文件快照可以帮助发现变化，但要区分业务字段与时间戳、随机标识等非确定部分。只能按明确规则规范化后者，不能把金额、顺序和错误信息全部忽略。

## 旧实现有错误，也要原样保留吗？

行为基线描述现状，不代表现状全部正确。

如果业务确认某种旧行为是缺陷，就单独记录要改变的范围、正确判据及对调用方的影响。先明确这是行为修正，再更新相关预期。

例如，旧实现把无权限请求当空结果返回。是否改成拒绝，应结合接口约定判断，不能在“拆分类”的提交里顺手完成。

否则，审查者无法分清某个差异来自结构调整，还是来自新的业务决定。

基线也不能由实现者为了让检查通过随意改弱。更新预期时，要能说明规则为何变化，而不是只说新实现输出不同。

## 金额和空值，为什么是最容易被“简化”的地方？

假设两笔折算后的明细各为 `0.335` 元，教学规则要求逐行按 `HALF_UP` 保留两位小数，再汇总。

逐行得到 `0.34 + 0.34 = 0.68`；先求和再保留两位，则是 `0.67`。两种代码都很简洁，但含义不同。

因此，提取计算逻辑时要固定：

- 输入与输出单位，是元、分还是其他精度。
- 舍入发生在哪一步，采用什么模式。
- 空金额表示未知、无记录还是确实为零。
- 汇总是否包含被过滤、取消或退款的订单。

`null` 改成 `0`、空对象改成空列表，也要看调用方如何解释。减少空值判断不能成为改变协议的理由。

长订单号同样不能为了统一数据类型先转成 `double`。标识与可计算数值承担不同职责，格式化输出不能损失原始身份信息。

## 应该怎样拆，才能让每一步都可检查？

先寻找容易隔离的接缝，而不是一次性重写整条链路。

一种顺序是先提取纯计算，再显式传入依赖，最后通过适配层保留原有入口：

```java
public ExportArtifact export(
        ExportRequest request,
        AuthenticatedCaller caller) {
    var snapshot = snapshotLoader.loadVisibleOrders(request, caller);
    var lines = settlementCalculator.calculate(snapshot, calculationRules);
    var content = legacyCsvRenderer.render(lines, exportFormat);
    return artifactWriter.write(content, request.operationId());
}
```

这段代码只说明职责，省略类型、授权和失败处理，不是一份可运行实现。

第一次调整可以只提取计算方法，保留原调用顺序与格式；下一次再拆查询依赖；确认边界后，才考虑改变内部数据流。

每一步都检查差异和对应判据。若提交示例需要表达意图，可以使用 `refactor(订单): 提取结算明细计算`，不要把结构调整与依赖升级、协议变更塞进同一次修改。

## 拆成新类之后，事务和代理会自动保持吗？

不会。原来由 Spring 代理调用的方法，改成同类内部调用或私有方法后，即使注解仍在，也不能据此认定事务边界相同。

反过来，为了“保证一致性”把整个导出入口加上事务，可能让文件写入、通知 HTTP 或模型调用都发生在长事务中。

重构方案应明确读取快照需要什么一致性、计算是否纯内存、文件写入失败怎样处理，以及通知与业务记录怎样关联。

查询器被拆到另一个 Bean，也要核对它实际经过的代理与配置。代码移动到了新文件，不等于已经验证了运行语义。

Mock 可以帮助检查分支，但不会证明目标数据库的锁、提交、序列化或真实 HTTP 行为。证明范围见[测试分层与 Testcontainers](../engineering/engineering-integration-test-testcontainers.html)。

## 给 AI 的任务，怎样避免从重构滑向重写？

任务说明应包含确定基线、允许范围和完成判据：

```text
目标：先提取订单结算纯计算，不改变导出入口和外部协议。
基线：指定提交及对应的行为夹具。
只读输入：接口契约、计算规则、排序与错误码约定。
允许修改：计算实现及为本次提取所需的调用位置。
约束：
- 不升级依赖，不改表结构，不改变文件列与金额口径。
- 不删除失败用例，不放宽断言，不扩大事务。
- 发现旧行为与业务规则冲突时，先列出差异。
交付：修改说明、对应判据及尚未执行的检查。
```

有必要改变共享契约或数据结构时，先重新评估影响范围。不能因为新设计更方便，就默认调用者愿意一起迁移。

具体任务拆分方法见[规范驱动编程](./ai-coding-spec-coding.html)，差异审查见[AI 代码验收](./ai-coding-acceptance.html)。

## 新旧实现怎样对照，才不会产生两次副作用？

对纯计算，可以让相同夹具分别进入新旧实现，比较金额、排序、字段和异常语义。

但不能为了对照完整导出流程，就向真实支付、通知或外部写接口各调用一次。结果相同，也可能已经重复执行。

可以把副作用入口替换为隔离的接收端，或只回放记录下来的只读输入，比较“计划产生什么动作”。真正的写入语义另设受控验收。

如果使用影子流量，还要限制数据范围、费用和资源，避免旁路读取敏感信息或拖慢正式请求。

合法差异应事先列入检查规则；不能在看见结果不同以后，临时把该字段排除。跨服务字段与语义的核对见[接口契约测试](../engineering/engineering-api-contract-testing.html)。

## 什么证据才能支持“这次重构可以交付”？

验收应绑定整合后的具体提交，分别检查：

1. 关键夹具上的业务输出与禁止变化。
2. 接口、文件格式、错误和排序契约。
3. 目标组件上的事务、数据库与外部调用边界。
4. 大结果下的内存、分页和资源释放。
5. 回退配置，以及已经产生的数据和副作用如何处理。

覆盖率提高，只说明更多代码被执行；AI 自评“逻辑等价”，也不能替代这些证据。

回滚代码不自动撤销已写文件、已发通知或数据库迁移。需要迁移时，应单独设计兼容窗口和恢复步骤，不能把它附带在本次结构调整中。

本文只提供判据，没有执行这些检查。关于能抓住缺陷的断言，可继续看[Java 缺陷与测试案例](./ai-coding-java-bugfix-walkthrough.html)。

## 小结

1. 先明确外部行为、事务与资源边界，再让 AI 改结构，方法签名不变不代表兼容。
2. 行为基线使用可解释夹具，旧缺陷另行确认，不能随意复制或放宽预期。
3. 金额、空值、排序、标识和时间规则容易被简化，小步提取时要分别核对。
4. 新旧对照限制副作用，Mock、覆盖率和模型自评都不能证明完整运行语义。
5. 交付证据绑定具体版本，重构、依赖升级和数据迁移分清范围，代码回退不等于业务撤销。
