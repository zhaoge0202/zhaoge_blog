# 手写一个 RPC 框架再读源码的一次复盘

读源码最怕的就是"看得懂每一行，看不懂为什么这么写"。我之前读 Dubbo，觉得它的 Filter 链、Exchange 层、Header 协议拆得真细，但说不出它为什么要拆成这样。后来我干了一件事：**自己先手写一个最小 RPC 框架**，把能想到的坑全踩一遍，再回头读源码。这次复盘让我明白，源码里很多"看起来绕"的设计，其实都是被某个具体问题逼出来的。

## 我写的那个简易框做了什么

不追求生产级，就追求一条调用链能跑通，目标是把 RPC 的关键环节都自己实现一遍：

1. **服务端**：注册一个接口的实现，起一个 Netty 服务监听端口。
2. **客户端**：用 JDK 动态代理生成接口的代理对象，调用时把接口名、方法名、参数类型、参数序列化成请求。
3. **协议**：自定义一个简单的协议头（魔数 + length + requestId），body 用 Hessian 序列化。
4. **网络**：Netty 做 NIO 通信，客户端用 `requestId` 把响应和请求关联起来（多路复用）。
5. **服务发现**：先用一个本地 Map 当注册中心，后面换成写个简易 ZooKeeper 注册。

跑通那一刻挺爽，但接下来全是坑。

## 踩的坑，和源码里的对应答案

### 坑一：粘包拆包

我一开始直接 `writeAndFlush`，客户端多发几次就乱码了——TCP 是字节流，没边界。我才知道要做**协议头定界**：先读固定长度头拿 body length，再按 length 读 body。后来读 Netty 的 `LengthFieldBasedFrameDecoder`，发现它就是把这套流程封装好了，Dubbo 的 `ExchangeCodec` 也是这个套路。

> 源码里看着复杂的编解码，本质就是"先读头再按头读体"，我自己踩过才觉得不绕。

### 坑二：序列化的兼容

我用了 Java 原生序列化，加了个字段，老客户端调新服务直接 `InvalidClassException`——序列化版本号变了。我才知道生产 RPC 不用 Java 原生，得用能向前兼容的（Protobuf 按字段编号、Hessian 字段增减容忍）。读 Dubbo 默认 Hessian、gRPC 用 Protobuf，就理解了为什么是这个选型。

### 坑三：线程模型

服务端我一开始用"一个连接一个线程"，连接多了线程炸了。改成 Netty 的 Reactor 模型后，又遇到业务慢调用把 worker 线程占住，影响别的连接。这才理解 Dubbo 为什么有**业务线程池**和 IO 线程分离——IO 线程只管读写，业务逻辑扔到独立线程池，慢业务不拖垮 IO。

### 坑四：超时和重试

客户端没配超时，下游卡住我自己也卡死（线程池打满）。加了超时，又发现重试会把下游打爆——一次失败重试三次等于放大三倍流量。读 Dubbo 的 `cluster` 层Failover/Failfast 策略、看 gRPC 的 retry policy，就明白"重试要克制、要分场景"不是空话。

### 坑五：服务发现的优雅

我用本地 Map 做注册中心，服务端一挂，客户端还往死地址发请求。后来做心跳、做实例摘除、做订阅通知，越做越像注册中心。再读 ZooKeeper/Nacos 做注册中心的实践，才知道那些"临时节点心跳""订阅推送""保护阈值"每个都是被这类问题逼出来的。

## 这次复盘最大的收获

**自己写一遍，是读源码最好的预习**。

- 不写过粘包，看 `LengthFieldBasedFrameDecoder` 只觉得是个工具类；写过了才知道它是定界的命根子。
- 不做过线程分离，看 Dubbo 的 `AllDispatcher` 只觉得分了好多层；做过了才知道 IO 和业务不分会出人命。
- 不踩过重试放大故障，看容错策略只觉得是配置项；踩过了才知道每种策略防的是什么。

读源码的顺序也因此变了：以前从入口一路 `debug` 往里钻，容易陷在细节里；现在先问"这层是为解决什么问题而存在的"，带着自己踩过的坑去对照，看哪个类对应我哪个坑，一下就通了。

## 给也想读源码的人

1. **别一上来就读大框架**，先挑一个你能复刻的小功能（比如 RPC、连接池、缓存），自己写个能跑的最小版本。
2. **刻意留坑**，不要照着源码写，自己凭理解写，坑会自动暴露，这些坑就是源码设计要解决的问题。
3. **再读源码时做对照**：它的每个抽象、每层划分，对应我哪个坑、用了什么手段解决。读不懂的地方，多半是你还没踩到那个坑。
4. **挑核心链路读**，别想逐行读完整个框架。RPC 就读调用链 + 协议 + 注册发现，Spring 就读 IoC 启动 + Bean 生命周期，剩下的用到再读。

## 小结

- 读源码看不懂"为什么这么写"，往往是因为没自己踩过那个坑。
- 手写一个最小 RPC 框架，把粘包、序列化兼容、线程模型、超时重试、服务发现全踩一遍，再读 Dubbo/gRPC 就通了。
- 源码的抽象和分层，大多是被具体问题逼出来的：定界、线程分离、容错策略、注册中心机制。
- 读源码顺序：先问"这层解决什么问题"，再带坑对照，而不是从入口逐行 debug。
- 挑核心链路读，别贪大求全；挑一个能复刻的小功能自己写，是读源码最好的预习。
