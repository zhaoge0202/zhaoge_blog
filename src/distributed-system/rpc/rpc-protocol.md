# RPC 协议怎么设计？序列化、协议头和私有协议怎么取舍？

RPC 调用流程讲的是"调用经历哪些步骤"，但每一步在网络上到底传什么字节，就是 RPC 协议的事。协议设计直接决定了 RPC 的性能、扩展性和兼容性——为什么 Dubbo 有自己的协议头、为什么 gRPC 跑在 HTTP/2 上、为什么序列化格式选型这么重要，都藏在协议层。

## RPC 协议要解决什么

一次 RPC 调用，要把"调用哪个接口、哪个方法、什么参数、什么返回值"编码成字节流，跨网络传给对端，对端解码、执行、再把结果编码回来。协议要解决：

- **定界**（粘包拆包）：TCP 是字节流，没有消息边界，怎么知道一个请求到哪结束。
- **序列化**：对象怎么转字节、字节怎么转对象。
- **元数据**：接口名、方法名、参数类型、调用 ID（多路复用时关联请求响应）。
- **扩展性**：协议头要能加新字段不破坏老版本。

## 协议头：定界的核心

主流做法是**协议头（header）+ 协议体（body）**：

```
+--------+--------+--------+--------+
| magic  | length |  flags |  ...   |  协议头（定长）
+--------+--------+--------+--------+
|         body (序列化后的请求体)     |  协议体（变长）
+------------------------------------+
```

- **magic（魔数）**：固定几个字节（如 0xdabb），用来快速判断"这是个 Dubbo 协议包"，垃圾数据或粘包半包能立刻识别丢弃。
- **length**：body 长度，有了它就知道读到哪是一个完整包——**这就是粘包拆包的标准解法**：先读头拿 length，再按 length 读 body，不够就等。
- **flags / request id**：标记请求 / 响应、调用 ID（多路复用：一个连接上多个并发请求，靠 ID 关联响应）。
- **扩展字段**：序列化类型、压缩、版本等。

读包流程：读魔数校验 → 读 length → 按 length 读 body → 解码。这就是 Netty 里 `LengthFieldBasedFrameDecoder` 干的事。

## 序列化：协议体的编码

| 方案       | 特点                             | 适用                         |
| ---------- | -------------------------------- | ---------------------------- |
| JSON       | 文本、可读、跨语言、慢、体积大   | HTTP API、调试、跨语言低要求 |
| Protobuf   | 二进制、紧凑、快、需 IDL、跨语言 | gRPC、高性能内部 RPC         |
| Hessian    | 二进制、Java 友好、Dubbo 默认    | Java 内部 RPC                |
| Kryo / FST | 二进制、Java、快、不支持跨语言   | Java 内部高性能              |
| Java 原生  | 慢、不跨语言、安全风险           | 不推荐                       |

选型权衡：跨语言选 Protobuf / JSON；纯 Java 内部高性能选 Kryo / Hessian；调试和兼容外部选 JSON。

> 序列化的坑：Java 原生序列化有反序列化 RCE 风险（历史上很多 CVE），生产别用；Hessian 也有过反序列化漏洞，要限制白名单或升级。

## 私有协议 vs 通用协议（HTTP / gRPC）

- **私有二进制协议**（Dubbo 协议、自研协议）：紧凑、快、可控，但要自己处理编解码、网关透传、多语言支持。内部服务间高频调用适用。
- **HTTP/2 + Protobuf（gRPC）**：复用 HTTP/2 基础设施（网关、LB、TLS），跨语言，生态好，但有 HTTP 头开销和 Trailers 处理复杂度。
- **HTTP + JSON（REST）**：通用、易接、调试方便，但性能最差，适合对外 API。

取舍：内部对性能极致要求用私有协议或 gRPC；对外开放用 HTTP；要跨语言和生态用 gRPC。

## 协议设计的常见坑

- **不要用特殊分隔符定界**（如换行）：body 里含分隔符就乱，固定长度头才是正道。
- **大消息**：超长 body（几 MB）占内存、可能触发拆包，RPC 一般传引用或分块，大数据走文件 / MQ。
- **向后兼容**：协议头留足保留字段，加字段不破坏老端；序列化用 Protobuf 的字段编号机制天然兼容。
- **心跳与空闲**：协议层要支持心跳包，避免长连接被防火墙断开。

## 小结

- RPC 协议解决定界（粘包拆包）、序列化、元数据、扩展性；协议头（魔数 + length + flags + id）+ 协议体是主流结构。
- length 字段是粘包拆包的标准解法：先读头拿 length，再按 length 读 body。
- 序列化跨语言选 Protobuf / JSON，纯 Java 高性能选 Kryo / Hessian，别用 Java 原生序列化（RCE 风险）。
- 私有协议快但要自己造轮子，gRPC 复用 HTTP/2 生态，REST 通用但慢。
- 协议别用分隔符定界，大消息别走 RPC，协议头留保留字段做向后兼容。
