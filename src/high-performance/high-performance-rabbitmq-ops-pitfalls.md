# RabbitMQ 生产环境最容易踩哪些坑？

> RabbitMQ 用起来简单，出问题时表现却很像“神秘卡死”。这篇把最常见的几类事故按“现象 → 原因 → 处置”整理成清单。

上一篇讲的是可靠性机制，这一篇讲运维视角：**为什么本地跑得好好的，一上生产就各种怪现象。**

先看几个非常典型的现象，它们背后是不同的坑：

| 现象                                             | 大概率原因                                       |
| ------------------------------------------------ | ------------------------------------------------ |
| 生产者全部卡住、日志停止输出，消费者还在正常消费 | 触发了内存/磁盘告警，Broker 阻塞了发布连接       |
| 队列深度不高，但业务明显堆积                     | 消息全在 unacked 状态，prefetch 太大或消费者卡死 |
| 只有一个队列特别慢，加机器也没用                 | 单个队列副本是单核热点，扩消费者不扩队列         |
| 应用启动直接报 406 / 403                         | 拓扑声明参数不一致，或用了 `amq.` 前缀的队列名   |
| 一条坏消息让整个队列反复重试、业务全停           | 默认 requeue 行为导致的投递循环                  |
| 跨机房部署后消息莫名丢失或重复                   | Erlang 网络分区（脑裂）                          |

## 内存与磁盘水位：Broker 会用“阻塞发布”保护自己

RabbitMQ 有一套资源告警机制（alarm）：节点内存或磁盘用超阈值时，它不会丢消息，而是**阻塞所有发布消息的连接**，让消费者继续把队列消费掉，等水位降下来再自动恢复。

这个行为的细节值得记牢：

- 被阻塞的是**发布连接**（客户端会收到 `connection.blocked` 通知），消费连接不受影响。所以“生产端全卡、消费端还活着”是它的典型特征。
- 是**全集群传播**的：一个节点触发告警，其他节点也会阻塞发布。这点很多人不知道，排查时容易只看单节点。
- 它的本质是流量刹车，不是容量保护。阈值只是“开始拦”的点，不代表之前不会 OOM。

内存阈值的关键参数：

| 参数                                    | 说明                                                               |
| --------------------------------------- | ------------------------------------------------------------------ |
| `vm_memory_high_watermark.relative`     | 相对可用内存的比例，**当前默认 0.6**（早期版本是 0.4，别背老数字） |
| `vm_memory_high_watermark.absolute`     | 绝对内存上限，容器环境推荐用它                                     |
| `vm_memory_high_watermark_paging_ratio` | 达到阈值的这个比例时开始把队列内容换页到磁盘，默认 0.5             |

两个实践要点：

1. **容器里一定用 absolute**。RabbitMQ 对 cgroups 限制的探测在不同 Erlang/OS 版本上并不可靠，按相对值算出来的阈值可能远大于容器实际内存，结果是被 OOMKill 而不是被自己的告警拦住。
2. **别把阈值调高当解决方案**。阈值调到 0.9 只是把“阻塞发布”换成“更快 OOM”。真正的解法是让队列能消费掉：扩消费者、修慢消费、加 TTL/长度上限。

磁盘同理，`disk_free_limit` 触发时也是阻塞发布。quorum queue 对磁盘 IO 的要求明显高于 classic queue（每次提交都要 fsync 日志），机械盘上跑 quorum 队列很容易看到“吞吐上不去、延迟抖动大”。

## 单个队列是单核热点：这条约束决定扩容姿势

官方文档的措辞很直接：一个队列副本（无论 leader 还是 follower）的热路径基本只使用一个 CPU 核，因此**单个队列在多数场景下是反模式**。

这解释了一类很常见的困惑：业务量涨了，消费者实例从 4 个扩到 40 个，吞吐却不涨。原因不是消费者不够，而是这个队列本身只能单核跑，40 个消费者抢一个队列的投递能力。

正确的扩容方向：

| 做法                         | 说明                                                          |
| ---------------------------- | ------------------------------------------------------------- |
| 按业务维度拆队列             | 订单按业务线/地区拆多个队列，每个队列独立消费者               |
| 用 `x-modulus-hash` Exchange | 按 routing key 取模散到 N 个队列，天然分流                    |
| 需要按 key 保序时            | 每个队列单消费者（或 Single Active Consumer），顺序和并行兼得 |
| 吞吐到极限时                 | 换 stream + stream 协议客户端，队列模型不适合再往上顶         |

反过来说，如果你的业务量根本没到这个量级，却在纠结“队列是不是要拆 64 个”，那是在做无效优化。判断依据应该是队列的发布/投递速率和消费者利用率，不是拍脑袋。

## unacked 堆积：队列不深但业务不动

这是 prefetch 相关的经典陷阱。队列页面上 `ready` 很小、`unacked` 很大，消费者进程内存却在涨，业务没进展。

机制回顾：

- `prefetch` 决定一个消费者手上最多有多少条未确认消息。
- prefetch 太大（或 `autoAck=true` 的无限制投递）时，Broker 会把大量消息一次性推给消费者，消息卡在客户端缓冲区，看起来队列已空。
- 消费者处理慢时，这些消息既没被处理、也没被确认，**别的实例也拿不到**，于是“扩容无效”。

排查顺序：

1. 看 `unacked` 数量是否接近 `消费者实例数 × prefetch`。
2. 看消费者侧的线程池/连接池是否被打满（常见于消费逻辑里同步调用了慢接口）。
3. 调小 prefetch（核心业务从 10-50 起）验证吞吐是否反而更稳。

管理界面里还有个更好用的指标：**consumer utilisation（消费者利用率）**，表示“消费者有消息可处理的时间占比”。低于 30% 通常说明 prefetch 或消费者数量设置不当；接近 100% 说明确实消费不过来，该扩容了。这个指标比单纯看队列深度更能定位问题。

## 连接与 Channel：最容易在代码层出问题的部分

### Channel 不是线程安全的

上一章提过，这里给具体后果：多线程共用一个 Channel 发消息，会出现帧交错，客户端可能抛 `AlreadyClosedException` 或 `IOException`，也可能静默发出内容错乱的消息。这不是“偶发网络问题”，是使用方式错了。

正确做法：

- 每个线程（或每个消费回调执行上下文）独立 Channel；
- 或者用连接池封装，借出 Channel 时保证独占；
- 消费端的 ack 必须在收到消息的**同一个 Channel** 上做。

### 连接风暴与 Channel 频繁创建

两种反向的坑：

| 坑                   | 表现                           | 处置                                    |
| -------------------- | ------------------------------ | --------------------------------------- |
| 每条消息新建连接     | 连接数飙升、端口耗尽、CPU 抖动 | 复用长连接，连接池化                    |
| Channel 频繁创建销毁 | Erlang 进程调度抖动、CPU 升高  | 复用 Channel，控制单连接 Channel 数量级 |

官方建议单连接的 Channel 数控制在几十到两百之间，且不要低于这个数量级的复用粒度。还有一种间接表现：`file descriptor` 打满导致节点崩溃。RabbitMQ 每个连接和队列都占 fd，加上未确认消息的内部引用，`ulimit -n` 建议至少 10 万级，容器环境要单独配置。

### 心跳与连接保活

默认心跳间隔是 60 秒。客户端与 Broker 之间如果隔着 LB 或 NAT，空闲连接可能被中间设备悄悄断开，表现为“隔一段时间就重连一次”。排查这类问题：先看客户端日志里的连接重建频率，再对比 LB 的空闲超时，把心跳设成小于 LB 超时的值。

## 网络分区：跨机房部署绕不开的一道坎

RabbitMQ 集群靠 Erlang 分布式机制同步元数据，对网络抖动非常敏感。跨机房、跨可用区部署时，一旦节点之间出现网络分区（split-brain），会出现两套“各自认为自己是正常”的集群状态，后果是队列状态不一致、消息重复或丢失。

处理策略在配置项 `cluster_partition_handling` 里：

| 策略             | 行为                                 | 适用                       |
| ---------------- | ------------------------------------ | -------------------------- |
| `pause_minority` | 少数派节点自动暂停服务，避免数据分叉 | 推荐，集群节点数 ≥3 时使用 |
| `autoheal`       | 分区恢复后选一方继续，另一方数据丢弃 | 可接受少量丢失的非核心业务 |
| `ignore`         | 不处理，靠人工介入                   | 基本不要用                 |

更根本的解法是新版本的方向：**用 quorum queue**。它基于 Raft，多数派不可用时队列直接不可写，天然不会分叉——用“暂时不可用”换“不会脑裂”，这是可靠的取舍。

还要注意集群节点数的常识：3 节点容忍 1 节点故障，2 节点集群没有容错能力（多数派还是 2，挂一个就写不进），所以**别用双节点做高可用**。

## 拓扑声明漂移：406 和 403 的实战含义

这两个错误码上一章提过，这里补处置方法，因为它们是“上线第一分钟就撞墙”的高频问题：

| 错误                      | 触发                                                                                 | 处置                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `406 PRECONDITION_FAILED` | 同名队列/Exchange 的属性与声明不一致（durable、exclusive、auto-delete、x-arguments） | 删除重建（会丢消息）或让声明方对齐配置；根治是把拓扑收敛成一份声明，应用只校验不改 |
| `403 ACCESS_REFUSED`      | 使用了 `amq.` 前缀的名字，或 vhost 权限不足                                          | 改名；检查用户在该 vhost 的 configure/write/read 权限                              |

第二个还有一个部署期常见变体：**默认用户 `guest` 只允许本机登录**。容器化部署时应用从别的机器连过来会被拒绝，正确做法是创建业务用户并按 vhost 授权，而不是把 `guest` 放开。

## Spring Boot 集成：几个默认值会咬人

Java 项目大多通过 Spring AMQP 接入，下面几个默认值值得核对一遍：

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: manual # 手动 ack，auto 是可靠性杀手
        prefetch: 20
        default-requeue-rejected: false # 默认是 true！
        concurrency: 5 # 最小并发消费者数
        max-concurrency: 20
        retry:
          enabled: true
          max-attempts: 3
```

重点说 `default-requeue-rejected`：它默认是 `true`，意味着监听器抛异常时消息会被 requeue。结合上一章讲的“requeue 会放回队头”，一条必然失败的消息会在队头反复重投，本地/测试环境的表现是“日志里同一条消息一直在报错”，生产上的表现是整个队列被一条坏消息堵死。

三种处理方式的取舍：

| 方案                                    | 特点                                     |
| --------------------------------------- | ---------------------------------------- |
| `default-requeue-rejected: false` + DLX | 推荐，失败进死信，可人工归因和重放       |
| 容器重试（`retry.enabled`）             | 进程内重试，快但重启即失效，适合瞬时抖动 |
| 业务自己控制重试计数 + 延迟队列         | 最可控，成本最高，核心链路值得           |

另外两个参数容易被忽略：`concurrency` / `max-concurrency` 决定每个 `@RabbitListener` 的消费者数量（等于 Channel 数），设太大反而会把 prefetch 的效果冲掉；`acknowledge-mode: manual` 之后一定要记得在业务成功分支里 `basicAck`，忘了 ack 的消息会一直挂在 unacked，直到连接断开才回来。

## 监控清单：先看哪几个指标

运维视角的收尾是一张指标表。数量不用多，但这几个必须有告警：

| 指标                       | 为什么重要                        | 参考阈值                               |
| -------------------------- | --------------------------------- | -------------------------------------- |
| `messages_ready`（按队列） | 积压的直接信号                    | 按业务定，通常 >1w 告警                |
| `messages_unacknowledged`  | 消费者卡死或 prefetch 过大        | 接近 `实例数 × prefetch` 时告警        |
| 内存占水位比例             | 触发告警后会阻塞全部发布          | 接近 `vm_memory_high_watermark` 时预警 |
| 磁盘剩余                   | 同上，且 quorum 对 IO 敏感        | 剩余 <20% 预警                         |
| file descriptors 使用率    | 打满会直接崩节点                  | >80% 预警                              |
| consumer utilisation       | 判断该扩容还是该调 prefetch       | 长期 <30% 说明配置不当                 |
| 连接数与 Channel 数        | 连接风暴/Channel churn 的先行指标 | 与基线比突增即告警                     |
| 网络分区事件               | 脑裂的唯一直观证据                | 出现即告警（日志关键词 partition）     |

排障顺序建议固定下来，避免每次都靠猜：

1. **先分清是“发不进”还是“消费不动”**：看发布速率和 ready/unacked。
2. 发不进 → 查资源告警（内存、磁盘、连接阻塞）、查 confirm/return 错误率。
3. 消费不动 → 查 unacked、消费者利用率、消费逻辑耗时（慢 SQL、慢下游）。
4. 都不对 → 查拓扑（绑定是否漂移、队列类型是否被改）、查网络分区日志。

如果是纯粹的“消息堆起来了怎么办”，处置顺序（止血 → 扩容 → 修慢消费 → 批量重放）在[消息积压篇](/high-performance/high-performance-message-backlog.html)里已经展开过，这里不重复。

## 小结

- 内存/磁盘告警会**阻塞所有发布连接**且在全集群传播，消费不受影响；容器里用 absolute 阈值，别靠调高水位解决容量问题。
- 单个队列副本是单核热点，扩消费者不扩队列等于白扩，正确姿势是拆队列或用 `x-modulus-hash` 分流。
- prefetch 太大（或 auto-ack）会把消息堆成 unacked，队列看着空、业务却不动，用 consumer utilisation 判断该扩容还是该调参。
- Channel 非线程安全、连接要复用但 Channel 数别乱飙；fd 上限要拉到 10 万级，否则节点会直接崩。
- 跨机房要防 Erlang 网络分区：配置 `pause_minority`，根本解法是 quorum queue；别用双节点集群做高可用。
- Spring AMQP 的 `default-requeue-rejected` 默认是 `true`，配合 requeue 回队头的特性会让一条坏消息堵死整个队列，生产必须改成 `false` 走死信。
