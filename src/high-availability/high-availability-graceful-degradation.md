# 服务降级怎么做才不变成「摆设」？有哪些常见降级策略？

降级和熔断常被一起说，但不是一回事：熔断是"下游不行了我就不调了"的自动保护，降级是"这个功能现在保不住了，我用次优方案顶一下"的主动取舍。降级做不好，要么形同摆设（开关定义了从不触发），要么一刀切（核心功能也降级掉），这篇讲怎么把降级做成真正能用的兜底。

## 降级和熔断的区别

|      | 熔断               | 降级                                     |
| ---- | ------------------ | ---------------------------------------- |
| 触发 | 自动（统计失败率） | 可自动（熔断时联动）也可手动（运营开关） |
| 目的 | 保护调用方不雪崩   | 在能力不足时保核心、弃非核心             |
| 范围 | 单接口 / 下游      | 业务功能粒度                             |

熔断常带 fallback（被熔断时走降级逻辑），所以熔断的 fallback 是降级的一种触发场景，但降级不只有熔断触发。

## 常见降级策略

### 1. 读降级

读不到就返回兜底：缓存挂了返回默认值、推荐服务挂了返回热门列表、个性化挂了返回通用。原则是**读链路允许"差不多"**，用次优数据顶上，不让用户看到 500。

### 2. 写降级

写不进去就降级：数据库主库挂了写消息异步补偿、发短信通道挂了转日志后续补发、计数器写不进降级到本地累加。原则是**写链路允许"晚一点一致"**，先收下再补。

### 3. 同步转异步

下单高峰，扣库存同步太慢，转成"先返受理、异步处理"；发券高峰，同步发券堆积，转 MQ 异步发。把强一致实时操作降级为最终一致异步操作。

### 4. 关闭非核心功能

大促前关闭推荐刷新、积分结算、数据上报、日志采集这类非核心。**保核心交易，弃次要功能**——这是降级的本质：资源不够时优先保命。

### 5. 兜底数据 / 默认值

列表为空返回默认商品、搜索失败返回热搜词、用户信息查不到返回游客态。让页面"有东西看"而不是空报错。

## 降级怎么"不变成摆设"

很多团队降级开关写了但从没用过，原因：

- **开关和代码脱节**：开关定义了，但代码里没判断；或判断了但 fallback 逻辑没实现。演练时才发现开关无效。
- **降级路径没测试**：平时从没走过降级，真触发时降级逻辑本身有 bug，比主链路挂得更彻底。
- **降级判断条件不合理**：触发条件设得过严（要 99% 失败才降）或过松（一次超时就降），线上抖动频繁误触发。

要让降级可用：

1. **开关可热更新**（配置中心），别等重启。
2. **降级路径要演练**：定期手动触发降级开关，验证 fallback 真能用。
3. **降级分级**：P0 / P1 / P2 按优先级，先降 P2（非核心），不够再降 P1，P0（核心交易）尽量不降。
4. **可观测**：降级触发要打日志、上报指标，否则线上"为什么走了降级"查不清。

## 自动降级 vs 手动降级

- **自动降级**：熔断触发 fallback、超时返回默认——代码内置，响应快，但策略固定。
- **手动降级**：大促前运营通过配置中心关闭某功能——灵活，按预案走，但需人介入。

成熟方案两者都要：自动降级兜小故障，手动降级（预案 + 开关平台）兜大促 / 故障。

## 小结

- 降级是"保核心弃非核心"的主动取舍，熔断是"下游不行就不调"的自动保护，二者常配合但目的不同。
- 五类降级：读降级返兜底、写降级转异步补偿、同步转异步、关闭非核心、兜底默认值。
- 降级不变成摆设的关键：开关热更新、降级路径要演练、降级分级、可观测。
- 自动降级兜小故障，手动降级（预案 + 开关平台）兜大促，两者都要。
